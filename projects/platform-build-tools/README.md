# @mfe/platform-build-tools

## 이 프로젝트를 처음 열었다면

[HTML 개발 안내서](../../docs/mfe-project-handbook.html#project-platform-build-tools) · [실행·발행 순서](../../docs/mfe-project-handbook.html#workflow) · [플랫폼 제공 목록](../../docs/mfe-project-handbook.html#platform)

- 담당: 플랫폼 팀.
- 목적: 서비스 팀이 충돌 방지 설정을 매번 직접 작성하지 않도록 공통 빌드 규칙을 배포합니다.
- 사용: 다른 프로젝트의 devDependencies에서 vendor의 npm tarball을 설치합니다. 브라우저에서 불러오는 SDK와는 별도입니다.
- 수정 시점: 빌드 규칙을 바꿀 때 수정합니다. 새 도구를 패키징해 필요한 소비 프로젝트가 도입하고 다시 빌드해야 반영됩니다. 기존 배포 파일은 바뀌지 않습니다.

| 주요 파일 | 역할 |
| --- | --- |
| [lib/project.cjs](lib/project.cjs) | 입력 검증, 소스 해시와 배포 ID 생성, MF 의존 선언 해석. 런타임 의존성은 소비자 ID와 별칭으로 조회하도록 변환합니다. |
| [bin/mfe-build.cjs](bin/mfe-build.cjs) | Webpack·Babel 설정, React 공유, CSS Modules, 다른 프로젝트 소스 import 차단, dist와 release.json 생성. |
| [lib/retry-loader.cjs](lib/retry-loader.cjs) · [runtime/retry.cjs](runtime/retry.cjs) | 각 컨테이너의 공개 모듈 ID 대응표 생성, 실패한 공개 모듈 조회·캐시 정리. D 복구 시 B부터 로딩을 다시 준비하는 데 사용합니다. |
| [bin/mfe-serve.cjs](bin/mfe-serve.cjs) | 빌드 결과 미리보기. Remote는 파일을 제공하고 Shell은 등록부·다른 배포물을 통합 서버로 전달합니다. |

이 프로젝트는 npm 도구 패키지로 `bin/`, `lib/`, `browser/`, `runtime/`를 배포합니다. 서비스용 MF 설정·`src/`·`dist/` 구조를 사용하지 않습니다. 소비 프로젝트의 설정은 [폴더·설정 안내](../../docs/mfe-project-handbook.html#files)를 참고합니다.

---

Each service installs this package in its own project. It does not require a workspace, symlinks, or another application's source.

Required project inputs:

- `package.json` with a semantic version and the service's own dependencies.
- `package-lock.json` generated by that project's npm install.
- `mf.config.cjs` with the configuration below.
- `mf.dependencies.json`, an alias-to-release-metadata object (`{}` when there are no remotes).
- `src/`, containing every source file, exposed module, and shell HTML entry.

```js
// mf.config.cjs
module.exports = {
  service: 'b',
  kind: 'remote',
  exposes: { './Widget': './src/Widget.jsx' },
  port: 4203,
};
```

A shell uses `kind: 'shell'`, `entry: './src/index.js'`, and `html: './src/index.html'`. Put `__SHELL_SCRIPT__` in its HTML script URL. All service identifiers must start with a letter and use letters, digits, underscores, or hyphens.

Entries of `mf.dependencies.json` can be exact artifact `release.json` objects or runtime requirements. Exact descriptors include `id`, `name`, `service`, `version`, `entry`, and `dependencies`. Neither mode fetches remote code during build. Source code can continue to import `b/Widget`.

The common platform SDK instead declares its compatible version range:

```json
{
  "platform": { "mode": "runtime", "service": "platform", "requires": ">=1.0.0 <2.0.0" }
}
```

The platform remote calls `globalThis.__MFE_RUNTIME__.getContainer('platform')`. Before importing SDK consumers, the shell must fetch and freeze one approved composition and install this runtime resolver. This project uses one SDK container and one shared React instance per page. A new compatible SDK selection therefore needs no consumer rebuild.

Business requirements use the same input shape, for example `"b": { "mode": "runtime", "service": "b", "requires": ">=1.4.0 <2.0.0" }`. The build generates a promise remote calling `getDependencyContainer(consumerArtifactId, 'b')`. The composition's `runtimeBindings[consumerArtifactId].b` selects an exact published B. A and C can choose different B artifacts without rebuilding. Each consumer artifact has one binding per alias per document; two mounts of the same consumer use the same binding. Existing pages retain their snapshot. The store validates the complete graph, supported ranges, service identities and cycles before activation. This checks metadata, not semantic API compatibility.

Run `mfe-build` from the service directory. It produces only that project's `dist/` and `dist/release.json`. Release `dependencies` contains exact pins; `runtimeRequirements` records the SDK range and installed React/React DOM versions; `runtimeDependencies` records business aliases with service and supported range. Selected runtime artifact IDs are not build inputs. The artifact ID hashes all files under `src`, package and lock files, both MF configuration files, and this tool's version. IDs are independent of the project's absolute location. Global container names replace any non-identifier characters in IDs with underscores.

Output uses `publicPath: 'auto'`, a unique Webpack runtime name, and artifact-prefixed CSS Modules. Non-module CSS is allowed only inside a shell's `src`. JavaScript imports can resolve only to the project's `src` or its own `node_modules`; outside and symlinked source is rejected. React is not a dependency of this tool. When the project declares React or React DOM, its installed versions are shared as exact, strict singletons.

Run `mfe-serve` after building. `PORT` overrides `config.port` (default `4200`); `HOST` defaults to `127.0.0.1`. `/artifacts/<current-id>/...` serves this project's files. `/` serves shell HTML or remote release metadata, and `/release.json` serves metadata. A shell proxies other artifact URLs, `/compositions/...`, and `/registry.json` or `/registry/...` to `MF_REMOTE_ORIGIN` (default `http://127.0.0.1:4173`). A proxy back to the same local server is rejected. This is a local preview server, with caching disabled.

## 서비스 단독 개발 (`mfe-dev`, 1.3.0부터)

서비스 프로젝트에서 `npm run dev`를 실행합니다. 서비스의 `mf.dev.json`과 플랫폼이 준비한 `dev/manifest.json`, `dev/remotes/`가 필요합니다. 개발 Host 자체는 도구의 `browser/`에서 빌드하며, SDK 구현은 포함하지 않습니다. `platform/sdk`를 MF로 불러와 `PlatformProvider`, `DevLayout`, `PageContainer`를 사용합니다. SDK는 `>=1.2.0 <2.0.0`, React/ReactDOM은 서비스와 정확히 같은 버전이어야 합니다.

- `bin/mfe-dev.cjs`: 개발 서버, 소스 감시, 직렬 재빌드, 성공 후 자동 새로고침, 오류 표시. `PORT`로 포트를 바꿀 수 있습니다. 0은 테스트용 임의 포트입니다.
- `lib/build.cjs`: 일반 빌드와 개발 빌드가 공유하는 컴파일러. `bin/mfe-build.cjs`는 이 함수를 호출하는 CLI입니다.
- `lib/dev-manifest.cjs`: 키트 파일 해시, 실제 release 메타데이터, SDK/React/의존 범위·누락·순환을 확인합니다.
- `browser/index.js`, `runtime.js`, `bootstrap.jsx`: 고정 조합 설치, MF 로딩, 개발 화면·복제·테마·다시 마운트 도구. 런타임 로더는 Shell과 같은 계약을 구현하며 SDK 소스는 들어 있지 않습니다.

개발 결과는 `.mfe-dev/`에 보관하고 `dist/`는 변경하지 않습니다. 소스 변경 시 상태를 보존하는 HMR 대신 전체 문서를 새로고침합니다. 잘못된 소스는 마지막 성공 화면 위에 오류를 표시하며, 다음 정상 저장 때 복구합니다. 실행 중 이전 빌드 파일은 보존합니다. `src/`, MF 설정, `mf.dev.json`, `dev/manifest.json` 변경을 감시합니다. npm 의존성·잠금 파일 변경 후에는 재시작합니다.

`mf.dev.json`의 `pageContainer: false`는 서비스가 자체적으로 `PageContainer`를 사용하는 경우입니다. `module`은 현재 서비스가 공개한 React default export 이름이고, `title`, `description`, `user: {id,name}`, `theme`은 개발 설정입니다. 서비스를 직접 연 상태의 테마 변경은 DevLayout에 적용되며 서비스 내부의 테마 대응 스타일은 해당 서비스가 작성합니다.

발행된 MF 파일을 담은 개발 키트는 npm SDK 패키지가 아닙니다. 같은 프로젝트에서 HTTP로 제공하더라도 SDK·서비스는 별도 container로 로드됩니다. 키트를 서비스 저장소에 포함하거나 별도 다운로드 과정으로 공급해야 합니다. 현재 키트 생성 도구는 통합 프로젝트의 `npm run prepare:dev -- SDK_ID`이며, 중앙 API 다운로드·업무 API mock은 아직 없습니다. UI 서비스 A/C/B에 적용하고 데이터 모듈 D는 B를 통해 확인합니다.

## 영역별 수동 재시도 지원 (1.5.0)

1.4.0에서 추가한 업무용 `mode: runtime` remote 프록시를 유지합니다. init은 같은 share scope를 보관하고 get에서 소비자 바인딩에 맞는 대상을 조회·초기화합니다. SDK의 중앙 선택·singleton 정책은 유지합니다.

1.5.0은 `retryProtocol: "failed-modules-v2"`를 기록합니다. 예약 공개 모듈 `./__mfe_retry__`은 다음 API를 제공합니다.

- `protocol`: `failed-modules-v2`.
- `getFailedExposes()`: `require.cache`에 평가 실패가 기록된 공개 모듈 이름만 반환합니다. 빌드 도구가 exposes 설정을 `require.resolveWeak` 기반 ID 대응표로 컴파일하므로 서비스 코드의 개별 모듈 이름을 Host에 하드코딩하지 않습니다. 대응표 참조는 업무 모듈을 실행하거나 동기 import하지 않습니다.
- `resetFailedModules()`: `strictModuleErrorHandling: true`로 기록한 실패 캐시만 삭제하고 ID 목록을 반환합니다. 성공한 모듈은 유지합니다.

[SDK remote-loader.js](../platform-sdk/src/remote-loader.js)는 하위부터 `getFailedExposes()` → 실패 캐시 삭제 → 해당 공개 이름으로 `container.get()`을 수행합니다. 이 준비 단계에서는 반환된 factory를 실행하지 않습니다. 부모 C가 이미 B의 factory를 받아 둔 경우에도 B의 D 파일 로딩을 다시 진행할 수 있습니다. 마지막에 C를 실행하고 해당 영역만 마운트합니다. v1의 캐시 삭제 프로토콜도 인식하지만 구형 빌드가 자동으로 D 복구를 지원하는 것은 아닙니다.

D 2.0의 진입 파일·실행 청크가 실패하면 B 2.1과 C에 평가 실패가 남습니다. 캐시만 지우는 v1에서는 D 재요청 없이 같은 오류가 반복되는 상황을 실제 재현했고, v2의 공개 모듈 로딩 재준비로 해결했습니다. 정상 A·B 1.4·D 1.0·SDK의 상태와 캐시는 유지합니다.

버튼·오류 경계·실패 복구 순서는 SDK 1.3.0의 RemoteRegion과 remote-loader.js에 있습니다. 서비스 팀은 SDK 컴포넌트를 import하고 이 도구가 생성한 복구 API는 SDK가 사용합니다. 중첩 준비 도구가 A/C/B 2.1의 독립 복사본에 도구 1.5.0을 설치·빌드합니다. B 업무 소스는 유지하며 새 배포 ID로 발행합니다. 새 SDK 1.3.0을 선택하며 B 1.4·D·Shell은 기존 파일입니다. A는 새 SDK 컴포넌트를 사용하도록 한 번 전환합니다. 최초 도입 뒤 같은 파일의 장애 복구에는 재빌드나 버전 변경이 없습니다.

`cd ../../integration` 후 `npm run test:nested`로 31개 검사를 실행합니다. C/B/D의 실제 HTTP 실패·복구, 반복·동시 재시도, 대기 중 제거, 직접 B의 DOM·상태 보존을 검증합니다. Webpack 5.112.2에 맞춘 구현이므로 컴파일러 변경 시 재검증합니다. 고정 URL 외부 모듈의 실패 캐시, 공통 SDK 실패, 임의 평가 부작용·업무 API 오류까지 자동 복구하는 계약은 아닙니다. [HTML 설명](../../docs/mfe-runtime-operations.html#nested-d-retry).

## 등록형 메뉴의 배포 정보 (1.6.0)

`release.json`에 공개 모듈 목록 `exposedModules`를 기록한다. 관리 서버는 메뉴 등록 시 선택한 모듈 이름이 목록에 포함되는지 검사한다. 이 목록이 없는 옛 배포물은 계속 사용할 수 있지만 모듈 존재 확인은 실제 로딩 시점에 이뤄진다. default export의 React 컴포넌트 여부나 업무 동작까지 보증하지는 않는다.

Shell의 mf.config.cjs에 `navigationProtocol: 'registered-menu-v1'`을 선언하면 release에 기록한다. Shell 종류에서만 허용하며 관리 서버/UI가 등록형 메뉴 지원 여부를 판단한다. 이것은 프로젝트 전용 프로토콜이다. 메뉴 자체와 메뉴별 배포 ID는 빌드 결과에 넣지 않고 조합 스냅샷에 저장한다. 서비스 팀은 메뉴를 늘릴 때 Shell을 빌드할 필요가 없다.

실제 메뉴/페이지 UI와 런타임 해석은 Shell·관리 앱, 검증과 저장은 integration 서버가 제공한다. 빌드 도구만 올려서는 구형 Shell에 메뉴 기능이 생기지 않는다. [처음 전환과 새 서비스 등록](../../docs/mfe-project-handbook.html#registered-services).

## 공개 위젯 카탈로그 (1.7.0)

업무 Remote의 mf.config.cjs에 widgets: [{id, title, exposedModule, contract: 'platform-widget-v1'}]을 선언한다. 빌드/발행 검사는 widgets ID 중복, 실제 exposes 포함 여부, 계약 이름을 검사한다. 일반 exposes 전체를 위젯으로 간주하지 않는다. 서비스는 React default export와 공통 instanceId를 지원하며 사용자 값은 MF SDK Context에서 받는다. 실제 UI/API 동작은 통합 검증한다.

Shell의 dashboardProtocol: 'registered-dashboard-v1'은 대시보드 배치 지원을 나타낸다. 서비스별 배치와 버전은 조합에 저장하고 Shell 번들에 넣지 않는다. lib/widgets.cjs 검증을 로컬 등록 서버도 재사용한다. [대시보드 사용법](../../docs/mfe-project-handbook.html#dashboard-widgets).
