01

저장 위치가 바뀌어도 유지할 원칙

현재의 파일 기반 등록부를 DB로 옮기는 것은 운영 환경에 적합한 다음 단계입니다. 버전 검색·팀별 권한·동시 변경·사용 현황·감사 이력이 늘어날수록 장점이 있습니다. 단, MF 버전 충돌 자체를 DB가 해결하는 것은 아닙니다. SDK 공유·격리·호환성 검사·고정된 실행 조합은 그대로 필요합니다.

이 문서는 설계 제안입니다. 현재 프로젝트의 운영 저장소는 여전히 로컬 JSON·파일이며, DB 서버·마이그레이션·S3 연동은 구현하지 않았습니다.

담당제공하는 것직접 다루지 않는 것
서비스 팀공개 모듈, 지원 SDK·업무 의존 범위, 빌드 산출물, 호환성 검증 결과운영 DB에 직접 INSERT/UPDATE하지 않음. 자신의 권한으로 발행 API를 호출.
플랫폼 등록부 API팀 권한, 매니페스트 검증, 조합 생성·선택, 정책·참조 검사서비스의 업무 API 동작까지 자동으로 호환된다고 판단하지 않음.
백그라운드 작업자파일 검증·삭제, 스냅샷 발행, 공지 전송, 실패 재시도작업 중 DB 조건을 우회하거나 임의로 최신 버전을 선택하지 않음.
Shell·서비스 런타임고정된 조합의 SDK·B·D를 MF로 로드하고 탭 사용 기한 갱신DB 연결 정보나 운영 변경 권한을 브라우저에 넣지 않음.

변경되지 않는 조건: 한 문서의 SDK는 하나, 같은 소비자 배포 ID·별칭에는 대상 하나, 배포 파일은 불변, 조합은 문서 수명 동안 고정, 등록 해제와 실제 삭제는 별도입니다.

처음 DB 구현은 하나의 운영 API와 하나의 PostgreSQL 쓰기 기준으로 시작하는 안입니다. 관리 서버가 여러 대여도 같은 DB 잠금·revision 규칙을 따라야 합니다. 지역별 동시 쓰기나 분산된 등록부는 이 설계의 초기 범위에 포함하지 않습니다.

(composition_id, placement_id)와 (composition_id, position)은 각각 유일하게 하고 span은 1 또는 2로 제한합니다. 같은 위젯의 복제 배치는 허용합니다. 새 조합·배치·의존성을 하나의 트랜잭션으로 기록한 뒤 활성 포인터를 변경합니다. 이전 배치와 공개 목록은 탭·롤백이 참조하는 동안 보존합니다. DB 구현은 여전히 설계안입니다.

핵심 테이블 DDL — 구현할 때의 출발점

아래 SQL은 설계 예시이며 이번 작업에서 DB에 실행하지 않았습니다. 표시한 PK/FK만으로 전체 운영 규칙이 완성되지는 않습니다.

PostgreSQL 관계·제약의 골격
-- 관계와 제약을 설명하는 핵심 DDL 예시입니다.
-- 운영 권한, 불변 필드 트리거, 수명주기·탭·작업 테이블은 아래 설계를 별도 구현해야 합니다.
CREATE TABLE services (
  service_id text PRIMARY KEY,
  owner_team text NOT NULL
);
CREATE TABLE releases (
  artifact_id text PRIMARY KEY,
  service_id text NOT NULL REFERENCES services(service_id),
  semver text NOT NULL,
  metadata_schema integer NOT NULL CHECK (metadata_schema > 0),
  manifest jsonb NOT NULL CHECK (jsonb_typeof(manifest) = 'object'),
  manifest_sha256 text NOT NULL CHECK (manifest_sha256 ~ '^[0-9a-f]{64}$'),
  storage_prefix text NOT NULL UNIQUE,
  created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE TABLE declared_dependencies (
  consumer_artifact_id text NOT NULL REFERENCES releases(artifact_id),
  alias text NOT NULL,
  mode text NOT NULL CHECK (mode IN ('runtime', 'shared', 'fixed')),
  required_service text NOT NULL REFERENCES services(service_id),
  supported_range text,
  fixed_target_id text REFERENCES releases(artifact_id),
  PRIMARY KEY (consumer_artifact_id, alias),
  CHECK (
    (mode = 'fixed' AND fixed_target_id IS NOT NULL AND supported_range IS NULL)
    OR
    (mode IN ('runtime', 'shared') AND fixed_target_id IS NULL AND supported_range IS NOT NULL)
  )
);
CREATE TABLE compositions (
  composition_id text PRIMARY KEY,
  schema_version integer NOT NULL CHECK (schema_version > 0),
  snapshot jsonb NOT NULL CHECK (jsonb_typeof(snapshot) = 'object'),
  snapshot_sha256 text NOT NULL CHECK (snapshot_sha256 ~ '^[0-9a-f]{64}$'),
  object_key text NOT NULL UNIQUE,
  publication_state text NOT NULL CHECK (publication_state IN ('pending', 'ready', 'failed')),
  created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE TABLE composition_members (
  composition_id text NOT NULL REFERENCES compositions(composition_id),
  artifact_id text NOT NULL REFERENCES releases(artifact_id),
  PRIMARY KEY (composition_id, artifact_id)
);
CREATE TABLE composition_roots (
  composition_id text NOT NULL,
  role text NOT NULL,
  artifact_id text NOT NULL,
  PRIMARY KEY (composition_id, role),
  FOREIGN KEY (composition_id, artifact_id)
    REFERENCES composition_members(composition_id, artifact_id)
);
CREATE TABLE composition_bindings (
  composition_id text NOT NULL,
  consumer_artifact_id text NOT NULL,
  alias text NOT NULL,
  target_artifact_id text NOT NULL,
  PRIMARY KEY (composition_id, consumer_artifact_id, alias),
  FOREIGN KEY (consumer_artifact_id, alias)
    REFERENCES declared_dependencies(consumer_artifact_id, alias),
  FOREIGN KEY (composition_id, consumer_artifact_id)
    REFERENCES composition_members(composition_id, artifact_id),
  FOREIGN KEY (composition_id, target_artifact_id)
    REFERENCES composition_members(composition_id, artifact_id)
);
CREATE TABLE environment_heads (
  environment_id text PRIMARY KEY,
  composition_id text NOT NULL REFERENCES compositions(composition_id),
  revision bigint NOT NULL CHECK (revision >= 0),
  updated_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX members_by_artifact ON composition_members(artifact_id, composition_id);
CREATE INDEX bindings_by_target ON composition_bindings(target_artifact_id, composition_id);
CREATE INDEX fixed_consumers_by_target ON declared_dependencies(fixed_target_id)
  WHERE fixed_target_id IS NOT NULL;
DB 제약으로 보호운영 API에서 검사추가 운영 장치
PK·UNIQUE: 같은 조합·소비자·별칭의 중복 대상 방지SemVer 파싱·범위, alias의 mode와 service, 전체 그래프의 누락·순환기존 소비자 산출물을 사용하는 조합 테스트.
FK: 존재하는 배포물·선언·조합 구성원 참조공통 SDK 하나, SDK/React 호환, SDK 루트와 실제 참조 일치알 수 없는 매니페스트 스키마는 수용하지 않는 버전 협상.
NOT NULL·CHECK: 상태 값과 같은 행의 기본 형식지원 종료의 정확한 경로 예외, 모든 환경·탭·롤백·고정 참조불변 필드 UPDATE 금지 권한/트리거, 메타데이터 삭제 대신 tombstone.

CHECK에 다른 테이블 조회나 “현재 시각을 지나면 자동 실패” 같은 규칙을 넣어 해결하려 하지 않습니다. FK·UNIQUE·CHECK의 역할과 한계는 PostgreSQL 제약 문서를 기준으로 구현합니다. 운영 정책은 작업 직전 잠금 안에서 다시 계산합니다.

주요 추가 인덱스는 release_files(artifact_id), tab_leases(composition_id, expires_at), tab_artifact_refs(artifact_id, released_at), outbox_jobs(status, next_attempt_at)입니다. 실제 조회 계획과 데이터량으로 조정합니다. 참조 수 캐시는 화면 표시용이며, 삭제 허용을 캐시 값 0만 보고 결정하지 않습니다.

04

서비스 버전을 등록하는 순서

  1. 서비스 CI가 자기 프로젝트만 빌드해 배포 ID·release 메타데이터·노출 모듈·파일별 해시를 준비합니다. 플랫폼은 토큰의 팀과 service 소유권을 확인합니다.
  2. 등록 API가 idempotency key와 요청 해시를 기록하고 pending 발행 레코드를 만듭니다. 같은 키·같은 요청은 기존 결과를 반환하고, 같은 키·다른 내용은 409로 거절합니다.
  3. 승인된 저장소 prefix에 파일을 업로드합니다. 임시 업로드 권한은 그 prefix에만 적용하며 임의 URL을 운영 entry로 등록하지 못하게 합니다.
  4. 검증 작업자가 entry·chunk·파일 목록·해시, 허용된 경로/출처, 매니페스트 스키마를 검사합니다. S3 업로드·네트워크 검증 중 DB 행 잠금을 길게 잡지 않습니다.
  5. DB 트랜잭션에서 발행 요청과 동일한 내용을 확인한 뒤 release_files·declared_dependencies를 기록하고 ready로 전환합니다. 파일이 준비되기 전에는 조합 후보에 노출하지 않습니다.
  6. 서비스 팀 또는 운영자가 조합 미리 검사로 새 버전을 선택합니다. 발행 자체는 environment_heads를 변경하지 않습니다.
상황처리
같은 artifact_id와 같은 내용 재발행동일 요청으로 처리. 메타데이터·파일을 덮어쓰지 않음.
같은 artifact_id인데 해시가 다름409 ARTIFACT_CONTENT_CONFLICT. 새 ID가 필요한 배포로 거절.
동일 semver의 새 artifact_id별도 배포로 등록 가능. 어느 빌드를 채택할지 명시적으로 선택. semver만으로 삭제·롤백하지 않음.
고정 의존 대상이 아직 없음검증 대기 또는 거절. 대상 ready 확인 전 소비자 ready 금지. runtime 범위 선언은 대상 선택을 조합 단계까지 미룰 수 있음.
이미 등록 해제·삭제한 ID같은 ID를 재발행해 복구하지 않음. 이관 작업을 포함해 tombstone 보존.
CI 테스트가 실패함파일 발행 여부와 별개로 운영 조합 승인 조건 미충족. 검사 기록에 정확한 공급자·소비자 ID를 남김.

ready는 파일과 메타데이터가 준비됐다는 뜻입니다. 모든 소비자와의 업무 호환성이 증명됐다는 뜻은 아닙니다. 호환성 증거는 조합 해시 + 테스트 버전 + 결과로 연결하고, 운영 적용 기준으로 사용할 범위를 별도로 정합니다.

05

조합 선택·동시 변경·롤백

조합 생성은 준비 단계와 적용 단계로 나눕니다. 무거운 파일 작업은 트랜잭션 밖에서 끝내고, 환경 head를 바꾸는 짧은 트랜잭션에서 현재 조건을 다시 검사합니다.

  1. 미리 검사: 현재 head·정책 버전과 선택안을 읽어 전체 그래프를 해결합니다. candidate 내용 해시, 검사 기준 revision, 정책 revision, 토큰 만료 시각을 반환합니다. preview는 활성 head를 쓰지 않습니다.
  2. 준비: 정확한 Shell HTML과 JSON 스냅샷을 불변 키로 저장하고 발행을 확인합니다. JSON·관계 테이블의 구성원을 일치시킵니다. 아직 새 사용자는 이 조합을 선택하지 않습니다.
  3. 적용 트랜잭션: 현재 head의 revision을 잠금 아래 확인합니다. candidate의 모든 배포물·경로와 정책·파일/접근 상태를 다시 검사합니다. 미리 검사 토큰은 검사 생략 권한이 아닙니다.
  4. 커밋: head를 새 compositionId로 변경하고 revision을 1 증가시킵니다. audit와 후속 outbox 작업을 같은 트랜잭션에 기록합니다.
  5. 응답: 새 revision·compositionId를 반환합니다. 응답이 유실되어 재시도하더라도 같은 idempotency key는 원래 결과를 돌려줍니다.

실행 가능한 SQL 함수가 아닌 처리 순서
BEGIN
  lock environment head;
  lock composition-retirement rows;
  lock referenced release policy rows in artifact_id order;
  assert expectedRevision matches;
  assert candidate hash and preview token match;
  assert snapshot publication_state = ready;

경쟁 상황결과
관리자 두 명이 revision 42에서 편집먼저 적용한 요청이 43을 만듦. 뒤 요청은 409 HEAD_CHANGED로 거절하며 자동 덮어쓰기 없음.

미리 검사 이후 지원 종료·등록 해제적용 직전 정책 검사가 거절. 준비한 스냅샷은 미활성 상태로 남음.
임시 네트워크 오류로 동일 적용 요청 재전송동일 idempotency key/요청 해시이면 원래 결과 반환. 새 이벤트를 이중 기록하지 않음.
이전 조합으로 롤백이전의 전체 SDK·B·D 조합을 후보로 가져와 같은 검사/적용 경로 사용. revision은 증가하며 종료 버전 재도입도 검사.

지원 종료 예외는 “그 버전이 어딘가에서 쓰이고 있음”이 아니라 그 환경의 직전 조합과 정확히 같은 사용 경로입니다. D가 같더라도 A 또는 B 배포 ID가 바뀌어 새 경로가 되면 신규 사용으로 판단합니다.

PostgreSQL의 행 잠금·격리 수준을 바탕으로 구현하되, 아래 잠금 규칙을 모든 쓰기 경로에 공통 적용해야 합니다. 잠금 동작 · 격리 수준

브라우저 부팅·캐시·구형 스키마

/registry.json 같은 진입 API는 DB head를 한 번 읽고 그 compositionId에 해당하는 전체 스냅샷을 돌려줍니다. HTML에서 선택한 Shell과 이후 가져올 조합 JSON도 같은 ID를 사용해야 합니다. 각각의 최신 값을 따로 읽으면 전환 순간에 서로 다른 조합이 섞일 수 있습니다.

  1. 새 진입: 플랫폼이 현재 head를 읽어 선택한 Shell HTML과 고정된 manifest URL을 연결합니다.
  2. Shell 시작: 탭 사용 기한을 발급받고 조합을 고정한 뒤 SDK·서비스를 불러옵니다.
  3. 지연 로딩: C를 나중에 열더라도 같은 조합의 C→B→D를 사용합니다. 개별 버전을 DB에서 다시 선택하지 않습니다.
  4. 조합 변경: 새 진입에만 적용합니다. 기존 탭은 사용 기한을 갱신하며 처음 조합을 유지합니다.

불변 JSON과 배포 파일은 CDN 캐시 대상으로 삼을 수 있지만, 현재 head·사용 기한·정책 API는 별도의 캐시 규칙이 필요합니다. DB/API 장애 때 신규 탭에 오래된 조합을 무조건 제공하는 fallback은 종료·삭제 정책을 우회할 수 있으므로, 유효한 사용 기한 발급과 허용 상태를 확인하지 못하면 시작을 보류합니다. 기존 탭은 기존 기한 내에서만 계속 동작합니다.

삭제 검사와 heartbeat가 교차할 때의 잠금 규칙

초기 구현은 정확성을 우선해 모든 관련 쓰기 연산에 아래 순서를 공통 적용하는 안입니다.

  • 잠금 순서: 환경 head(필요한 경우, 환경 ID순) → 조합 보관 정책(조합 ID순) → 배포 정책(배포 ID순) → 탭/참조 행. 잠근 뒤 새롭게 발견한 선행 범위가 있으면 그 트랜잭션을 되돌리고 다시 시작합니다.
  • 활성화·고정 참조 발행·새 lease·갱신·탭 해제·구형 탭 지연 보고·삭제가 해당 배포 정책 행의 공통 잠금 경로에 참여해야 합니다. 한 경로라도 우회하면 “참조 0 검사 뒤 새 참조 추가” 경쟁이 생깁니다.
  • 삭제 작업은 배포 정책 행을 잠근 후 읽기 기준 시점의 최신 보호 참조를 다시 조회하고 deleting으로 전환합니다. DB FK만으로는 deleting 대상에 새 참조가 생기는 것을 막지 못합니다.
  • 이 단순 배타 잠금 방식은 공유 SDK의 heartbeat 경합을 키울 수 있습니다. 실제 부하에서 검증한 뒤 compatible read/admission 잠금과 exclusive retirement 잠금을 구분하거나 갱신 처리를 최적화합니다. 고성능 처리가 이미 검증됐다는 뜻은 아닙니다.
  • 잠금 시간 제한·교착·직렬화 실패에는 트랜잭션 전체를 제한적으로 재시도합니다. 재시도 사이 S3 업로드나 공지를 다시 수행하지 않도록 outbox와 멱등 키를 사용합니다.

SELECT h.environment_id, h.composition_id

JOIN composition_members m ON m.composition_id = h.composition_id

사용 경로는 snapshot의 고정 의존, runtimeBindings, 공통 SDK 암묵 연결을 모두 펼쳐 A→B→D 형태로 보여줍니다. composition_members의 단순 개수만으로 경로 예외를 판정하지 않습니다.

새 lease는 sessionId에 compositionId를 고정하며, 갱신은 증가하는 sequence와 서버 시각을 검사합니다. 만료·종료·정리된 sessionId는 늦은 보고로 부활시키지 않습니다. 구형 탭의 버전별 해제는 tab_artifact_refs의 tombstone을 유지하고 그 탭의 다른 artifact 참조는 계속 갱신합니다.

개발 키트·환경별 선택

현재 개발용 Host는 서비스 폴더의 dev/manifest.json과 dev/remotes/를 읽습니다. 이는 플랫폼이 발행한 SDK·업무 모듈의 개발용 고정 스냅샷이며 npm SDK 소스가 아닙니다. 브라우저는 실제 remoteEntry.js를 HTTP로 요청하고 MF container를 초기화합니다.

DB 도입 후에는 플랫폼의 “개발 키트 생성” API가 개발 환경 head 또는 지정한 조합을 읽고, 같은 형식의 매니페스트·파일 목록·체크섬을 내보내면 됩니다. 서비스 개발자는 키트를 받아 자기 프로젝트에서만 실행합니다. 현재 이 API와 원격 다운로드 명령은 구현하지 않았으며, integration/tools/prepare-dev.cjs가 로컬 발행 저장소에서 같은 역할을 합니다.

개발 키트는 호환성 검사와 재현을 위해 버전을 고정합니다. 항상 latest를 따라가게 하지 않습니다. 의도적으로 새 키트를 받아 SDK·의존 모듈 변경을 확인합니다. 오프라인 복사본은 제품 서버의 탭 관측·원격 접근 종료 대상에 포함되지 않으므로, 개발용 재현 자료의 보존·폐기 정책은 별도로 관리합니다.

요청플랫폼 처리서비스 팀의 결과
개발 환경의 현재 조합에서 A만 개발dev head를 한 번 읽어 A를 로컬 대체할 위치로 정함. SDK와 B/D 전이 의존성은 고정.A의 소스 + dev/manifest.json + 필요한 remote 파일만 받음.
버그 재현용 과거 조합 지정지정 composition의 파일 보존·접근 권한을 확인. 재현 전용 허용 정책을 명시.항상 같은 SDK/B/D로 재현. 운영의 신규 선택 규칙을 자동으로 우회하지 않음.
새 SDK를 시험하고 싶음dev 후보 조합을 별도로 검사·발행해 키트를 생성. production head는 변경하지 않음.기존 서비스 소스 그대로 SDK 호환성 테스트.
키트 다운로드 중 실패불변 키트 ID와 파일별 해시로 재개/재시도. 모든 파일 검증 뒤 로컬 manifest를 교체.절반만 내려받은 상태가 현재 개발 키트가 되지 않음.

개발 키트 manifest에는 제품 운영 API의 자격 증명을 넣지 않습니다. mock 사용자 정보와 실제 로그인 토큰은 구별하며, 오프라인 키트의 사용량은 제품 탭의 보호 lease로 계산하지 않습니다.

  2. 적재: 불변 release/composition을 먼저 이관하고 파일 해시·건수·의존 그래프를 대조합니다. 실패한 발행·삭제 중간 상태도 정상으로 둔갑시키지 않습니다.
  3. 그림자 조회: 쓰기는 기존 저장소 한 곳에만 유지하고 DB 조회 결과와 비교합니다. 비교용 복제 경로를 운영 판단의 기준으로 사용하지 않습니다.
  4. 최종 동기화: 관리 변경과 사용 기한 기록의 쓰기 경로를 통제한 짧은 전환 구간에서 최종 상태를 이관합니다. 기존 탭의 갱신 경로·현재 기한을 먼저 보호해야 하며, 허용 시간을 넘으면 안전하게 잠기고 재진입하도록 처리합니다.
  5. 단일 쓰기 전환: 운영 API·lease·job worker를 함께 DB 기준으로 전환합니다. 일부 API만 JSON에 쓰는 상태를 남기지 않습니다. origin·CDN 제공 경로도 이 상태를 참조하게 합니다.
  6. 관찰: 활성 조합·기한 갱신·삭제 차단 결과를 대조합니다. 기존 정적 파일과 스냅샷은 검증·보존 기간 동안 남깁니다.
이관을 되돌릴 때의 조건

DB에 새 쓰기가 발생하기 전에는 이전 읽기 경로로 돌아갈 수 있습니다. DB에서 새로운 활성화·lease·정리 기록이 발생한 뒤에는 오래된 JSON 포인터로 단순 복귀하면 안 됩니다.

  • 쓰기 중지 또는 통제 후 DB의 최신 head·lease·정리 tombstone·정책을 파일 형식으로 다시 내보내 검증해야 합니다.
  • 역변환이 준비되지 않았다면 DB 운영 상태를 유지한 채 API 코드만 이전 호환 버전으로 되돌리는 복구를 우선합니다.
  • 실제 삭제된 파일이나 무효화된 사용 기한은 DB 롤백만으로 되살리지 않습니다. 파일 복구와 사용자 재진입은 별도 절차입니다.

새 최상위 서비스를 DB에 등록하는 것과 Shell에 메뉴·라우트를 추가하는 것은 별개입니다. 현재 A/C를 아는 Shell을 범용 카탈로그로 바꾸는 작업까지 DB 이관에 포함된 것으로 간주하지 않습니다.
