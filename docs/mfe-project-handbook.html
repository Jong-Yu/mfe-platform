서비스 개발과 프로젝트 안내

내 서비스 하나를 실행하고 수정한 뒤 발행하는 방법. 프로젝트별 역할과 파일 설명은 필요할 때 찾아봅니다.

START

처음 개발할 때는 네 곳만 보세요

Shell·SDK·MF가 낯설다면 입문 설명서부터 읽으세요. 이 문서는 실제로 파일을 열고 수정하는 사람을 위한 안내서입니다.

  1. 자기 서비스 실행: 준비된 키트로 B 프로젝트를 띄웁니다.
  2. 폴더와 파일: src, MF 설정, 개발 키트, dist를 구분합니다.
  3. SDK 사용 코드: 공통 Provider와 위젯 경계가 어디에 있는지 봅니다.
  4. 빌드·발행·선택: 수정한 화면을 제품 조합에 반영합니다.

새 서비스를 만드는 경우에는 E 서비스 생성·발행 실습 → 관리 화면에서 메뉴 연결를 먼저 진행하세요. 아래의 네 단계 안내는 이미 프로젝트를 받은 경우의 개발 흐름입니다.

10개 프로젝트 전체 목록은 필요한 프로젝트만 찾아 읽으세요. 플랫폼 담당자는 플랫폼이 제공할 것과 새 서비스 연결도 확인합니다.

01

02

서비스 폴더 하나로 개발하기

A·C·B 1.x·B 2.x의 폴더만 있으면 개발 화면을 띄울 수 있습니다. 각 서비스에 발행된 SDK와 필요한 의존성의 개발 키트를 포함했습니다. SDK·B·D 서버나 제품 Shell을 따로 켜지 않아도 됩니다.

예: 프로젝트 루트에서 B 1.x 개발
cd projects/service-b-v1
npm ci
npm run dev

기본 주소는 A 4201, C 4202, B 1.x 4203, B 2.x 4204입니다. 기존 npm start와 같은 포트를 사용하므로 동시에 켜려면 PORT=4300 npm run dev로 바꿉니다. D는 UI가 없는 함수 모듈이므로 B에서 확인합니다.

서비스 프로젝트 · npm run dev자기 소스만 빌드하고 .mfe-dev/에 저장
↓ HTTP + 실제 Module Federation
발행된 SDK → PlatformProvider · DevLayout · PageContainer
↓
현재 서비스 → 고정된 B / D MF 모듈

개발 Host는 npm 빌드 도구에 포함된 얇은 실행기입니다. SDK 구현은 Host 번들에 넣지 않고 platform/sdk를 통해 로드합니다. 로컬 파일을 같은 서버가 제공하더라도 SDK와 서비스는 각각의 remoteEntry.js·container로 실행합니다. 제품용 SDK 배포 방식을 npm으로 바꾼 것이 아닙니다.

파일역할
mf.dev.json개발할 노출 모듈(./Widget), 제목·설명, mock 사용자·테마, PageContainer 자동 적용 여부.
dev/manifest.jsonSDK 배포 ID, 현재 서비스의 localBindings, 하위 모듈의 runtimeBindings, 파일별 SHA-256. 개발 키트의 선택을 고정합니다.
dev/remotes/<배포 ID>/플랫폼이 발행한 SDK/B/D의 실행 파일. 서비스 팀이 수정하거나 다시 빌드하지 않습니다. 다른 팀의 소스 저장소는 필요 없습니다.
.mfe-dev/host/ · builds/생성된 개발 Host와 현재 서비스의 빌드. 실행 중 이전 빌드는 남겨 두며 운영 dist/를 덮어쓰지 않습니다. 서버 종료 후 캐시 정리가 가능합니다.

SDK가 제공하는 화면 경계

개발 Host의 기본 배치
import { PlatformProvider, DevLayout, PageContainer } from 'platform/sdk';

<PlatformProvider user={devUser} theme="light">
  <DevLayout serviceName="OTA" tools={devTools}>
    <PageContainer title="OTA" description="차량 업데이트">
      <Service instanceId="dev-1" />
    </PageContainer>
  </DevLayout>
</PlatformProvider>

PageContainer는 title·description·actions·children·width(standard/wide)를 받습니다. 제목과 콘텐츠 간격, 최대 폭, 모바일 여백을 제공합니다. main을 중복 생성하지 않는 section입니다. 위젯 인스턴스 상태는 기존 WidgetBoundary가 관리합니다.

서비스 페이지가 직접 PageContainer를 import해도 됩니다. 이때 SDK 요구 범위를 >=1.2.0 <2.0.0으로 선언하고, 개발 설정에서 pageContainer: false로 두어 자동 감싸기를 끕니다. 제품 환경도 SDK 1.2.0 이상을 선택해야 해당 API를 사용할 수 있습니다. 개발 키트와 제품의 SDK 선택은 별개입니다.

저장·오류·개발용 값

  • src/나 MF 설정 변경을 감지해 현재 서비스만 재빌드하고 성공하면 전체 문서를 새로고침합니다. 저장하지 않은 입력과 로컬 상태는 초기화됩니다.
  • 빌드 오류가 있으면 마지막 성공 화면을 유지하고 오류를 표시합니다. 다음 정상 저장에서 갱신됩니다.
  • 테마 선택, 인스턴스 복제, 다시 마운트로 Context·상태·구독·팝업 수명주기를 확인합니다. SDK 기본값을 바꾸지 않고 mock user/theme을 전달합니다.
  • React/SDK 불일치, 미선택 의존성, 범위 위반, 순환, 파일 누락·변조는 시작 또는 재빌드 전에 거절합니다. 파일 해시는 무결성 확인이며 매니페스트 발행자 인증을 대신하지 않습니다.
  • npm 의존성·lockfile 변경 후에는 다시 설치하고 dev를 재시작합니다. API mock, 실제 로그인, 제품 탭 사용 기한·삭제 보호의 검증은 이 화면에 포함하지 않습니다.

플랫폼이 새 개발 키트를 공급할 때

플랫폼 담당자 · integration에서 실행
# SDK를 별도로 빌드·발행한 후 실제 배포 ID 사용
npm run prepare:dev -- SDK_ARTIFACT_ID

이 명령은 발행 저장소에서 SDK와 현재 A/C 경로의 B/D 파일을 복사해 각 UI 서비스의 dev 키트를 갱신합니다. 서비스 빌드나 제품 활성 조합을 바꾸지 않습니다. 서비스 팀은 전달받은 자기 폴더에서만 실행합니다. 실제 별도 저장소 운영에서는 플랫폼이 이 키트를 파일 저장소/CI로 공급해야 합니다. 중앙 다운로드 API는 아직 구현하지 않았습니다.

오프라인 키트는 제품 탭 사용 추적과 별개입니다. 제품 버전의 등록 해제·접근 종료가 이미 복사한 개발 파일까지 원격 삭제하지 않습니다. 재현 자료의 보존 정책을 별도로 둡니다.

개발 Host CLI · 개발 매니페스트 검증 · SDK 구현 · Layout 스타일 · 키트 생성

검증 명령: integration의 npm run test:dev. 네 UI 프로젝트를 각각 별도 임시 폴더로 복사해 오프라인 설치하고, 그 프로젝트의 서버 외 모든 HTTP 요청을 차단한 브라우저에서 검사합니다. MF 요청·공통 React·PageContainer·소스 갱신·오류 복구·인스턴스 정리·모바일·제품 출력 분리를 확인합니다. 검증 보고서

서비스 폴더를 읽는 공통 규칙

일반적인 MF Remote 프로젝트
service-b-v1/
├── src/                     # 직접 작성하는 구현
│   ├── Widget.jsx           # 외부로 공개할 모듈
│   └── Widget.module.css    # 모듈 전용 스타일

구분직접 관리하는 것왜 필요한가
서비스 소스src/와 mf.config.cjs의 exposes공개 이름 ./Widget은 소비자의 b/Widget import와 연결됩니다. 내부 파일명은 변경해도 공개 이름을 유지할 수 있습니다.
MF 의존 계약mf.dependencies.json어떤 서비스가 필요한지와 지원 버전 범위를 빌드 시 선언합니다. 실제로 선택한 배포 ID를 넣는 곳은 중앙 조합입니다.
설치·버전package.json · package-lock.json서비스 릴리스 버전과 React·빌드 도구 등의 설치 버전을 고정합니다. 루트 설치에 기대지 않습니다.
공통 빌드 도구vendor/mfe-platform-build-tools-<버전>.tgz서비스를 별도 폴더로 옮겨도 도구를 설치할 수 있습니다. 런타임 SDK를 담은 npm 패키지가 아닙니다.
생성 결과node_modules/ · dist/npm ci/build로 만듭니다. 새 build는 해당 프로젝트의 dist를 교체하지만 발행된 artifact-store 파일은 그대로 남습니다.

release.json의 id는 버전 문자열과 빌드 입력의 해시로 구분됩니다. 소스·package/lock·MF 설정·빌드 도구 버전이 입력이고, 선택된 런타임 B/D/SDK ID와 README는 입력이 아닙니다. 같은 1.4.0이라도 소스가 다르면 별도 배포 ID이며, 운영에서 정확한 대상은 배포 ID로 지정합니다.

release.json 필드뜻
id · name · entry배포물 식별자 / MF container 이름 / 진입 파일 경로.
service · version · kind논리적 서비스명 / 릴리스 버전 / remote 또는 HTML 진입 앱(shell).
dependencies고정 의존 배포 ID. 도구는 지원하지만 현재 SDK·B·D 경로는 런타임 모드를 사용합니다.
runtimeRequirements공통 SDK 지원 범위와 설치된 정확한 React·ReactDOM 버전.
runtimeDependenciesb/d 같은 업무 의존성의 별칭·서비스명·지원 범위. 실제 선택 ID는 포함하지 않습니다.
04

서비스가 SDK와 다른 서비스를 사용하는 방법

Provider는 하위 컴포넌트에 공통 값을 공급하고, Boundary는 위젯마다 따로 관리할 상태의 경계를 만듭니다. 아래 SDK 코드에 나오는 instanceId는 화면 복제본의 이름입니다.

B의 예제로 읽으면 가장 빠릅니다. 선언 → import → Provider 안에서 실행의 세 단계입니다.

① B의 mf.dependencies.json — SDK와 D 요구사항
{
  "platform": {
    "mode": "runtime",
    "service": "platform",
    "requires": ">=1.0.0 <2.0.0"
  },
  "d": {
    "mode": "runtime",
    "service": "d",
    "requires": ">=1.0.0 <2.0.0"
  }
}
② B의 import — URL이나 정확한 D 버전을 코드에 쓰지 않음
import React from 'react';
import { WidgetBoundary, usePlatform, useWidgetScope } from 'platform/sdk';
import { describe } from 'd/data';
import styles from './Widget.module.css';

function Content() {
  const { user } = usePlatform();
  const scope = useWidgetScope();
  return (
    <article className={styles.panel}>
      <p>{user.name} · {describe()}</p>
      <button onClick={() => scope.setCount(value => value + 1)}>
        {scope.count}
      </button>
    </article>
  );
}

export default function Widget({ instanceId }) {
  return (
    <WidgetBoundary instanceId={instanceId} artifactId={__ARTIFACT_ID__}>
      <Content />
    </WidgetBoundary>
  );
}

위 코드는 현재 B 구현을 줄인 예입니다. __ARTIFACT_ID__는 빌드 도구가 넣습니다. instanceId는 Shell이 같은 문서에서 고유하게 부여해야 합니다. 복제한 위젯은 다른 instanceId를 사용합니다.

③ Shell의 실행 경계
// Shell이 먼저 런타임 조합을 고정한 후 실행
import { PlatformProvider } from 'platform/sdk';

createRoot(document.getElementById('root')).render(
  <PlatformProvider>
    <App />
  </PlatformProvider>
);
// App이 로드한 A/C → B의 내부에서 WidgetBoundary를 사용
현재 공개 API누가 사용하는가제공하는 것
PlatformProviderShell이 화면 전체를 감쌈platformVersion, user, theme Context. 기본 user는 김개발/demo, theme은 light입니다. 개발 Host는 선택적 user/theme props로 mock 값을 전달합니다. 실제 인증은 별도입니다.
usePlatform()공통 정보가 필요한 서비스같은 Provider의 값 조회. Provider 밖이면 오류를 냅니다. 인증·권한 검증을 대신하지 않습니다.
WidgetBoundary각 B 위젯의 최상위instanceId/artifactId, 인스턴스별 상태·캐시·구독·Portal DOM 경계. 공개 위젯이 내부에서 감싸므로 Shell이 다시 감쌀 필요가 없습니다.
useWidgetScope()Boundary 내부 컴포넌트count/setCount, eventCount, cache(Map), portalRoot, subscribe(handler). 구독 해제 함수를 effect cleanup에 반환합니다.
ReactIdentity · PlatformContext · getRuntimeSnapshot() · emitDemoEvent()이 예제의 Shell·테스트같은 React/Context인지, 구독과 상태가 분리되는지 검증하는 진단 API. 범용 업무 이벤트 플랫폼이 완성된 것은 아닙니다.

공통 헤더와 사이드바는 서비스가 import하지 않습니다. 현재는 Shell이 렌더링합니다. 서비스는 콘텐츠와 WidgetBoundary를 사용합니다. 개발용 DevLayout·PageContainer는 SDK 1.2.0부터 제공하고, Dev Host는 빌드 도구 1.3.0의 npm run dev로 실행합니다. 운영의 헤더·사이드바는 계속 Shell이 담당합니다.

대시보드가 위젯마다 업무 데이터를 준비하게 하지 않는다는 기존 원칙도 유지합니다. 지금 전달하는 instanceId는 공통 실행 식별자이고 onMounted는 검증용 콜백입니다. 위젯마다 달라지는 업무 props를 대시보드에 추가하는 구조가 아닙니다. 현재 A/C는 이 공통 값을 B로 그대로 전달합니다.

별도의 업무 흐름에서 차량 선택 결과를 받아야 한다면 B가 공개할 입력·출력 계약이 필요합니다. 이 예제에는 차량 목록 조회나 선택 결과 계약이 없습니다. 같은 세션이라는 이유만으로 임의 정보가 자동 전달되는 것도 아니며, 공통 정보는 SDK, 업무 데이터는 위젯이 담당할 API를 통해 연결하도록 구현해야 합니다.

실제 호출 순서는 Shell index → 고정 조합/runtime → bootstrap·공통 SDK → loader의 A/C → b/Widget → d/data입니다. A/C와 B는 소비자 자신의 배포 ID와 별칭으로 의존성을 찾습니다. 같은 B 배포물의 두 인스턴스는 같은 D를 쓰고, 상태만 따로 가집니다.

06

실행·개발·발행의 실제 순서

이미 이 환경이 준비되어 있다면 서버 실행만 하면 됩니다. 전체 build를 실행해야 문서를 읽거나 기존 화면을 볼 수 있는 것은 아닙니다.

기존 환경 — 프로젝트 루트에서
cd integration
npm start

대시보드는 4173/, 관리는 4173/admin, 이 안내서는 4173/handbook입니다. 이미 서버가 켜져 있으면 주소를 열면 됩니다.

처음 받은 환경 — Node.js 24 권장, 프로젝트 루트에서
cd integration
npm ci
npm run setup
npm run build
npm start

setup은 각 프로젝트를 따로 설치하고, build는 예제 전체를 각각 빌드·발행한 뒤 활성화합니다. 기존 SDK·소비자별 B/D 선택은 유지하도록 동작하며 새 A/C 배포물에는 기존 선택을 이어 붙입니다. bootstrap은 fixtures로 의존 선언을 다시 쓰는 초기화이므로, 일상 수정에는 쓰지 않습니다.

작업 대상직접 실행할 명령확인 위치
SDK·A·C·B·D해당 프로젝트에서 npm ci, npm run build. 필요 시 npm start.start는 Remote JSON·파일을 제공합니다. A/C/B의 단독 개발 UI는 npm run dev로 확인하며, 제품 조합 검증은 발행·선택 후 통합 호스트에서 합니다.
Shellprojects/shell에서 npm ci, npm run build. 발행·선택 후 통합 호스트로 확인.npm start의 4180은 별도 미리보기. upstream(기본 4173)의 선택 Shell ID와 빌드 ID가 같아야 합니다. 탭 보호·추적 검증은 4173에서 합니다.
관리 화면integration에서 npm run build:admin/admin. 이 프로젝트에는 npm start 스크립트가 없습니다. 처음에는 setup 또는 프로젝트의 npm ci로 설치합니다.
빌드 도구projects/platform-build-tools에서 npm ci, npm pack생성 tarball을 필요한 프로젝트의 vendor에 배포하고 package/lock을 갱신합니다. 빌드 도구 자체에는 build/start 스크립트가 없습니다.

Remote 미리보기 기본 포트: SDK 4200, A 4201, C 4202, B 1.x 4203, B 2.x 4204, D 1.x 4205, D 2.x 4206입니다. 모든 서버를 동시에 켤 필요는 없습니다. 발행 후에는 4173이 저장소의 파일을 제공합니다. npm start는 빌드 파일 미리보기입니다. UI 서비스의 npm run dev는 소스 감시·재빌드·전체 새로고침을 제공합니다. 입력 상태를 보존하는 HMR은 아닙니다.

예: B 1.x의 화면을 바꾸고 A에서 확인하기

  1. service-b-v1/src/Widget.jsx 또는 Widget.module.css를 수정합니다. API 변경이라면 기존 소비자 호환성도 확인합니다.
  2. B만 빌드합니다. 외부 서비스 소스나 실행 서버는 빌드에 필요하지 않습니다.
  3. 생성된 B 배포물을 발행합니다. 발행만으로 현재 A의 선택이 바뀌지는 않습니다.
  4. 관리 화면에서 A 경로의 새 B와 그 B의 D를 선택하고 검사 후 적용합니다.
  5. 새 탭에서 화면을 확인합니다. 기존 탭은 처음 받은 조합을 유지합니다.
B만 빌드·발행 — 프로젝트 루트에서 시작
cd projects/service-b-v1
# 배포할 변경이라면 package.json과 lockfile 버전도 함께 갱신
npm run build
cd ../../integration
npm run publish -- ../projects/service-b-v1
선택을 CLI로 처리할 경우 — integration에서
# 아래 ID 자리는 registry.json / 발행 출력의 실제 배포 ID로 교체
npm run activate -- --bind 'A_ID:b=NEW_B_ID' --bind 'NEW_B_ID:d=D_ID'

# 같은 B를 유지한 채 D만 변경
npm run activate -- --bind 'B_ID:d=NEW_D_ID'

# 공통 SDK만 변경
npm run activate -- --platform 'NEW_SDK_ID'

# A 자체를 바꿨다면 새 A 역할과 그 A의 의존성을 함께 연결
npm run activate -- --A 'NEW_A_ID' --bind 'NEW_A_ID:b=B_ID'

# Shell 자체를 바꾼 경우
npm run activate -- --shell 'NEW_SHELL_ID'

# 이전 전체 조합으로 롤백
npm run activate -- --composition 'PREVIOUS_COMPOSITION_ID'

선택할 대상은 먼저 발행되어야 합니다. A 예시의 B는 D 연결이 이미 준비된 배포물을 가정하며, 새 B라면 --bind NEW_B_ID:d=D_ID도 추가합니다. 관리 화면은 현재 SDK·B·D 변경을 중심으로 구현되어 있어 A/C/Shell 자체 교체는 위 CLI를 사용합니다.

현재 소스 폴더의 B는 1.4/2.1, D는 1.0/2.0이어도 서버는 검증 때 발행해 보존한 1.5/2.2, 1.1/2.1을 선택할 수 있습니다. 소스의 package.json, 방금 만든 dist, 현재 선택된 배포물은 서로 다른 개념입니다. 실제 선택은 /registry.json 또는 관리 화면에서 확인합니다.

빌드와 발행은 새 파일을 준비하는 단계이고, 활성화는 사용할 조합을 고르는 단계입니다. 서비스별 버전 선택 절차와 파일 삭제·구형 탭 운영은 기존 운영 설명서에 이어집니다.

07

플랫폼에서 제공해야 하는 것

서비스 팀이 공통 기반을 직접 다시 만들지 않게 하려면 아래처럼 전달 경로까지 정해 제공해야 합니다. 현재 구현된 것과 추가로 필요한 것은 구분합니다.

제공 항목누가 어떻게 받는가현재 상태
공통 화면·진입점Shell을 제품 URL로 제공. 헤더·사이드바·로더·공통 Provider를 담당.구현 등록형 페이지 메뉴·주소 연결 구현. 한 단계 hash 라우트, 최대 50개.
런타임 SDKplatform/sdk MF Remote와 지원 범위. 필요한 서비스가 import.구현 Context·위젯 인스턴스 경계. 인증 연동·권한·다국어·알림 API는 없음.
빌드 규칙빌드 시 사용하는 공통 도구 패키지. 서비스가 자체 설치.구현 배포 ID/container/CSS 규칙·React 공유·소스 경계. 현재 JS/JSX와 개발 모드 빌드.
개발용 Host·Layout서비스 하나를 지정하면 공통 Provider·테마·사용자 mock 아래에서 실행하는 개발 전용 진입점.구현 npm run dev + 고정된 dev 키트. SDK 1.2.0의 Provider·DevLayout을 MF로 사용. 업무 API mock·중앙 키트 다운로드 API는 별도 과제.
콘텐츠 Container·디자인 규칙SDK의 공통 PageContainer·UI 컴포넌트·디자인 토큰으로 제공 가능.일부 구현 SDK 1.2.0의 PageContainer: 제목·설명·액션·여백·폭. WidgetBoundary는 수명주기 경계. 전체 디자인 시스템은 추가 과제.
공개 모듈 규격·개발 템플릿./Widget 등 노출 규격, 공통 인스턴스 값, 선택적 설정 스키마, 지원 범위 선언과 예제.예제 일부 현재 A/C/B 예제만 있음. 자동 scaffold·타입 선언·위젯 목록/설정 스키마 없음.
의존 등록·선택·롤백발행 API/CLI, 배포 메타데이터, 고정 조합, 운영 화면.로컬 구현 integration과 admin. 신규 최상위 서비스 등록은 일반화하지 않음.
사용 추적·제거 정책탭 관측과 기한, 사용 경로, 지원 종료·등록 해제·삭제 검사.로컬 구현 플랫폼 서버가 관리. 서비스 팀은 종료 계획과 전환 검증을 제공.
호환성 확인 도구기존 소비자 산출물과 새 공급자를 조합하는 CI 검사·실패 시 활성화 차단.예제 검사 그래프·범위·공존 테스트 있음. 임의 업무 API의 의미적 호환성을 자동 증명하는 도구는 없음.
실제 운영 연동S3/CDN 발행·접근 통제, 인증/권한, 서버 측 업무 권한, 모니터링·감사·공지 발송.추가 필요 현재 로컬 파일·로컬 관리 API. 공지 기록을 저장하지만 실제 알림은 보내지 않음.

따라서 “공통 SDK를 MF로 전달한다”는 선택과 “개발 도구를 npm으로 설치한다”는 선택은 함께 사용할 수 있습니다. SDK의 실제 실행 버전은 중앙 조합이 고르고, 빌드 도구는 각 프로젝트가 설치한 버전으로 코드를 만듭니다. 하나의 플랫폼 버전 번호로 이 둘을 묶어 관리하고 있지는 않습니다.

플랫폼이 자동으로 지키는 것 / 서비스가 책임지는 것

플랫폼 도구가 강제하는 것서비스 팀에서 구현·검증하는 것
container/runtime 이름과 CSS 클래스에 배포 ID 반영document.body 같은 전역 DOM 변경, window/localStorage 키, 전역 이벤트·타이머의 충돌과 정리. SDK가 임의 JavaScript를 격리하지는 않음.
SDK 한 개, 선언된 React 정확한 버전, 의존 범위·서비스 종류·누락·순환 검사같은 함수명·인자·반환값·부작용을 유지하는지. 범위 문자열이 같아도 업무 동작은 테스트해야 함.
Boundary에 속한 캐시·구독·Portal 경계 제공Boundary 사용, 고유 instanceId, 직접 만든 effect·네트워크·구독의 정리. 같은 ID 중복을 SDK가 자동 거절하지는 않음.
등록 해제와 파일 삭제 분리, 현재·탭·롤백·고정 참조 확인자기 서비스의 종료 일정·대체 버전·이관 계획, 관측 밖 소비자와 외부 API 사용 확인.

현재 화면에서 공유해야 하는 것은 선택한 SDK 하나와 호환 React 실행 환경입니다. 모든 서비스의 배포 버전이나 빌드 도구 버전까지 같아야 한다는 뜻은 아닙니다. SDK의 지원 범위와 공개 동작을 유지한 업데이트는 소비자 재빌드 없이 선택합니다.

WIDGET

공개 위젯을 선택해 대시보드에 배치하기

서비스가 공개한 위젯을 관리 화면에서 선택하고, 순서와 너비를 정해 적용합니다. 새 위젯이나 다른 서비스 버전을 추가해도 Shell 코드를 수정하지 않습니다. 배치 정보도 버전 조합에 저장하므로 기존 탭을 유지하고 이전 배치로 롤백할 수 있습니다.

이번 구현에서의 역할

Shell 안에 공통 대시보드 표시 영역을 구현했습니다. 별도 대시보드 프로젝트를 만든 것은 아닙니다. 플랫폼 팀은 표시 영역·관리 화면·검사·운영 기능을 제공하고, 서비스 팀은 업무 위젯과 조회 로직을 만듭니다. 메뉴는 페이지 하나를 여는 연결이고, 대시보드는 여러 위젯을 함께 배치하는 연결입니다. 두 설정은 별도로 관리하지만 같은 SDK와 조합을 사용합니다.

1. 서비스 팀이 대시보드용 위젯을 명시적으로 공개합니다

일반 exposes에는 데이터 함수도 있을 수 있습니다. 따라서 모든 공개 모듈을 위젯으로 취급하지 않고 widgets에 지정한 모듈만 관리 화면에 표시합니다. 빌드 도구 1.7.0을 사용하는 프로젝트의 mf.config.cjs 예시입니다.

서비스 프로젝트의 mf.config.cjs
module.exports = {
  service: 'car', kind: 'remote', port: 4207,
  exposes: {
    './CarPicker': './src/CarPicker.jsx',

이 경우 선택 목록에는 차량 선택·차량 요약만 나타나며 ./data는 제외됩니다. 위 예제의 소스 파일은 서비스 팀이 작성해야 합니다. 실행 가능한 시작 프로젝트는 integration/templates/service-e이며 이미 알림 위젯 선언을 포함합니다. E 실습의 0~5단계로 생성·단독 실행·발행한 뒤 아래 관리 화면에 등록하세요.

기존 서비스에 위젯 공개 정보를 처음 넣을 때는 해당 서비스의 새 배포물이 필요합니다. 기존 발행 파일의 release.json을 덮어쓰지 않습니다. 빌드 도구 1.7.0은 선언을 검사하고 release.json에 widgets를 기록합니다. 같은 버전 번호라도 설정과 내용이 달라지면 새로운 배포 ID가 생성됩니다. 처음 공개한 뒤 배치·선택만 바꾸는 데에는 서비스 재빌드가 없습니다.

위젯의 공통 계약: 업무마다 다른 props는 받지 않습니다

platform-widget-v1은 이 프로젝트의 계약 이름입니다. 공개 모듈은 React 컴포넌트를 default export하고, Host가 주는 공통 instanceId를 받아 SDK WidgetBoundary의 범위로 사용합니다. 사용자·테마는 같은 SDK Context에서 받고, 업무 데이터는 서비스가 직접 조회합니다. 헤더·사이드바나 전역 PlatformProvider를 위젯이 만들지 않습니다.

위젯의 기본 형태
import { WidgetBoundary, usePlatform } from 'platform/sdk';

function Content() {
  const { user } = usePlatform();
  return <p>{user.name}님의 알림</p>;
}

export default function Widget({ instanceId }) {
  return <WidgetBoundary instanceId={instanceId} artifactId={__ARTIFACT_ID__}>
    <Content />
  </WidgetBoundary>;
}

각 배치에는 dashboard-배치ID가 전달됩니다. 다른 배치 ID로 같은 위젯을 두 번 사용하면 상태·캐시·팝업 영역도 따로 만듭니다. 관리자에게 임의 업무 props나 실행 코드를 입력받지 않습니다. 공통 계약 자체가 바뀌면 지원 Host/SDK와 검증도 변경해야 하며, 모르는 계약은 서버가 거절합니다.

2. 플랫폼 담당이 표시 기능을 최초 한 번 도입합니다

이번 표시 영역을 포함한 Shell 1.3.0·관리 앱 1.2.0·최신 integration 서버로 최초 한 번 전환합니다. Shell이 사용하는 빌드 도구는 1.7.0이며, SDK는 기존 1.3.1 배포물을 그대로 사용했습니다. 메뉴 등록 절차의 최초 전환 명령을 같은 격리 실습 저장소에서 실행하면 현재 소스의 새 Shell/Admin을 빌드·발행·선택합니다. 구형 Shell에서는 배치 기능이 비활성화됩니다.

이후 새 서비스의 위젯을 발행해도 플랫폼 담당자가 Shell import를 추가할 필요가 없습니다. 서비스 팀/CI의 서비스 빌드·발행과 관리자의 위젯 선택·배치 적용은 별도 단계입니다.

3. 관리 화면에서 선택하고 배치합니다

  1. 대시보드 위젯 관리 화면을 엽니다. 직접 구성한 서버라면 해당 포트의 /admin#dashboard로 접속하세요. 새 발행 후에는 “최신 조합 불러오기”로 목록을 갱신합니다.
  2. 위젯 추가를 누르고 서비스의 정확한 배포 버전과 공개 위젯을 선택합니다. 서비스가 다른 서비스를 참조하면 하위 버전도 선택합니다.
  3. 배치 ID·표시 제목·너비를 정합니다. “위로/아래로”로 순서를 바꾸고 배치 미리보기를 확인합니다. 미리보기에서는 업무 코드를 실행하지 않습니다.
  4. 조합 검사 → 변경 적용을 누릅니다. 수정하면 검사 결과가 무효화되어 다시 검사해야 합니다.
  5. 제품 화면을 새 탭으로 엽니다. 위젯 설정이 있는 조합은 첫 화면이 대시보드입니다. /#/dashboard로도 접근합니다. 기존 A/C 실험 화면은 “버전 공존 검증” 메뉴(/#/verification)에 남습니다.

4. 적용·실패·롤백과 삭제 보호

  • 새 탭부터 반영: 기존 탭은 이전 배치·버전·입력을 유지합니다. 관리 화면 적용이 이미 열려 있는 화면을 실시간으로 재배치하지 않습니다.
  • 메뉴 이동: 처음 대시보드에 진입할 때 위젯을 로드하고 이후 숨겨 보존합니다. 페이지 메뉴와 오가도 입력을 유지하고 숨긴 영역의 팝업도 함께 숨깁니다. 숨긴 위젯의 구독·업무 작업은 계속 실행될 수 있습니다.
  • 영역별 실패: 기존 SDK RemoteRegion을 그대로 사용합니다. B 2.1 또는 그 하위 D 로딩 실패는 해당 위젯에만 표시하고, 파일 복구 후 각 영역의 다시 시도 버튼으로 복구합니다. B 1.4 입력·카운터는 유지됩니다. 같은 실패한 배포물의 여러 위젯은 각각 오류/재시도 UI를 가집니다.
  • 롤백: 관리 이력에서 이전 조합 불러오기 → 조합 검사 → 이 조합으로 롤백. SDK·서비스·하위 의존성·페이지 메뉴·위젯 순서/너비/제목을 함께 복원합니다.
  • 삭제 보호: Shell → 배치 → 서비스 → 하위 서비스까지 사용 추적에 포함합니다. 위젯 제거 후에도 열린 탭과 롤백 참조가 파일 삭제를 막습니다. 기존 A/C 검증 경로나 페이지 메뉴의 사용도 따로 남을 수 있습니다.

로딩·React 렌더 오류를 영역별로 처리하는 기능입니다. 같은 브라우저에서 실행하므로 임의 전역 변경이나 무한 루프를 분리하는 보안 경계는 아닙니다. 공개 정보 검사는 컴포넌트의 업무 동작까지 보장하지 않으므로 서비스 팀의 통합 검증이 필요합니다.

1. 서비스 팀: 자기 프로젝트를 빌드·발행합니다

처음 만드는 팀은 아래 E 프로젝트 실습의 0~5단계를 따르세요. 서비스는 헤더·사이드바 없이 콘텐츠를 만들고, ./Widget 등 공개 모듈에서 React 컴포넌트를 default export합니다. 사용자·SDK는 공통 Provider에서 받습니다. Shell은 모든 페이지에 공통으로 instanceId="menu-메뉴ID"만 전달합니다. 서비스마다 다른 업무 입력을 관리 화면에 추가하는 구조가 아닙니다.

발행과 메뉴 등록은 별도입니다. 현재 관리 화면은 이미 발행된 서비스의 정확한 배포 ID를 선택합니다. 파일 업로드나 임의 script URL 입력은 제공하지 않습니다. 로컬 발행 예시는 npm run publish -- /서비스프로젝트/절대경로이며 해당 프로젝트의 dist 전체를 저장합니다.

3. 관리 화면: 서비스와 메뉴를 등록합니다

  1. 서비스 · 메뉴 관리를 엽니다. 다른 저장소나 포트를 쓰면 주소를 맞춥니다. 최근 발행한 서비스가 안 보이면 최신 조합 불러오기를 누릅니다. 이 버튼은 저장하지 않은 편집도 초기화합니다.

  3. 해당 저장소에서 설치·빌드합니다. 형제 폴더 소스를 import하지 않습니다.
  4. CI가 dist와 release.json을 플랫폼의 발행 경로로 보냅니다. 현재 제공된 publish CLI는 로컬 경로 입력이며 원격 업로드 CI는 추가 구현이 필요합니다.
  5. 기존 소비자와 함께 검증한 뒤 사용할 조합을 활성화합니다. 독립 저장소로 옮기면 integration의 fixture 경로도 검증 환경에 맞게 조정합니다.

호환성이 깨지는 변경은 어디서 처리하는가

B가 공개 API를 깨면 A/C 중 새 API를 채택하는 서비스가 코드를 수정하고 지원 범위를 갱신해 다시 빌드합니다. 아직 이전 API가 필요한 서비스는 이전 B를 계속 선택할 수 있습니다. 공개 모듈 버전 범위만 넓히고 테스트 없이 연결하지 않습니다.

SDK는 한 문서에서 하나를 공유하므로, 새 SDK가 기존 서비스를 지원하지 않으면 그 조합을 바로 전환할 수 없습니다. 먼저 호환 API를 함께 제공하거나 필요한 소비자들을 이관한 뒤 조합을 전환합니다. 이 프로젝트는 SDK의 명목 버전과 별개인 계약 스키마 버전·자동 어댑터를 구현하지 않았습니다.
