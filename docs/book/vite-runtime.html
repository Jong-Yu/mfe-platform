현재 구현 · VITE · 01

V1. 프로젝트는 따로 만들고, 사용자의 화면에서는 함께 실행합니다

이 저장소의 목표는 A·B·C·D와 공통 SDK를 각각 개발하고 빌드하면서, 한 브라우저 화면에서는 필요한 버전들을 연결하는 것입니다. 현재 projects/는 플랫폼 빌드 도구 2.0.0을 통해 Vite 8.3.6과 @module-federation/vite 1.23.11을 사용합니다.

먼저 하나의 제품을 떠올려 보세요. 왼쪽에는 메뉴, 위에는 사용자 이름, 가운데에는 OTA 화면과 정비 화면이 있습니다. 두 화면은 모두 차량 선택 위젯을 쓰지만, OTA는 B 1.x의 사용법에 맞춰 개발했고 정비는 B 2.x를 사용합니다. B를 하나로 강제하면 한쪽을 동시에 수정해야 합니다. 이 프로젝트는 두 B 배포물을 구분해 불러오되 공통 React와 SDK는 공유하는 방법을 구현합니다. OTA·정비·차량 선택은 학습용 이름이며, 실제 화면은 카운터·메모·팝업으로 분리 상태를 확인합니다.

MFE, MF, Vite는 서로 다른 질문에 답합니다

이름답하는 질문이 프로젝트의 선택
MFE · Micro Frontend팀과 업무별로 프런트엔드의 개발·배포 경계를 어떻게 나눌까?Shell·SDK·서비스가 자체 소스, 설정, package와 잠금 파일을 가지고 따로 빌드합니다.
MF · Module Federation서로 다른 빌드가 공개한 모듈을 실행 중에 어떻게 가져올까?b/Widget, platform/sdk, d/data 같은 공개 모듈을 연결합니다.
Vite + MF 플러그인작성한 소스와 설정을 어떤 실행 파일로 만들까?ES 모듈 형식의 remoteEntry.js, 실행 청크, CSS와 Shell 진입 파일을 만듭니다.
이 저장소의 플랫폼 코드어떤 버전을 선택하고, 충돌·오류·기존 탭을 어떻게 관리할까?배포 ID, 고정 조합, 소비자별 연결, SDK 경계, 발행·검사·롤백 정책을 추가합니다.

MF를 설치했다고 독립 배포와 버전 운영이 모두 완성되지는 않습니다. MF는 공개 모듈을 연결하는 기반이고, 이 저장소의 조합 저장소와 런타임이 “A가 사용하는 B는 어느 배포물인가”를 결정합니다. Vite는 그 계약을 브라우저에서 실행할 수 있는 파일로 만드는 단계입니다.

저장소를 두 방향으로 읽기: 만드는 쪽과 실행하는 쪽

개발·빌드 시점
  각 projects/서비스
    자체 src + package/lock + mf 설정
      └─ 플랫폼 빌드 도구 → Vite + MF → 자체 dist/
                                      └─ 발행 → 배포물 저장소

선택·실행 시점
  관리 화면 / 운영 명령 → 검사한 조합 저장 → 새 탭의 조합 선택
    └─ Shell HTML + shell.js
        ├─ 이 탭의 고정 조합 + MF 런타임
        ├─ 공통 React / ReactDOM + platform/sdk
        ├─ A → B 1.x → D 1.x
        ├─ C → B 2.x → D 2.x
        └─ 등록된 메뉴와 대시보드 위젯
             └─ 조합이 지정한 서비스의 공개 모듈

위 그림의 A/C 경로는 버전 공존을 확인하는 기본 사례입니다. 등록형 메뉴와 대시보드는 다른 진입 경로이며, Shell이 조합의 목록을 읽어 서비스 모듈을 배치합니다. A가 항상 모든 서비스의 부모인 것은 아닙니다. A → C → B처럼 한 서비스를 다른 서비스 안에 넣는 중첩 사례는 별도의 통합 시나리오에서 구성합니다.

위치책임과 수정하는 이유다른 영역과의 관계
projects/shell/공통 진입, 헤더·메뉴, 라우팅, SDK Provider, 서비스 배치페이지를 시작하고 고정 조합을 설치합니다. SDK와 서비스를 MF로 불러옵니다.
projects/platform-sdk/공통 사용자·테마 Context, 위젯 상태 경계, RemoteRegion, 개발용 레이아웃자체 Remote 배포물입니다. 서비스가 platform/sdk로 가져옵니다.
projects/service-a/, service-c/다른 업무 모듈을 사용하는 소비자 화면각자의 b 요구 범위와 조합 연결로 서로 다른 B를 사용합니다.
projects/service-b-v1/, service-b-v2/공개 React 위젯과 내부 UIB는 A/C에 대해서는 공급자이고, SDK·D에 대해서는 소비자입니다.
projects/service-d-v1/, service-d-v2/공개 데이터 함수 모듈MF는 화면 컴포넌트뿐 아니라 JavaScript 함수·값도 연결할 수 있습니다.
projects/platform-build-tools/설정 검증, Vite 빌드, CSS 경계, 배포 정보, 단독 개발 도구각 프로젝트가 npm 개발 의존성으로 설치합니다. 런타임 SDK를 담은 패키지는 아닙니다.
projects/platform-admin/, integration/발행·버전 선택·메뉴·배치·복구·사용 추적·검증관리 UI와 서버·명령이 같은 조합 저장소를 다룹니다. 관리 앱 자체의 배포 선택은 서비스 실행 조합과 구분됩니다.

한 저장소에 모여 있다는 사실과 하나의 앱으로 빌드한다는 것은 다릅니다. 이 프로젝트는 루트 npm workspace에 의존하지 않습니다. 개별 서비스는 다른 서비스의 src/를 직접 import하지 않고, 자기 src/와 설치한 패키지 안에서 빌드합니다. 전체 설치·빌드를 순서대로 실행하는 통합 명령은 실험을 편하게 하는 도구입니다.

공통 SDK와 공통 빌드 도구를 구분하세요

SDK의 버튼 재시도 정책을 호환되게 개선하면 SDK를 새로 빌드·발행하고 새 조합에서 선택할 수 있습니다. 이미 발행된 소비자의 import는 그대로입니다. 반면 빌드 도구의 CSS 이름 규칙을 바꾸면 그 도구로 소비자를 다시 빌드해야 새 규칙이 산출물에 들어갑니다. 서비스의 npm에 설치하는 @mfe/platform-build-tools 버전과 브라우저가 사용하는 SDK 버전은 서로 독립적입니다.

이 학습서의 현재 구현 설명은 최상위 projects/와 integration/를 기준으로 합니다. 뒤의 20개 독립 예제는 Webpack 실행 파일까지 보존한 과거 학습 스냅샷입니다. 사용자별 구독은 예제 20의 기능이고, DB·S3 확장은 설계안입니다. 현재 루트 구현의 기능으로 섞어 읽지 마세요.

현재 구현 · VITE · 02

V2. “B를 쓴다”는 말은 공개·요구·선택 세 단계로 나뉩니다

B는 무엇을 공개할지 선언하고, A는 어떤 B와 호환되는지 선언합니다. 실제 B 배포물은 제품 조합에서 선택합니다. 이 세 정보를 분리해야 A를 다시 빌드하지 않고 호환되는 B를 바꿀 수 있습니다.

1. 공급자 B: 사용할 수 있는 모듈 이름을 공개합니다

다음은 service-b-v1/mf.config.cjs의 공개 설정입니다. 공개 이름 ./Widget은 다른 프로젝트가 사용하는 계약이고, ./src/Widget.jsx는 B가 관리하는 내부 파일입니다. 내부 파일을 옮겨도 공개 이름과 입력·출력을 유지하면 소비자의 import를 그대로 둘 수 있습니다.

// projects/service-b-v1/mf.config.cjs
module.exports = {
  service: 'b',
  kind: 'remote',
  port: 4203,
  exposes: { './Widget': './src/Widget.jsx' }
};

service는 논리적 서비스 이름, kind는 빌드 역할입니다. remote는 다른 코드가 가져갈 모듈을 공개하고, shell은 HTML과 실행 진입점을 갖습니다. 여기의 port는 개발·미리보기 서버 설정이며 운영 조합에서 특정 B를 고르는 키가 아닙니다.

2. 소비자 A: 필요한 별칭과 지원 범위를 선언합니다

// projects/service-a/mf.dependencies.json
{
  "b": {
    "mode": "runtime",
    "service": "b",
    "requires": ">=1.4.0 <2.0.0"
  }
}

// projects/service-a/src/index.jsx
import React from 'react';
import BWidget from 'b/Widget';

export default function ConsumerWidget(props) {
  return <BWidget {...props} />;
}

b는 A 안에서 사용하는 별칭입니다. b/Widget은 별칭 b가 가리키는 Remote의 ./Widget을 의미합니다. requires는 “이 범위의 B를 연결할 수 있다”는 선언이며, 가장 높은 버전을 자동으로 찾아 달라는 지시가 아닙니다. 실제 연결은 조합이 정합니다.

A는 여기서 SDK를 직접 import하지 않습니다. A가 가져오는 B가 platform/sdk와 d/data를 사용하므로 B의 의존 선언에 SDK와 D가 들어갑니다. 각 서비스는 자신이 직접 사용하는 의존성을 선언하고, 조합 검사는 그 연결을 따라 전체 그래프를 확인합니다.

// projects/service-b-v1/mf.dependencies.json
{
  "platform": {
    "mode": "runtime", "service": "platform",
    "requires": ">=1.0.0 <2.0.0"
  },
  "d": {
    "mode": "runtime", "service": "d",
    "requires": ">=1.0.0 <2.0.0"
  }
}

3. 조합: 소비자별로 정확한 배포 ID를 연결합니다

다음은 관계를 보여주는 설명용 JavaScript 표기입니다. A_ID 같은 값은 실제 배포 ID의 자리표시자이고, 그대로 실행하거나 저장할 JSON은 아닙니다.

runtimeBindings = {
  [A_ID]:   { b: B_1_ID },
  [C_ID]:   { b: B_2_ID },
  [B_1_ID]: { d: D_1_ID },
  [B_2_ID]: { d: D_2_ID }
};
selected.platform = SDK_ID;

검색 키는 소비자 배포 ID + 별칭입니다. A의 b와 C의 b는 철자가 같아도 서로 다른 항목이므로 B 1.x와 B 2.x가 함께 존재할 수 있습니다. B 1.x와 B 2.x가 사용하는 d도 같은 방식으로 구분합니다. 반면 platform은 한 페이지 전체에서 하나를 선택하는 특별한 공통 의존성입니다.

동일한 A 배포물을 두 번 띄운 경우에는 둘 다 같은 A→B 연결을 씁니다. 두 A 인스턴스마다 다른 B를 고르는 기능은 이 표에 없습니다. 화면 복제본의 상태는 instanceId와 SDK 경계가 나누며, 배포 버전 선택과 화면 상태 분리를 서로 다른 문제로 다룹니다.

빌드 도구는 이 설정을 무엇으로 바꾸나요?

입력 또는 산출물담긴 정보누가 사용하는가
src/컴포넌트·함수·CSS Modules, 다른 서비스의 공개 모듈 importVite가 변환·묶어서 실행 파일을 만듭니다.
mf.config.cjs서비스 이름, Shell/Remote 역할, 공개 이름과 파일, 선택적 위젯 목록플랫폼 빌드 도구가 MF 플러그인 설정으로 변환합니다.
mf.dependencies.json별칭, 서비스 이름, 지원 범위 또는 고정 의존 배포 정보빌드 시 연결용 코드를 만들고 배포 정보에 요구사항을 기록합니다.
dist/remoteEntry.jsRemote의 공개 모듈에 접근하는 ES 모듈 입구브라우저 런타임이 가져와 init·get을 호출합니다.
dist/assets/실제 실행 청크, CSS, 소스맵 등입구와 공개 모듈에서 필요한 파일을 추가로 로드합니다.
dist/release.json정확한 배포 ID, 진입 파일, 형식, 요구사항, 공개 모듈과 의존 관계발행 도구·조합 검사·실행 런타임이 같은 배포물을 식별합니다.
저장된 조합 JSONShell·SDK·서비스 선택, 소비자별 연결, 메뉴·대시보드 배치한 탭이 시작할 때 선택표를 받아 유지합니다.

배포 ID는 서비스_버전_해시 형태입니다. 해시 입력에는 소스, package와 잠금 파일, 두 MF 설정 파일, 빌드 도구 버전이 들어갑니다. 절대 폴더 경로와 README, 현재 런타임에서 선택한 B·D·SDK의 실제 ID는 이 입력에 넣지 않습니다. 따라서 같은 입력으로 별도 폴더에서 빌드해도 같은 ID를 만들 수 있고, 조합의 B 선택만 바꿔도 A의 ID는 바뀌지 않습니다.

release.json에서 현재 Vite 구현을 판별하는 필드

format: "esm"은 브라우저 ES 모듈로 로드한다는 뜻이고, federation: "vite"는 현재 빌드 방식을 기록합니다. retryProtocol: "vite-preflight-v1"은 이 배포물이 지원하는 복구 규약입니다. exposeChunks는 공개 모듈과 생성된 청크의 연결, exposeImports는 공개 모듈별 정적 원격 의존 관계, federationImports는 전체에서 수집한 원격 import 목록입니다. 런타임은 이 정보를 이용해 부모 모듈을 평가하기 전에 필요한 하위 모듈을 준비합니다.

runtimeRequirements에는 SDK 지원 범위와 설치된 React·ReactDOM의 정확한 버전이, runtimeDependencies에는 b·d 같은 업무 의존 범위가 들어갑니다. dependencies는 고정 의존 모드에서 쓰는 배포 ID 목록입니다. 현재 루트의 SDK·B·D 연결을 설명할 때는 런타임 선택을 기준으로 읽습니다.

release.json은 이 프로젝트가 생성하는 배포 계약입니다. MF 플러그인의 manifest와 같은 파일이 아닙니다. 현재 빌드 설정은 플러그인의 manifest·dts 생성을 끄고 별도의 release 정보를 씁니다. 따라서 MF를 쓴다는 이유만으로 mf-manifest.json이나 다른 서비스의 TypeScript 선언이 자동으로 준비된다고 가정하면 안 됩니다.

V3. import 한 줄 뒤에서 조합·입구·공유 객체가 연결됩니다

A를 빌드할 때 B의 소스나 실행 파일을 받아 A에 넣지 않습니다. 빌드에는 “A가 별칭 b의 Widget을 사용한다”는 연결 정보를 넣고, 브라우저가 실행할 때 고정 조합을 통해 실제 B를 찾습니다.

빌드 시점: 실제 배포 URL을 나중에 찾을 연결을 만듭니다

플랫폼 빌드 도구는 선언된 각 Remote를 type: 'module'로 MF 플러그인에 전달합니다. 이때 entry에는 https://mfe.invalid/소비자ID/별칭/remoteEntry.js 형태의 표식을 넣습니다. 이 주소는 실제 서버가 아니며 요청해서는 안 되는 내부 식별 표식입니다. 표식에는 소비자와 별칭만 있고, 현재 선택한 B 배포 ID는 없습니다.

생성된 MF 연결 코드가 Remote 입구를 요구하면 플랫폼의 런타임 플러그인 loadEntry가 표식을 가로채 해석합니다. 표식의 소비자 ID를 확인한 다음, 런타임 의존이면 getDependencyContainer(consumerId, alias)를 호출합니다. SDK 별칭 platform은 이 탭에서 선택한 공통 SDK로 연결합니다. 그 결과 MF 플러그인의 모듈 연결 기능과 이 프로젝트의 버전 선택 정책이 함께 작동합니다.

A 소스: import BWidget from 'b/Widget'
  ↓ 빌드: A의 소비자 ID와 b 별칭으로 MF 연결 생성
생성된 연결: A_ID + b + ./Widget
  ↓ 실행: compositionPlugin.loadEntry
고정 조합: runtimeBindings[A_ID].b = B_ID
  ↓ artifacts[B_ID]에서 진입 파일 조회
/artifacts/B_ID/remoteEntry.js
  ↓ 공통 share scope로 init → get('./Widget')
Widget 실행 모듈 → React 컴포넌트 → 화면에 마운트

새 탭이 시작되는 과정을 한 단계씩 따라가기

  1. 서버가 선택된 조합의 Shell HTML을 제공합니다. 조합을 활성화할 때 서버는 해당 조합 JSON을 가리키는 __MFE_BOOT_URL__을 HTML에 넣어 보관합니다. HTML과 선택표가 서로 다른 순간의 버전을 가리키지 않도록 준비한 뒤 현재 조합 포인터를 바꿉니다.
  2. 브라우저가 Shell ES 모듈을 시작합니다. Shell의 src/index.js는 주입된 조합 URL을 가져옵니다. 주입값이 없는 경로에서는 /registry.json을 사용합니다. 응답의 Shell 배포 ID가 지금 실행 중인 Shell과 일치하는지도 확인합니다.
  3. 조합을 고정하고 런타임을 한 번 설치합니다. deepFreeze로 조합 객체를 재귀적으로 동결하고 __MFE_RUNTIME__에 런타임을 설치합니다. 같은 페이지에서 새 런타임으로 덮어쓰지 않습니다. 탭 보호가 필요한 실행에서는 보호 절차도 부팅 전에 시작합니다.
  4. 공통 SDK를 먼저 준비합니다. await import('platform/sdk')를 끝낸 뒤 bootstrap을 가져옵니다. React 렌더링을 시작할 때 SDK의 명명된 export와 Context가 준비되어 있도록 순서를 나눈 것입니다.
  5. Shell이 Provider 안에 화면을 만듭니다. bootstrap은 createRoot(...).render(<PlatformProvider><App /></PlatformProvider>)를 실행합니다. 공통 레이아웃과 현재 메뉴·대시보드 배치는 탭이 받은 조합을 기준으로 만들어집니다.
  6. 필요한 서비스의 공개 모듈을 요청합니다. A/C 공존 검증 화면은 Shell의 loadRemote를 사용합니다. 등록형 메뉴와 대시보드는 SDK의 RemoteRegion을 사용하며 각각 menu/메뉴ID, dashboard/배치ID라는 연결을 찾습니다.
  7. 하위 의존성을 준비한 뒤 공개 모듈을 평가합니다. A의 Widget은 B의 Widget을, B는 SDK와 D를 사용합니다. 런타임은 공개 모듈별 의존 목록을 따라 필요한 Remote를 준비하고, MF container의 get에서 얻은 factory를 호출해 모듈을 얻습니다.
  8. React가 해당 컴포넌트 인스턴스를 마운트합니다. 같은 B 코드가 재사용돼도 각 배치에 다른 instanceId를 주고 별도의 상태 경계를 만듭니다.

remoteEntry.js는 전체 앱이 들어 있는 단일 파일이 아니라 공개 모듈로 들어가는 입구입니다. 실제 공개 모듈을 가져올 때 추가 JS·CSS 파일을 요청할 수 있습니다. 따라서 발행·보관 단위는 entry 하나가 아니라 해당 배포물의 전체 파일 집합입니다.

React를 공유한다는 것과 SDK를 공유한다는 것

각 프로젝트는 자기 package와 잠금 파일로 React를 설치합니다. 빌드 도구는 설치된 React·ReactDOM 버전을 읽어 MF 공유 설정에 singleton: true, strictVersion: true, 정확한 requiredVersion을 넣습니다. ReactDOM을 사용하는 경우 react-dom/client도 공유 대상으로 설정합니다. 조합 검사 역시 소비자들의 정확한 React 버전이 맞는지 확인합니다.

실행 중에는 Host가 초기화한 공통 공유 표인 share scope를 Remote들에 전달합니다. 이 프로젝트의 런타임 플러그인은 Host의 최종 공유 표를 런타임에 연결하고, Remote를 초기화할 때 같은 표를 기준으로 삼습니다. 먼저 로드된 공유 모듈을 사용하는 loaded-first 전략도 명시합니다.

하지만 React만 같다고 SDK의 Context가 자동으로 같아지는 것은 아닙니다. SDK 소스를 서비스마다 복사하거나 두 SDK 배포물을 평가하면 별도의 Context 객체가 생길 수 있습니다. 그래서 이 런타임은 조합에 선택된 SDK 하나를 가져오고, 다른 SDK 선택을 같은 페이지에 로드하려는 요청은 거절합니다. Shell과 B가 같은 PlatformContext 객체를 사용해야 B의 usePlatform()이 Shell의 Provider 값을 읽습니다.

캐시가 세 단계인 이유

대상구분 기준유지되는 것
Remote container와 공개 모듈 로딩배포 ID, 공개 모듈 이름이미 성공한 파일·공유 초기화·모듈을 반복 요청마다 다시 실행하지 않도록 관리합니다.
SDK의 RemoteRegion 로딩런타임 객체 + 소비자 ID + 별칭 + 공개 모듈같은 연결을 동시에 요청하는 영역의 비동기 작업을 공유합니다.
사용자의 위젯 상태·메모 캐시React로 마운트한 WidgetBoundary 인스턴스같은 코드의 복제본이라도 카운터·입력·캐시는 따로 유지합니다.

공유하는 것은 실행 코드와 공통 기반이고, 각 위젯에서 사용자가 작업한 값은 별도입니다. “같은 B를 두 번 띄웠다”가 “상태도 하나다”를 의미하지 않는 이유입니다.

새 B를 선택한 뒤 늦게 C를 여는 기존 탭은 어떻게 되나요?

그 탭이 시작할 때 받은 조합을 계속 사용합니다. 아직 C를 화면에 표시하지 않았어도 나중에 C→B를 해석할 때 이전 조합의 연결을 찾습니다. 브라우저가 매 import마다 최신 registry를 다시 읽어 버전을 섞는 구조가 아닙니다. 새 조합은 새로 진입하거나 새로고침한 탭에 적용됩니다. 이것이 기존 배포 파일을 보관하고 열린 탭·롤백 참조를 추적해야 하는 이유입니다.

현재 구현 · VITE · 04

V4. 버전·인스턴스·실패를 서로 다른 경계로 다룹니다

서로 다른 B 버전을 가져오는 것만으로 안전한 화면 조합이 완성되지는 않습니다. 이 구현은 파일과 모듈, React 상태, CSS, 로딩 오류를 각각 구분해 관리합니다.

경계현재 Vite 구현이 구분하는 방법서비스가 지켜야 할 부분
배포 파일·MF 모듈배포 ID별 URL과 MF 이름, ESM 모듈 로딩, 배포 ID별 container 관리형제 프로젝트 소스를 직접 참조하지 않고 공개 계약을 사용합니다.
CSSRemote의 CSS Modules 사용, 클래스 이름에 배포 ID와 해시 포함, pure 모드·소스 경계 검사컴포넌트가 생성된 클래스 이름을 사용하고 공통 DOM에 임의 스타일을 주입하지 않습니다.
공통 사용자·테마선택된 SDK의 PlatformProvider와 공통 ContextSDK의 usePlatform()으로 값을 읽습니다. 실제 인증·권한 검증은 별도 구현입니다.
위젯 상태·캐시·구독·팝업WidgetBoundary 인스턴스별 상태, Map, 구독 집합, Portal DOMinstanceId를 전달하고 구독 정리 함수를 effect cleanup에 연결합니다.
원격 UI의 로딩·렌더링 실패RemoteRegion의 로딩 상태·오류 표시·재시도, 내부 RenderBoundary격리가 필요한 위치에 경계를 두고 업무 API 오류도 서비스에서 처리합니다.

WidgetBoundary는 무엇을 따로 만드나요?

B의 공개 Widget은 내부에서 WidgetBoundary로 콘텐츠를 감쌉니다. 경계가 마운트될 때 카운터 상태, 인스턴스별 Map, 구독 목록, 팝업을 붙일 DOM 영역을 만듭니다. 같은 B 배포물로 위젯을 두 개 렌더링해도 각 경계가 별도로 만들어집니다. 위젯을 제거하면 해당 구독이 정리되고 그 안의 팝업 DOM도 제거됩니다.

// 실제 B 위젯의 경계 구조를 줄인 예
import { WidgetBoundary, useWidgetScope } from 'platform/sdk';

export default function Widget({ instanceId }) {
  return (
    <WidgetBoundary instanceId={instanceId} artifactId={__ARTIFACT_ID__}>
      <Content />
    </WidgetBoundary>
  );
}

function Content() {
  const scope = useWidgetScope();
  return <button onClick={() => scope.setCount(n => n + 1)}>
    {scope.count}
  </button>;
}

instanceId는 화면 복제본을 알아보는 이름입니다. 같은 artifactId를 사용하더라도 서로 다른 인스턴스를 나타낼 수 있습니다. 빌드 도구가 넣는 __ARTIFACT_ID__와 서비스 팀이 전달하는 instanceId를 혼동하지 마세요.

현재 Remote 스타일은 .module.css를 사용해야 합니다. 클래스 이름은 배포 ID를 포함하므로 B 1.x의 panel과 B 2.x의 panel이 같은 전역 클래스로 충돌하지 않습니다. 순수 전역 선택자가 새어 나오는 경우에는 검사에서 거절합니다. 이 구조는 Webpack의 output.uniqueName이나 청크 전역 이름으로 설명하는 이전 방식과 구분해야 합니다.

오류 격리는 경계를 둔 위치에서 시작합니다

A의 실제 기본 소스는 B를 정적으로 import합니다. 이 경우 A를 가져오는 중 B를 준비하지 못하면 A 로딩도 실패할 수 있습니다. MF가 모든 하위 영역을 자동으로 별도 오류 경계로 나누지는 않습니다. 중첩 시나리오처럼 A 안에서 특정 C 영역만 재시도하려면 그 위치에 RemoteRegion을 배치합니다. 등록형 메뉴·대시보드에는 Shell이 이미 이 경계를 사용합니다.

// 의존성을 선언한 소비자가 원격 UI 영역을 배치하는 예
import { RemoteRegion } from 'platform/sdk';

<RemoteRegion
  consumerId={__ARTIFACT_ID__}
  alias="b"
  exposedModule="./Widget"
  instanceId="order-picker"
  label="차량 선택"
  componentProps={{ instanceId: 'order-picker' }}
/>

위 코드를 사용하는 서비스는 platform과 b를 직접 의존성으로 선언해야 합니다. consumerId는 요청하는 서비스 자신의 배포 ID이고, 대상 B의 ID가 아닙니다. alias는 그 소비자에게 선언·선택된 연결, exposedModule은 공급자의 공개 이름입니다. RemoteRegion은 공개 모듈의 default export를 React 컴포넌트로 렌더링하고 componentProps를 전달합니다.

Vite에서는 무엇을 다시 시도하나요?

  1. 처음 로드할 때 하위 의존 파일을 먼저 준비합니다. 런타임은 exposeImports를 따라 자식 공개 모듈을 준비한 뒤 부모의 공개 모듈을 가져옵니다. 하위 파일의 일시적인 로딩 실패가 부모 ESM 모듈의 평가 실패로 번지는 상황을 줄이기 위한 순서입니다.
  2. 실패한 영역에는 오류와 재시도 버튼을 표시합니다. 정상 영역을 다시 마운트하거나 전체 페이지를 새로고침하지 않습니다. 오류가 난 영역 안의 상태는 재마운트 과정에서 초기화될 수 있습니다.
  3. 버튼을 누르면 같은 고정 조합의 실패 경로를 준비합니다. SDK는 해당 영역의 의존 관계를 따라 지원되는 복구 규약을 확인하고, 실패한 공개 모듈의 캐시 항목을 정리·준비합니다. 새로운 버전으로 바꾸는 작업이 아닙니다.
  4. 실패한 네트워크 import는 새 요청 URL로 다시 시도합니다. 생성된 상대 동적 import는 플랫폼의 __MFE_IMPORT__를 사용합니다. 로딩 실패로 판별된 요청에는 다음 시도에서 mfe_retry 쿼리를 붙이며, 성공한 로딩은 유지합니다.
  5. SDK 1.3.1은 수동 재시도의 일시적 로딩 실패에 한 번 더 대응합니다. 버튼으로 시작한 재시도가 네트워크·파일 로딩 오류로 실패하면 500ms 뒤 한 번 더 시도합니다. 최초 자동 로딩에 무한 재시도를 넣은 것이 아니며, 수동 요청 한 번에서 최대 두 차례 시도합니다.

이 복구의 규약 이름이 vite-preflight-v1입니다. 브라우저의 ESM 캐시 전체를 지우거나 이미 실행된 코드를 unload하는 방식이 아닙니다. 정상 B의 상태·캐시·공유 객체를 유지하면서 실패한 로딩을 다시 시도하는 것이 목적입니다. 이전 Webpack의 require.cache·require.resolveWeak·webpack/container/remote/... 설명을 현재 실행 방식에 그대로 적용하지 않습니다.

복구할 수 있는 실패와 별도로 고쳐야 하는 문제

서버의 일시적 404·503 등으로 JS·CSS 파일을 가져오지 못했고 같은 배포 파일이 정상 제공되면 재시도로 복구할 수 있습니다. 반면 잘못된 공개 모듈 이름, 미등록 별칭, 호환되지 않는 조합, 모듈 실행 중 던진 임의 오류, 이미 일어난 전역 부작용, 업무 API의 의미적 실패를 이 규약이 자동 수정하지는 않습니다. SDK의 500ms 추가 시도 역시 일시적 로딩 오류만 대상으로 판별합니다.

현재 공유·격리는 보안 격리용 iframe이나 별도 JavaScript 실행 환경이 아닙니다. 서비스가 window에 전역 값을 쓰거나 같은 localStorage 키를 사용하면 서비스 간 합의가 필요합니다. React Context를 공유한다는 사실도 백엔드의 인증·권한 검증을 대신하지 않습니다.

메뉴·대시보드가 서비스를 연결하는 방식

등록형 Shell은 조합의 메뉴 목록을 읽고 메뉴별 menu/ID 연결을 사용합니다. 대시보드는 서비스가 widgets에 명시한 공개 위젯만 배치 후보로 사용하고 dashboard/ID 연결을 만듭니다. 일반 exposes에는 함수 모듈도 있으므로 모든 공개 모듈을 UI 위젯으로 취급하지 않습니다.

Shell이 해당 등록 프로토콜을 지원하는 상태라면 기존 서비스의 선택·제목·순서·너비·메뉴 구성을 조합에서 변경할 수 있습니다. 새 탭은 새 배치를 쓰고 기존 탭은 이전 배치를 유지합니다. 이 변경 자체는 Shell 소스를 다시 빌드하는 작업이 아닙니다. 새로운 공개 계약이나 Shell 기능이 필요하면 그 기능을 제공하는 코드 변경과 빌드는 별도로 해야 합니다.
