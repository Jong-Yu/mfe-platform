1. 작성하는 코드와 브라우저가 받는 파일

개발자는 React 컴포넌트를 작성합니다. 컴포넌트는 화면 일부를 만드는 함수라고 생각하면 됩니다. props는 부모가 전달하는 입력이고, state는 그 화면 안에서 바뀌는 값입니다. 같은 버튼 컴포넌트를 두 번 표시해도 각자의 state를 가질 수 있습니다.

// 개념 설명용 코드 — 프로젝트에 그대로 붙여 넣는 완성 예제는 아닙니다.
function CarCounter({ title }) {
  const [count, setCount] = React.useState(0);
  return <button onClick={() => setCount(count + 1)}>
    {title}: {count}
  </button>;
}

CarCounter의 코드는 하나여도 화면에 두 번 배치하면 두 인스턴스가 생깁니다. 이 구분이 나중에 “같은 B 위젯을 두 번 띄우는데 메모가 섞이면 안 된다”는 요구와 연결됩니다.

발행과 적용은 다른 행동입니다. 새 파일을 저장소에 올려도 어떤 화면이 쓸지 선택하지 않으면 기존 화면이 자동으로 바뀌지 않습니다. 이 구분은 모든 예제에 반복됩니다.

같은 로그인 쿠키를 가진다고 React의 사용자 값까지 자동으로 공유되지는 않습니다. 이 예제는 Shell이 Provider에 값을 넣고, 서비스가 같은 SDK의 Context를 읽습니다. Provider와 소비자가 같은 Context 객체를 써야 한다는 조건은 React 공식 문서에 설명되어 있습니다.

확인: 소스를 수정한 뒤 브라우저를 새로고침하면 운영 화면도 바로 바뀔까요?

아닙니다. 운영 화면이 사용하는 것은 발행된 배포물입니다. 수정한 서비스를 빌드·발행하고 새 조합에서 선택해야 합니다. 개발 서버는 저장 시 자동 빌드·새로고침을 해주므로 두 환경을 구분해야 합니다.

플랫폼은 서비스 팀들이 함께 쓰는 기반과 책임 범위입니다. 그 플랫폼 팀이 만드는 제품 진입 앱이 Shell이고, 서비스들이 사용하는 공통 코드가 SDK입니다. 플랫폼을 Shell과 같은 단일 프로그램 이름으로 사용하지 않습니다.

Shell이 OTA 페이지를 가져와 표시합니다. OTA가 차량 선택 위젯을 가져온다면 OTA도 소비자입니다. 다른 모듈을 가져오는 곳을 전부 Shell이라고 부르지는 않습니다. Host/Consumer는 연결에서의 역할이고, Shell은 제품의 공통 진입·구성을 맡는 역할입니다. 하나의 서비스는 Remote이면서 다른 Remote의 Host가 될 수 있습니다.

사용자공개된 선택지 안에서 개인 구독 선택20번의 subscription-console

운영 헤더·사이드바는 Shell이 한 번 그립니다. 서비스는 콘텐츠를 공개합니다. 단독 개발 때는 개발 Host가 SDK의 DevLayout으로 주변 틀을 보여주며, PageContainer는 제목·여백 같은 콘텐츠 규칙을 담당합니다. PageContainer를 서비스에서 직접 사용하면 개발 Host가 다시 감싸지 않도록 설정합니다.

대시보드는 누구의 것인가

이 구현에서는 대시보드의 배치 영역이 Shell에 있습니다. 관리자가 어떤 공개 위젯을 놓을지 정하고, 각 서비스가 위젯의 내용을 만듭니다. 대시보드를 별도 서비스로 만드는 설계도 가능하지만, 이 책에서 설명하는 현재 구현은 Shell의 조합 영역입니다.

nginx 라우팅 자체가 MF는 아닙니다. URL별 앱도 팀별 독립 개발이라는 MFE 구조를 구성할 수 있습니다. MFE는 조직·화면의 분할 방식이고 MF는 코드 연결 기술 중 하나입니다. 여러 통합 방식에 대한 설명에서도 빌드 시점 통합과 런타임 통합을 구분합니다.

확인: A가 C를 가져오면 A도 Shell인가요?

A는 C의 Host/Consumer입니다. 제품의 공통 진입점과 전체 레이아웃을 담당하지 않는 한, 그 이유만으로 Shell이라고 부르지 않습니다. 이 프로젝트의 Shell은 별도 앱입니다.

3. 소스 import는 같아 보여도 가져오는 시점이 다릅니다

MF(Module Federation)는 별도 빌드에서 공개한 모듈을 실행할 때 가져오도록 연결합니다. B가 ./Widget을 공개하고 A가 b/Widget을 사용하면, 플랫폼의 로더가 A의 별칭 b에 해당하는 정확한 B 배포물을 찾습니다.

  1. 공개: B가 mf.config.cjs의 exposes에 Widget을 선언합니다.
  2. 요구: A가 mf.dependencies.json에 B와 지원 범위를 선언합니다.
  3. 선택: 플랫폼이 조합에 A.b → 특정 B 배포 ID를 저장합니다.
  4. 부팅: 새 탭이 조합을 한 번 받아 고정합니다.
  5. 로딩: 필요한 순간 B의 remoteEntry.js와 실행 청크를 가져와 공개 모듈을 실행합니다.

remoteEntry.js는 원격 빌드의 공개 모듈에 접근할 입구입니다. 이것 하나에 모든 코드가 들어 있다는 뜻은 아닙니다. 입구를 읽은 뒤 다른 청크가 필요할 수 있어서, 구버전 entry만 남기고 청크를 지우면 기존 탭이 실패할 수 있습니다. MF container는 모듈을 제공하는 실행 단위이며 Docker 컨테이너와 다릅니다. Webpack의 원격 모듈 설명을 근거로 한 구분입니다.

B 구현을 npm 패키지로 설치해 A 번들에 포함A를 빌드할 때새 구현을 포함하려면 A 재빌드 필요
MF이지만 B의 정확한 배포물을 A 빌드 설정에 고정B 선택은 A 빌드 때, B 파일 로딩은 실행 때선택을 바꾸려면 A 재빌드 필요 — 예제 01
MF + 런타임 바인딩플랫폼 조합을 선택할 때호환 범위 안이면 A 재빌드 없이 B 선택 변경 — 예제 03
MF라고 자동으로 런타임 버전 선택이 생기는 것은 아닙니다.

스크립트를 가져올 수 있는 것과 어떤 버전을 가져올지 중앙에서 바꿀 수 있는 것은 다른 기능입니다. 조합·검증·등록부·운영 화면은 이 프로젝트가 MF 위에 추가한 구현입니다.

npm을 전혀 쓰지 않는 구조도 아닙니다. React와 빌드 도구는 npm으로 설치하고, SDK 구현과 업무 Remote는 MF로 가져옵니다. 타입이나 빌드 도구를 npm으로 공급하는 것과 런타임 SDK 구현을 npm 번들에 넣는 것도 구분합니다.

그럼 Shell 자체는 누가 가져오나요? 이 구현의 Shell은 조합이 고른 진입 앱입니다. 서버가 해당 조합의 HTML과 Shell 실행 파일을 연결해 주고, 시작한 Shell이 SDK·서비스 Remote를 가져옵니다. Shell을 npm으로 서비스에 설치하지는 않지만, 모든 Shell이 다른 Host가 가져오는 MF Remote여야 하는 것도 아닙니다. 실제 설정에서 Shell은 kind: 'shell', SDK는 kind: 'remote'입니다.

확인: SDK를 MF로 바꾸면 모든 서비스가 매번 새 SDK를 자동으로 쓰나요?

아닙니다. SDK 발행 후 새 조합에서 선택해야 합니다. 이미 열린 탭은 기존 SDK를 유지합니다. 새 SDK API를 처음 사용하는 서비스는 해당 코드를 빌드하고 지원 범위도 갱신해야 합니다.

SemVer의 기본 의미는 major=비호환 API 변경, minor=호환 기능 추가, patch=호환 버그 수정입니다. 이것은 공급자의 약속을 표현하는 규칙이지 코드의 호환성을 증명하는 장치가 아닙니다. SemVer 명세를 참고하세요. 이 등록부는 같은 의미 버전의 다른 빌드 ID를 구별할 수 있지만, 운영 릴리스는 내용을 바꾸면 새 버전을 발행하고 이미 발행한 파일은 덮어쓰지 않는 편이 명확합니다.

5. B를 하나 고르는 것이 아니라, 누가 쓰는 B인지 구분합니다

한 탭 · 공통 SDK 하나
└─ A
   ├─ b → B 1.4 → d → D 1.0
   └─ c → C 1.1
           └─ b → B 2.1 → d → D 2.0

중첩 사례에서도 A가 직접 쓰는 B는 1.4이고 C가 쓰는 B는 2.1입니다. C는 A의 B 선택을 물려받지 않습니다. 등록부는 소비자 배포 ID + 별칭으로 대상 배포물을 찾습니다.

// 의미를 보여주는 축약 표기입니다. 실제 ID·필수 필드를 생략했습니다.
runtimeBindings = {
  A배포ID: { b: B_1_4배포ID, c: C_1_1배포ID },
  C_1_1배포ID: { b: B_2_1배포ID },
  B_1_4배포ID: { d: D_1_0배포ID },
  B_2_1배포ID: { d: D_2_0배포ID }
}
현재 모델의 경계

같은 조합 안에서 동일한 C 배포물을 두 번 표시하면 C→B 선택은 같습니다. 상태는 인스턴스별로 나뉩니다. 동일한 소비자 배포물의 같은 별칭을 부모 경로마다 다르게 고르는 기능은 현재 구현하지 않았습니다. 사용자별로 서로 다른 조합을 만드는 20번과도 구분하세요.

도구가 이름을 생성하고 잘못된 버전 범위·순환을 거절하도록 할 수 있습니다. 그러나 “금액의 단위를 원에서 달러로 바꿨다” 같은 의미 변경이나 임의의 전역 부작용까지 범위 선언만으로 알아내지 못합니다. 공개 계약 검증과 소비자 사용 경로 테스트가 함께 필요합니다.

MF 자체는 중첩과 순환 연결을 표현할 수 있습니다. 이 프로젝트는 추적·선택·삭제를 단순하게 하기 위해 순환을 조합 검사에서 거절합니다. 순환이 생기면 공통 부분을 하위 모듈로 추출하거나 상위 화면이 두 기능을 조정하도록 경계를 다시 잡습니다. 두 팀이 항상 동시에 바뀌고 공유 상태가 많다면 같은 배포 단위로 묶는 선택도 검토합니다.

exposes는 공개 코드의 목록이고 widgets는 그중 대시보드에 배치해도 되는 모듈의 목록입니다. platform-widget-v1은 이 프로젝트가 정한 위젯 공통 계약 이름이며 MF 표준 계약 이름은 아닙니다.

위젯은 props를 받으면 안 되는가

독립 위젯의 목표는 대시보드가 위젯별 업무 데이터를 전부 준비하지 않게 하는 것입니다. 사용자는 SDK Context로 받고, 자기 업무 데이터는 위젯이 API로 조회합니다. 플랫폼이 넘기는 instanceId 같은 공통 실행 정보는 받을 수 있습니다. 이 대시보드의 공통 위젯 계약은 위젯마다 다른 업무 props를 요구하지 않습니다.

OTA 화면에 넣는 차량 선택 컴포넌트처럼 선택값이나 콜백이 필수인 경우에는 그 UI 모듈의 별도 공개 계약에 포함할 수 있습니다. 자동 등록 대시보드에 놓을 때는 필요한 설정·정보를 스스로 구할 수 있는 어댑터 위젯을 공개하는 방식으로 경계를 맞춥니다. “모든 서비스의 모든 props를 금지한다”는 규칙은 아닙니다.

현재 로컬 구현은 종료 계획·공지 기록과 삭제 조건을 관리합니다. 이메일·메신저 발송 성공까지 구현하지 않았습니다. 운영 확장안은 계획 저장과 함께 알림 작업을 저장하고 전송·재시도·실패 대기열·기한별 재알림을 처리하는 것입니다. “공지 기록이 있음”과 “실제로 전달됨”을 구분해야 합니다.

10. Alice의 변경이 Bob과 기존 탭을 바꾸지 않게 하기

20번은 공개된 기본 조합과 위젯 버전을 사용자가 선택해 저장하는 독립 예제입니다. Alice·Bob·Carol은 서로 다른 구독 레코드를 가집니다. 같은 화면 안의 SDK는 하나라는 규칙은 유지합니다.

Alice 구독 → 조합 X → 새 Alice 탭
  ├─ 기본 조합의 Shell / SDK / A / C / B / D
  └─ 개인 위젯 B 1.5 + B 2.1

Bob 구독   → 조합 Y → Bob 탭
Carol 구독 → 조합 Z → 아직 한 번도 화면을 열지 않아도 보호

기존 Alice 탭 → 변경 전 조합 W와 입력 상태 유지

저장 위치는 서버의 subscriptions.json입니다. 브라우저 localStorage만 보고 사용 여부를 판별하지 않습니다. 구독에는 선택한 기본 조합 ID·정확한 위젯 배포 ID·배치·해결된 전체 조합 ID·revision이 저장됩니다. 개인 저장은 전역 current.json을 변경하지 않습니다.

기본 조합은 A/C와 그 의존성도 포함하므로 현재 대시보드에 보이지 않는 해당 모듈까지 보수적으로 보호합니다. 새 위젯의 하위 D는 플랫폼이 공개한 고정 기본값으로 해결하며, 기본 조합에 이미 있는 배포물의 의존 연결은 그 조합을 따릅니다. 가장 높은 버전을 임의로 선택하지 않습니다.

동일한 조합을 두 사용자가 공유해도 소유 레코드는 따로입니다. 한 명이 해제했다고 다른 사람의 참조가 사라지지 않습니다. 개인의 과거 조합 파일은 감사 기록으로 남길 수 있지만 자동으로 영구 롤백 보호를 만들지는 않습니다. 실제 활성 구독·탭·공용 롤백 참조가 있는지를 따로 봅니다.

직접 비교하는 순서

  1. 예제 20을 실행하고 /subscriptions에서 Alice를 선택합니다.
  2. “현재 운영”과 B 1.4 위젯을 선택 → 조합 검사 → 저장 → 새 대시보드를 엽니다.
  3. 다른 브라우저 프로필 또는 시크릿 창에서 Bob으로 “이전 운영”과 B 2.1을 저장합니다.
  4. Alice를 B 1.5로 바꾼 뒤 새 탭과 기존 탭의 버전·입력 상태를 비교합니다.
  5. Carol은 B 1.4를 저장만 하고 대시보드를 열지 않습니다. 관리 화면의 B와 D 참조에 Carol이 나타나는지 봅니다.

같은 브라우저 프로필의 탭은 로그인 쿠키를 공유합니다. 서로 다른 사람을 동시에 비교하려면 프로필을 분리하세요. 데모 사용자 선택과 세션 바인딩은 구현했지만 실제 SSO·조직 권한·테넌트 보안을 완성한 것은 아닙니다.

확인: Carol이 한 달 동안 접속하지 않으면 Carol의 구독을 탭 만료처럼 정리해도 되나요?

현재 정책에서는 안 됩니다. 활성 구독은 지속되는 선택이고, lease는 특정 탭의 사용 기한입니다. 계정 탈퇴·구독 만료 같은 제품 정책을 추가하려면 별도로 설계하고 사용자 구독을 명시적으로 전환·해제해야 합니다.

11. DB는 선택과 참조를 관리하고, 파일은 저장소에 둡니다

이 장은 설계안입니다.

현재 동작은 로컬 JSON·파일 저장소로 구현되어 있습니다. DB 마이그레이션·S3 업로드·분산 운영을 실행 검증한 결과가 아닙니다. 상세 테이블·DDL·API·장애 처리는 이 문서의 DB 상세 부록에 모두 포함했습니다.

관리 화면 / 서비스 CI→인증된 등록부 API→DB
메타데이터·관계·정책→S3 / CDN
불변 파일·조합

브라우저는 DB에 직접 접속하지 않습니다. 서버가 검증한 조합을 받아 정확한 URL의 파일을 실행합니다. DB로 바꾸어도 한 탭의 고정 조합과 소비자별 연결이라는 규칙은 그대로입니다.

DB 변경과 함께 “외부에서 해야 할 작업”을 기록하고 작업자가 나중에 실행하는 방식입니다. DB 커밋과 S3·알림 성공을 같은 일로 착각하지 않게 합니다.

동시 삭제와 새 구독 저장은 같은 동시성 규칙을 따라야 합니다. 화면용 참조 개수 캐시가 0이라는 이유로 삭제하지 않고, 마지막 변경 단계에서 참조를 재검사합니다. DB 잠금 수단은 PostgreSQL 공식 문서의 기능을 이용할 수 있지만, 어떤 행과 작업을 묶을지는 이 플랫폼의 설계 책임입니다.

DB와 S3 사이에서 실패할 때

  1. 발행 요청을 pending으로 기록하고 파일을 업로드합니다.
  2. 파일 목록·해시·공개 모듈·요구 범위를 검증해 ready로 바꿉니다. ready 전에는 선택하지 않습니다.
  3. 조합을 검사·발행하고 준비가 끝난 뒤 현재 포인터를 바꿉니다.
  4. 삭제도 deleting → 실제 파일 처리 → 완료 확인 → deleted로 나눕니다. 실패하면 중간 상태와 재시도 기록을 유지합니다.

S3 버전 관리에서 단순 DELETE는 삭제 마커를 만들 수 있으므로 실제 버전 파일 제거와 다릅니다. AWS 삭제 마커 설명에 맞춰 파일 버전·CDN·보존 정책을 함께 설계해야 합니다.

이관은 저장 인터페이스 분리 → 기존 ID·파일·조합 적재 → 조회 결과 비교 → 최종 동기화 → 단일 쓰기 기준 전환 순서로 진행하는 안입니다. DB에서 새 구독·lease·삭제 기록이 생긴 후 오래된 JSON으로 단순 복귀하면 안 됩니다.

확인: DB를 도입하면 B 1.4와 B 2.1 충돌도 해결되나요?

DB는 정확한 선택과 사용 관계를 저장합니다. 브라우저의 container·CSS·상태 충돌은 빌드 도구·SDK·서비스 규칙이 해결해야 합니다. 두 책임은 연결되지만 서로를 대체하지 않습니다.

12. 예제에서 확인한 것과 제품에 채택할 것을 구분합니다

예제가 통과했다는 것은 해당 코드와 조건에서 시나리오가 동작했다는 뜻입니다. 실제 인증, 대규모 트래픽, 모든 계약의 의미적 호환성, S3·다중 서버 운영까지 검증했다는 뜻은 아닙니다. 제품 아키텍처 문서는 아래 결정과 그 전제를 명시하면 됩니다.
