Git에서 처음 시작하기: 설치 전에 Vite 사본인지 확인

먼저 Git, Node.js 22.12 이상, npm, 인터넷 연결과 일반 브라우저를 준비합니다. 아래 명령이 각각 버전을 출력하는지 확인하세요. 준비 검사는 별도 npm 패키지 없이 Node·Git·tar를 사용하므로 의존성을 설치하기 전에 실행할 수 있습니다.

git --version
node -v
npm -v

새 폴더를 만들 수 있는 위치에서 시작합니다. clone이 성공하면 내려받은 폴더로 이동해 정확한 커밋을 기록하고, Vite 학습서에 필요한 파일이 그 커밋에 포함됐는지 검사합니다.

git clone https://github.com/Jong-Yu/mfe-platform.git
cd mfe-platform
git rev-parse HEAD

Node 24가 컴퓨터에 설치되어 있는 것과 지금 터미널에서 선택되어 있는 것은 다릅니다. 최상위 .nvmrc의 값은 24이지만, 파일이 있다는 이유만으로 모든 터미널이 자동 전환되지는 않습니다. clone한 폴더에 들어온 뒤 현재 터미널의 Node 버전을 다시 확인합니다.

nvm을 사용하는 경우: 이 폴더에서 Node 24 선택

nvm을 이미 사용하는 사람은 clone한 프로젝트 최상위에서 다음 명령을 실행합니다. nvm install은 .nvmrc의 버전이 없으면 설치하고, nvm use는 현재 터미널에서 그 버전을 선택합니다.

nvm install
nvm use
node -v
npm -v

이 학습서의 실제 재실행은 이미 설치되어 있던 Node 24를 선택했습니다. 새 Node 설치 과정 자체를 검증했다는 뜻은 아닙니다.

nvm을 사용하지 않는다면 현재 사용하는 Node 관리 도구나 설치 방식으로 호환 버전을 선택하세요. 환경 경로를 바꿨다면 터미널을 다시 열고 clone한 폴더로 돌아옵니다. nvm 설치가 필수인 것은 아닙니다. 어느 방식을 쓰든 명령을 실행할 바로 그 터미널에서 아래 결과를 확인합니다.

node -v
npm -v

Node가 v24... 등 요구 조건인 22.12 이상이고 npm도 오류 없이 버전을 출력하면 준비 검사를 실행합니다. Node 16처럼 오래된 버전이 나오거나 npm이 Node 버전 불일치 오류를 내면 먼저 현재 선택을 고치세요.

node integration/tools/check-clone.cjs --git

설치 전 준비 검사는 현재 Vite 패키지 선언과 잠금 파일, vendor tarball, 개발 매니페스트가 참조하는 파일과 해시, 학습서의 Vite 본문을 확인합니다. --git은 필요한 파일 내용이 실제 HEAD에 포함됐는지도 확인합니다. 검사가 성공한 뒤에만 아래의 npm 설치로 진행하세요.

검사 파일이 없거나 Webpack 버전이라고 나오면 여기서 멈춥니다.

받은 커밋이 다른 버전이거나 Vite 전환 내용이 원격에 아직 반영되지 않은 상태일 수 있습니다. git rev-parse HEAD 결과를 clone 확인 기록과 비교하세요. 빌드 도구 1.7.x 등 이전 Webpack 프로젝트에서 npm ci가 성공해도 이 Vite 학습서의 준비가 완료된 것은 아닙니다. 로컬의 새 파일을 추가한 사본은 원격에서 받은 그대로의 사본과 구분해서 검증합니다.

선택: 이미 제공받은 현재 소스 사본에서 시작하는 경우

실습용 복사본에서 진행하면 평소 사용하던 소스·버전 선택·발행 저장소를 보존할 수 있습니다. projects/와 integration/의 소스·설정·잠금 파일, 각 서비스의 vendor/와 dev/ 키트, docs/ 학습서도 함께 가져옵니다. 기존 node_modules/, dist/, .mfe-dev/, 루트 artifact-store/, integration/artifacts/는 가져오지 않아도 됩니다.

복사본의 최상위에서 node integration/tools/check-clone.cjs로 파일 구성을 확인합니다. Git 이력이 없는 파일 사본에는 --git을 붙이지 않습니다. 이 경로는 제공받은 파일을 검증하는 것이며 원격 clone 결과를 증명하지 않습니다. 이후 명령은 이 실습용 사본의 최상위에서 이어갑니다.

개발에 필요한 파일과 실행 위치

실제 실행 검증에서는 이미 설치된 Node 24.22.1과 Chrome 157.0.8103.39, macOS를 사용했습니다. Node 설치 자체나 다른 운영체제를 확인한 결과는 아닙니다. 처음 패키지를 내려받을 인터넷 연결도 필요합니다.

vendor/mfe-platform-build-tools-2.0.0.tgz는 프로젝트가 함께 제공하는 빌드 도구 패키지이고, dev/manifest.json과 dev/remotes/는 발행된 SDK·D 등을 담은 개발 키트입니다. 이들은 npm 캐시가 아니라 실습에 필요한 제공 파일입니다. npm 캐시가 비어 있어도 이 파일은 갖고 시작합니다. vendor 파일을 찾지 못하는 오류나 개발 키트 파일·해시 오류가 나면 현재 Vite용 파일을 포함한 완전한 사본인지 먼저 확인하세요. npm ci가 누락된 vendor 패키지나 개발 키트를 새로 만들어 주지는 않습니다.

처음 npm ci는 잠금 파일에 기록된 외부 패키지를 npm 레지스트리에서 내려받습니다. 인터넷 연결과 레지스트리 접근이 필요하며, 아직 캐시를 채우지 않았다면 --offline으로 시작하지 않습니다. 빌드 도구는 devDependencies에 있고 플랫폼별 실행 바이너리는 optional dependencies로 설치되므로, 이 개발 실습에서는 NODE_ENV=production이나 --omit=dev·--omit=optional로 의존성을 제외하지 마세요. 그런 설정을 사용하던 터미널이라면 먼저 해제하고 정상 설치를 진행합니다.

본문을 따라 직접 버튼을 누르는 실습에는 일반 브라우저면 됩니다. Playwright는 V8의 자동 검증 스크립트를 실행할 때 필요한 별도 도구입니다. 단독 개발 검사 스크립트는 기존 integration의 Playwright를 관찰용으로 사용하고, 배포·버전 교체 검사는 복사본의 integration에 Playwright를 새로 설치합니다. 이 도구와 별개로 B 서비스 자체는 일반 브라우저에서 실행됩니다.

선택: 기존 캐시를 건드리지 않고 빈 캐시에서 처음 설치하기

macOS/Linux 터미널에서 아래 명령을 한 번 실행하면 새 임시 캐시가 생깁니다. 기존 npm 캐시를 지우거나 덮어쓰지 않습니다. 같은 터미널에서 이어지는 V5~V7의 설치·빌드·검증 명령은 이 경로를 사용합니다.

MFE_STUDY_CACHE=$(mktemp -d /tmp/mfe-study-cache.XXXXXX)
export npm_config_cache="$MFE_STUDY_CACHE"
export MFE_NPM_CACHE="$MFE_STUDY_CACHE"
export NPM_CACHE="$MFE_STUDY_CACHE"
printf '%s\n' "$MFE_STUDY_CACHE"

npm_config_cache는 일반 npm 명령, MFE_NPM_CACHE는 통합 setup, NPM_CACHE는 일부 자동 검증이 읽는 이름입니다. 모두 같은 새 경로를 지정합니다. 첫 설치에는 온라인 접근을 허용하고, MFE_OFFLINE=1이나 npm의 offline 설정을 켜지 않습니다. 새 터미널을 열었다면 출력해 둔 경로로 이 세 변수를 다시 지정하세요. mktemp를 다시 실행하면 다른 빈 캐시가 만들어집니다.

첫 설치가 끝난 뒤 다른 서비스나 SDK·D의 임시 복사본을 설치할 때에는 이번 실행에서 채운 같은 캐시를 재사용할 수 있습니다. 캐시를 재사용하는 것과 네트워크를 차단하는 --offline은 별개입니다. 오프라인 검사는 그 검사에 필요한 패키지가 모두 채워진 뒤에 실행합니다. 아래의 빈 캐시 검증은 여기에 더해 별도의 빈 npm 설정 파일과 공식 레지스트리를 사용하고 실제 다운로드 로그를 기록합니다.

프로젝트 최상위에는 모든 서비스를 함께 설치하는 npm workspace가 없습니다. projects/service-b-v1처럼 해당 서비스 폴더에 들어가 그 폴더의 잠금 파일로 설치합니다. 아래는 실습용 복사본의 최상위에서 시작하는 macOS/Linux 예입니다.

cd projects/service-b-v1
npm ci
npm run dev

npm ci는 package-lock.json에 기록된 의존성을 설치합니다. npm run dev는 해당 프로젝트가 설치한 mfe-dev를 실행합니다. 터미널에 Service Dev Host: http://127.0.0.1:4203/가 나오면 그 주소를 엽니다. 서버는 종료하지 않고 켜 둡니다. 포트가 사용 중이면 PORT=4303 npm run dev처럼 다른 번호를 지정하고 그 주소로 접속합니다.

이 B 프로젝트의 개발 Host는 SDK가 제공하는 PlatformProvider·DevLayout·PageContainer 안에 B의 ./Widget을 렌더링합니다. 사용자·테마는 mf.dev.json에 적힌 개발용 값입니다. 제품의 인증 서버에 로그인한 결과를 자동으로 가져오는 기능은 아닙니다.

파일누가 준비하나개발할 때의 의미
src/Widget.jsx, src/Widget.module.cssB 팀지금 수정하고 빌드하는 업무 UI와 스타일
mf.config.cjsB 팀과 공통 규칙논리 서비스명, 공개 모듈, 개발 포트

저장한 내용이 화면에 나타나는 순서

  1. mfe-dev가 개발 키트의 해시·의존 관계·SDK/React 호환성과 공개 모듈을 확인합니다.
  2. 현재 B 소스를 Vite로 빌드하고 .mfe-dev/builds/<배포 ID>/에 둡니다. 개발 Host도 별도로 준비합니다.
  3. 개발용 조합을 만듭니다. 그 조합은 방금 만든 B와 키트에 고정한 SDK·D를 연결합니다.
  4. 브라우저가 이 개발 조합을 읽고 SDK를 준비한 뒤 B를 마운트합니다. 외부 서비스 서버 대신 같은 개발 서버가 키트의 파일도 제공합니다.
  5. 소스·MF 설정·개발 설정·키트 매니페스트의 변경을 감지하면 재빌드를 순서대로 처리합니다. 성공 알림의 개발 조합 ID가 현재 화면과 다르면 브라우저가 전체 화면을 새로고침합니다. 이 ID에는 현재 서비스뿐 아니라 개발 설정과 키트의 연결도 반영됩니다.
Vite를 사용하지만, 이 개발 명령은 현재 전체 새로고침 방식입니다.

HMR이나 React Fast Refresh로 입력 상태를 보존하는 구현이 아닙니다. 변경한 소스·개발 설정·키트로 새 개발 조합이 만들어지면 화면이 새로고침되고 버튼 횟수와 입력값이 초기화됩니다. 후속 빌드가 실패하면 마지막 성공 화면에 오류를 표시합니다. 오류만 지워 직전 성공 소스로 돌아가고 다른 설정도 그대로라면 같은 조합을 재사용해 오류 안내만 사라질 수 있습니다. 처음 빌드부터 실패했다면 정상 개발 화면은 아직 없습니다. package.json·잠금 파일·설치 의존성을 바꾸면 설치를 정리한 뒤 개발 서버를 다시 시작합니다.

// 변경 전
<h2>Car Picker</h2>

선택 실습: 문법 오류가 나도 마지막 성공 화면이 남는지 확인

새 제목이 보이는 상태에서 카운터를 한 번 누르고 오류 중에도 유지할 메모를 저장합니다. 같은 소스의 마지막 줄에 임시로 const broken = ;를 넣어 저장하면, ‘빌드 오류 — 마지막 성공 화면을 유지합니다.’라는 안내와 오류 위치가 표시됩니다. 이때 기존 카운터·입력·캐시는 남아 있습니다. 오류 상세에 색상 제어 문자가 함께 보일 수 있지만 파일 위치와 오류 메시지를 기준으로 수정합니다.

방금 넣은 줄을 지워 직전 성공 소스와 완전히 같게 복구하고 개발 설정·키트도 바꾸지 않았다면, 같은 개발 조합을 다시 쓰므로 오류 안내만 사라지고 기존 상태가 유지됩니다. 성공한 소스를 새 내용으로 바꾸거나 개발 설정·키트를 바꿔 조합 ID가 달라지면 전체 새로고침과 상태 초기화가 일어납니다. ‘저장할 때마다 무조건 초기화’로 해석하지 마세요.

JSX가 들어 있는 파일은 .jsx 또는 .tsx를 사용합니다. Vite가 JavaScript·TypeScript를 실행 파일로 변환하지만, TypeScript의 타입 검사는 별도입니다. 현재 서비스의 npm run build만 성공했다고 타입 검사까지 통과한 것으로 해석하지 않습니다. 타입 검사를 도입한 서비스는 자체 TypeScript 설정과 검사 명령을 함께 관리해야 합니다.

개발 키트와 제품 조합은 언제 달라지나

개발 키트는 내 개발 환경에서 재현할 조합을 고정합니다. 제품 관리 화면에서 SDK나 D를 교체해도 이미 전달한 dev/manifest.json이 자동으로 따라 바뀌지는 않습니다. 반대로 키트를 갱신해도 제품의 current.json이 바뀌지는 않습니다. 제품 반영과 개발 환경 갱신은 서로 다른 작업입니다.

플랫폼 담당자는 발행된 조합을 준비한 뒤 integration에서 npm run prepare:dev를 실행해 A·C·두 B의 키트를 갱신할 수 있습니다. 현재 제품이 선택한 SDK와 B/D 연결을 사용하며 서비스 자체를 빌드하지 않습니다. 특정 SDK를 쓰려면 npm run prepare:dev -- SDK_ARTIFACT_ID의 마지막 값을 실제 발행 ID로 바꿉니다. 이 명령은 네 서비스의 개발 키트를 수정하므로, 팀에 전달하려는 버전인지 확인하고 실행합니다. 대상 SDK는 개발 레이아웃을 제공하는 호환 버전이어야 합니다.

npm start도 개발 화면 명령과 구분합니다. B 폴더의 npm start는 이미 만든 dist/ 파일을 제공하는 미리보기 서버입니다. B의 업무 화면을 감싸는 Host를 자동 생성하지 않습니다. B 화면 자체를 수정·확인할 때는 npm run dev를 사용합니다.

1. 전체 실행 환경을 처음 준비하는 경우

현재 통합 프로젝트의 기본 실행 명령은 다음과 같습니다. 프로젝트 최상위에서 시작하고, 각 명령이 성공한 뒤 다음 줄로 이동합니다. 이미 발행 저장소와 실행 서버가 있다면 매번 다시 할 필요는 없습니다.

cd integration
npm ci
npm run setup
npm run build
npm start

npm ci는 통합 도구의 의존성을 설치합니다. setup은 각 projects/*에서 개별 잠금 파일로 설치합니다. build는 서비스들을 각각 빌드·발행하고 Shell·A·C를 그 결과로 선택하는 통합 편의 명령이며 관리 앱도 준비합니다. 기존 SDK·소비자별 B·D 선택을 보존하는 코드가 들어 있지만, 발행과 조합 활성화까지 수행하므로 단순한 읽기 전용 빌드 검사는 아닙니다. 서비스 하나를 출시하려면 아래의 개별 빌드·발행 절차가 더 명확합니다.

npm start가 출력하는 주소를 엽니다. 기본값은 http://127.0.0.1:4173/이며 관리 화면은 /admin입니다. 대시보드가 설정된 조합에서 A/C 검증 화면을 보려면 /#/verification을 사용합니다. 서버 실행 터미널은 켜 두고, 다음 변경 명령은 두 번째 터미널에서 수행합니다. 두 번째 터미널도 프로젝트 최상위에서 node -v·npm -v를 확인하고, 필요하면 자신의 관리 도구로 Node 24를 선택한 뒤 진행하세요.

처음 실행한 정상 화면: 현재 제공된 설정으로 빈 저장소를 빌드하면 /에 ‘다른 버전, 하나의 플랫폼’과 A·C 카드가 자동으로 나타납니다. A 안에는 B 1.4.0과 D 1.0.0, C 안에는 B 2.1.0과 D 2.0.0이 보이고 SDK 1.3.1을 공유합니다. ‘등록 서비스 메뉴 0개’와 아직 배치가 없는 대시보드는 정상입니다. 기존 조합을 가져왔다면 선택 버전과 배치가 다를 수 있으므로 왼쪽 버전 공존 검증 메뉴로 이동해 실제 선택값을 먼저 확인합니다.

4173 포트를 다른 서버가 사용 중이면 그 서버를 임의로 종료하지 말고 PORT=4273 npm start로 복사본을 실행하세요. 이후 제품·관리 화면 주소도 모두 http://127.0.0.1:4273으로 바꿉니다.

bootstrap은 언제 필요한가

현재 제공된 소스와 설정으로 빈 발행 저장소를 시작할 때는 위의 npm run build만으로 기본 조합이 만들어집니다. npm run bootstrap은 의존 설정 자체를 fixture 기준으로 다시 작성하고 전체 새 배포물을 선택하려는 경우에 사용하는 명령입니다. 기존 선택과 자체 의존 선언을 유지하는 일상 빌드 절차에 넣지 않습니다. Webpack에서 Vite ESM으로 최초 전환할 때도 Host를 포함한 전체 구성을 준비해야 하며, 이전 Host에 Vite Remote만 교체하는 절차가 아닙니다.

2. B만 변경·빌드·발행하기

cd projects/service-b-v1

npm version patch는 package.json과 잠금 파일의 릴리스 버전을 올립니다. 기본 1.4.0에서 실행하면 1.4.1이 됩니다. --no-git-tag-version은 Git 커밋·태그를 만들지 않도록 합니다. 이미 발표한 같은 버전의 파일을 바꾸기보다 새 버전으로 기록하는 흐름입니다. 빌드가 끝나면 B의 dist/release.json에서 실제 배포 ID를 확인할 수 있습니다.

발행 직후 확인: 여기서 새 브라우저 탭을 열어도 아직 A의 B는 이전 제목·버전입니다. ‘빌드가 안 됐다’고 판단하지 말고 다음 선택 단계로 넘어가세요. dist/release.json의 새 B ID와 현재 조합이 A에 연결한 B ID는 이 시점에 서로 다릅니다.

3. A가 새 B를 선택하도록 적용하기

관리 화면에서는 A가 사용할 B와 그 B가 사용할 D를 함께 선택하고 ‘조합 검사’ → ‘변경 적용’ 순서로 진행합니다. 새 B는 이전 B와 다른 배포 ID이므로 runtimeBindings[새 B ID].d 연결도 필요합니다. 버전 번호만 비슷하다는 이유로 이전 B의 연결이 자동 상속되지는 않습니다.

아래는 같은 일을 CLI로 실행하는 절차입니다. 앞 단계에 이어 같은 integration 폴더·같은 터미널에서 실행합니다. 임의의 ID를 복사하지 않고, 현재 조합과 방금 빌드한 release.json에서 값을 읽습니다. CLI 실습 중에는 다른 관리 창에서 같은 저장소의 선택을 동시에 바꾸지 않습니다.

MFE_DEMO_PREVIOUS=$(node -p 'require("./tools/store.cjs").current().compositionId')
MFE_DEMO_A=$(node -p 'require("./tools/store.cjs").current().selected.A')
MFE_DEMO_D=$(node -p 'const c=require("./tools/store.cjs").current(); c.runtimeBindings[c.runtimeBindings[c.selected.A].b].d')
MFE_DEMO_NEW_B=$(node -p 'require("../projects/service-b-v1/dist/release.json").id')

npm run activate -- --bind "${MFE_DEMO_A}:b=${MFE_DEMO_NEW_B}" --bind "${MFE_DEMO_NEW_B}:d=${MFE_DEMO_D}"

첫 줄은 나중에 돌아갈 조합 ID, 둘째 줄은 A의 정확한 배포 ID를 저장합니다. 셋째 줄은 A가 현재 쓰는 B의 D를 읽어 새 B에서도 유지합니다. 넷째 줄은 방금 발행한 B의 ID입니다. 마지막 명령은 A→새 B와 새 B→기존 D 두 연결을 함께 검증·활성화합니다. 새 B가 기존 D를 허용하지 않으면 적용이 거절되며, 호환되는 D를 선택해야 합니다.

롤백할 때까지 이 터미널을 유지하세요. 위 변수는 현재 셸에만 남으며 export는 필요 없습니다. printf '%s\n' "$MFE_DEMO_PREVIOUS"로 이전 조합 ID를 출력해 따로 기록해 두세요. 터미널을 닫았다면 기록한 실제 ID를 npm run activate -- --composition 기록한_ID에 넣습니다. 새 조합으로 바꾼 뒤 current에서 다시 읽으면 돌아갈 이전 ID가 아니라 새 ID가 나오므로 주의합니다.

CLI activate는 내부 검증 후 바로 적용합니다. 관리 UI의 ‘검사’는 미리보기이며 적용 전까지 현재 포인터를 바꾸지 않습니다. 관리 UI는 검사 당시의 현재 조합과 검사한 대상 조합을 적용 직전 다시 비교해서 중간 변경을 거절합니다. 여러 운영자가 함께 작업하는 절차에는 이 차이를 고려해야 합니다.
