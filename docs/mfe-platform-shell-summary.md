공통 헤더와 사이드바를 사용하는 여러 서비스를 독립적으로 개발·배포하고, 대시보드에서는 서비스가 공개한 위젯을 조합한다. 이 요구를 기준으로 플랫폼, Shell, 공통 SDK의 역할과 두 가지 화면 구성 방식을 정리한다.

**공통 실행 코드는 MF로 제공하는 방향이다. 단일 Shell을 사용할지, URL별 독립 앱으로 구성할지는 아직 선택하지 않았다.**

## 1. 현재까지 확인한 요구와 미결정 사항

| 구분 | 내용 |
|---|---|
| 공통 화면 | 서비스들이 공통 헤더와 사이드바를 사용한다. |
| 독립 배포 | 서비스별로 빌드하고, S3 같은 외부 저장소에 버전별로 배포한다. |
| 공통 기반 | 플랫폼팀이 공통 UI, 개발용 Layout, Container, Provider 같은 기능을 제공한다. |
| 공통 코드 전달 | 브라우저에서 사용하는 공통 코드는 MF로 가져오는 방향이다. |
| 대시보드 | 각 서비스가 계약을 통해 공개한 위젯을 선택해서 표시한다. |
| 위젯 계약 원칙 | 대시보드는 위젯별 업무 입력을 알지 않는다. 공통 실행 계약 안에서 만든 새 위젯은 대시보드 코드 변경 없이 추가한다. |
| 의존성과 사용 추적 | 각 위젯이 사용하는 서비스·SDK의 필요 버전과 계약 정보를 배포 시 등록하고, 플랫폼이 의존 관계와 실제 사용을 추적한다. |
| 지원 종료와 파일 삭제 | 업그레이드만으로 구버전을 즉시 제거하지 않는다. 알림·유예 기간·지원 대상 확인을 거쳐 지원을 종료하고, 저장소 파일 삭제는 별도로 판단한다. |
| 미결정 | 단일 Shell에서 서비스 페이지를 조합할지, Nginx가 URL별 독립 앱으로 연결할지 선택해야 한다. |
| 후속 설계 | 위젯 계약과 버전 추적·지원 종료의 원칙은 정리했다. 구체적인 API·타입과 구현, 복수 버전의 선택·공존 방식, 자동 검증 방법, 알림 방식과 기간 값, 빌드 도구 전달 방식은 별도로 정한다. |

## 2. 플랫폼과 Shell과 SDK의 관계

이 문서에서는 다음 의미로 용어를 고정한다.

| 용어 | 의미 | 책임 |
|---|---|---|
| 플랫폼 | 여러 서비스에 제공하는 공통 기반 전체 | 공통 실행 환경, UI, 개발 도구, 연결 규칙 등을 제공 |
| Shell | 서비스 페이지를 담아 실행하는 바깥쪽 앱 | 공통 헤더·사이드바를 유지하고 서비스 페이지를 로드 |
| 공통 SDK | 서비스 개발·실행에 사용하는 공통 코드와 인터페이스의 묶음 | Layout, Container, Provider, Hook, 개발 도구 등을 제공 |
| 서비스 | 업무 페이지와 공개 위젯을 구현하는 단위 | 주문·고객 같은 업무 화면과 동작을 소유 |
| 대시보드 | 공개된 위젯을 선택하고 배치하는 화면 | 위젯 발견·로딩·배치와 표준화된 공통 입력 전달을 담당 |

플랫폼이라는 이름의 실행 앱이 추가로 생기는 것은 아니다. 단일 Shell을 채택한다면 플랫폼팀의 제공물은 다음처럼 구분된다.

    플랫폼팀이 제공하는 공통 기반
    ├ Shell 앱
    │  └ 사용자에게 보여줄 공통 틀과 서비스 페이지 로딩
    └ 공통 SDK
       └ 서비스 개발·실행에 필요한 공통 모듈과 도구

Shell과 SDK는 역할과 배포 산출물을 구분한 것이다. 이 구분만으로 저장소나 팀을 각각 분리해야 하는 것은 아니다.

MFE는 마이크로프런트엔드라는 아키텍처를, MF는 Module Federation이라는 모듈 공유 기술을 뜻한다. Shell의 존재 여부와 MF 사용 여부는 별개의 항목이다.

## 3. 공통 SDK를 MF로 전달하는 방식

**SDK는 기능의 묶음을 뜻하며, npm 패키지라는 뜻으로 한정하지 않는다.** 여기서는 공통 실행 모듈을 MF로 공개하고 Shell이나 서비스가 가져와 사용한다.

| 제공할 것 | 사용 시점과 방식 |
|---|---|
| 헤더·사이드바 | 화면을 구성하는 앱이 MF로 가져와 렌더링 |
| ContentContainer | 서비스 페이지·위젯이 MF로 가져와 공통 여백과 콘텐츠 영역 규칙을 적용 |
| 개발용 Layout | 서비스의 로컬 개발 화면에서 MF로 가져와 미리보기 환경을 구성 |
| 공통 Provider와 Hook | 실행 중 사용자·테마·플랫폼 기능 등의 값을 전달하고 사용 |
| MF 연결·빌드·배포 도구 | 개발·빌드·배포 단계에 필요. 프로젝트 템플릿이나 공통 CI 설정 등으로 제공할 수 있으며, 구체 방식은 미결정 |

MF는 공개할 모듈을 exposes 설정으로 지정하고, 소비하는 쪽에서 원격 모듈을 로드하는 기능을 제공한다. [MF 모듈 공개 설정](https://module-federation.io/configure/exposes.html), [MF 런타임 로딩](https://module-federation.io/guide/runtime/)

개발용 Layout은 로컬 미리보기를 위한 진입점에서 사용한다. 단일 Shell에 넣을 운영 페이지·위젯에 개발용 글로벌 헤더와 사이드바가 함께 포함되지 않도록 진입점을 구분한다.

React Provider는 실행 중 값을 전달하는 컴포넌트다. 위젯을 MF로 공개하거나 파일을 S3에 업로드하는 도구와는 역할이 다르다.

| 실행 환경 | 공통 Provider에 실제 값을 공급하는 주체 |
|---|---|
| 단일 Shell 구성의 운영 환경 | Shell |
| URL별 독립 앱 구성의 운영 환경 | 해당 서비스 앱의 공통 초기화 코드 |
| 로컬 개발 환경 | 개발용 Layout의 테스트 설정 |

Provider와 Hook가 같은 Context를 사용하려면 동일한 Context 인스턴스로 연결되어야 한다. 동일한 버전 번호만 맞추는 것으로 충분하지 않으며, 공통 모듈의 로딩·공유 설정도 맞춰야 한다. [React Context의 동일 인스턴스 조건](https://react.dev/reference/react/useContext#caveats)

## 4. 구성안 A 단일 Shell이 서비스 페이지를 조합

    사용자 브라우저
    └ Shell 앱
       ├ 공통 헤더
       ├ 공통 사이드바
       └ 주소에 맞는 서비스 페이지를 MF로 로드
          ├ /dashboard → 대시보드 페이지
          ├ /orders    → 주문 페이지
          └ /customers → 고객 페이지

Shell이 공통 영역을 렌더링하고 유지한다. 서비스팀은 글로벌 헤더와 사이드바를 제외한 페이지 본문과 공개 위젯을 개발한다. 서비스 내부의 탭·검색 영역·툴바는 서비스가 담당한다.

서비스 간 이동은 Shell 내부의 클라이언트 라우팅으로 처리한다. Shell을 유지하도록 구성하면 본문의 서비스 페이지가 바뀌어도 공통 영역의 상태와 연결을 유지할 수 있다. 개별 페이지의 입력 상태까지 자동으로 보존되는 것은 아니다.

이 구성에서 Nginx는 화면 URL에 Shell을 전달하고 정적 파일과 API 요청 등을 연결한다. 본문에 어떤 서비스 페이지를 표시할지는 브라우저의 Shell이 결정한다.

새 서비스 등록 때문에 반드시 Shell을 재빌드할 필요는 없다. 서비스 주소·메뉴·경로를 외부 설정에서 읽고 동적으로 등록하도록 구현하면, 공통 계약을 만족하는 서비스는 설정 변경으로 추가할 수 있다. 이는 필요한 등록·검증 기능을 구현했을 때의 동작이며, MF만 설정하면 자동으로 완성되는 기능은 아니다.

## 5. 구성안 B Nginx가 URL별 독립 앱으로 연결

    /orders
    └ 주문 앱 실행
       ├ 공통 헤더·사이드바를 MF로 로드
       └ 주문 화면 표시

    /customers
    └ 고객 앱 실행
       ├ 공통 헤더·사이드바를 MF로 로드
       └ 고객 화면 표시

이 구성에는 모든 서비스 화면에서 계속 실행되는 단일 Shell이 없다. 각 서비스가 독립 앱으로 시작하고, 공통 모듈을 가져와 자기 화면을 구성한다.

**공통 헤더와 사이드바의 코드는 공유하지만, 실행 중인 공통 화면 인스턴스는 앱 사이에 자동으로 이어지지 않는다.** 다른 서비스 앱으로 이동할 때 일반적으로 문서 전체가 전환된다. 같은 앱 내부의 화면 이동은 클라이언트 라우팅으로 처리할 수 있다. [경로 기반 MFE와 앱 간 이동](https://nextjs.org/docs/app/guides/multi-zones)

공통 헤더·사이드바나 위젯을 MF로 가져오므로, 이 구성도 MF를 사용하는 구조다. Nginx의 URL 분기 자체가 MF 기능인 것은 아니다.

### 발생할 수 있는 문제와 대응

| 문제 | 구체적인 상황 | 대응 방향 |
|---|---|---|
| 공통 영역이 다시 시작됨 | 다른 앱으로 이동하면 사이드바 펼침 상태, 열어 둔 알림창, 메모리 상태가 초기화되고 알림 연결이 재생성될 수 있음 | 필요한 상태를 저장·복원하고 연결 재시작을 처리 |
| 앱 초기화 책임이 분산됨 | 서비스마다 사용자 확인, Provider 설정, 오류 처리와 화면 조립 방식이 달라질 수 있음 | 플랫폼이 공통 초기화 함수와 연결 규칙을 제공 |
| 앱 간 이동 처리가 필요함 | 다른 서비스 경로를 현재 앱 내부 라우터가 처리하면 화면을 찾지 못할 수 있음 | 서비스별 URL과 이동 규칙을 통일하고 Nginx 경로에 맞춰 연결 |
| 공통 모듈의 사용 환경이 여러 개임 | 공통 헤더·SDK 변경이 각 앱의 설정과 실행 환경에 맞는지 확인해야 함 | 지원 버전과 계약을 정하고 사용 앱들과 호환성을 검증 |

로그인이 반드시 풀리는 것은 아니다. 공통 세션으로 로그인은 유지할 수 있으며, 문서 전환으로 사라지는 앱 메모리 상태와 로그인 세션을 구분해야 한다.

헤더와 사이드바를 MF로 제공하므로 공통 UI를 변경할 때마다 모든 서비스를 재빌드해야 하는 것은 아니다. 호환되는 버전을 선택해 반영하는 정책이 필요하다.

### 두 구성의 차이

| 항목 | 단일 Shell | URL별 독립 앱 |
|---|---|---|
| 공통 영역을 실행하는 주체 | Shell | 각 서비스 앱 |
| 서비스 간 이동 | Shell을 유지하며 본문 전환 | 일반적으로 문서 전체 전환 |
| 공통 영역의 메모리 상태 | Shell이 유지되는 동안 보존 가능 | 저장·복원 처리 필요 |
| 앱 시작과 공통 기능 연결 | Shell에서 공통 초기화 | 각 앱이 공통 초기화 규칙을 적용 |
| 공통 SDK의 MF 제공 | 가능 | 가능 |
| 서비스의 독립 빌드·배포 | 가능 | 가능 |
| 대시보드의 공개 위젯 조합 | 가능 | 가능 |

공통 영역의 모양을 통일하는 것과, 서비스 이동 중에도 공통 영역의 상태·동작을 유지하는 것은 서로 다른 요구다. 단일 Shell 채택 여부는 이 요구와 앱 초기화 책임을 어디에 둘지를 기준으로 결정한다.

## 6. 대시보드는 공개된 위젯을 조합

**대시보드는 각 서비스가 계약을 통해 공개한 위젯을 선택하고 배치한다.** 위젯의 업무 UI와 동작은 제공하는 서비스가 소유한다.

    대시보드
    ├ 주문 서비스의 주문 요약 위젯
    ├ 주문 서비스의 배송 현황 위젯
    └ 다른 서비스가 공개한 위젯

| 담당 | 책임 |
|---|---|
| 위젯 제공 서비스 | 위젯 구현, 업무별 설정과 기본값, 데이터 조회, 화면과 동작 |
| 대시보드 | 위젯 발견·로딩·선택·배치와 표준화된 공통 입력 전달 |
| 플랫폼 | 공통 실행 기반, 모듈 로딩 기능, 사용자·조직 정보 접근과 공통 연결 규칙 |

단일 Shell 구성에서는 Shell이 대시보드 페이지를 불러오고, 대시보드가 위젯을 불러온다. URL별 독립 앱 구성에서는 대시보드 앱이 공통 헤더·사이드바와 공개 위젯들을 불러온다.

대시보드는 위젯을 불러오는 MF 호스트 역할을 한다. 이 역할만으로 대시보드가 전체 플랫폼의 Shell이 되는 것은 아니다. 호스트는 모듈을 소비하는 관계상의 역할이고, Shell은 공통 화면 틀을 유지하는 앱의 책임을 뜻한다.

### 위젯 추가 시 대시보드 코드를 바꾸지 않는 원칙

**대시보드는 위젯별 업무 내용을 모르고, 모든 위젯이 따르는 공통 실행 계약만 안다.**

주문 위젯에만 필요한 조회 기간이나 주문 상태, 주문 클릭 전용 콜백 등을 대시보드가 개별적으로 연결하는 구조로 만들지 않는다. 업무별 입력과 설정 화면은 위젯이 담당하고, 공통 화면 이동 기능 등은 플랫폼 SDK의 공개 기능을 사용한다.

모든 props를 없애는 것이 필수 조건은 아니다. 예를 들어 동일한 위젯을 여러 개 배치할 때 구분하는 인스턴스 ID처럼, 모든 위젯에 같은 규칙으로 전달할 수 있는 입력은 공통 계약에 포함할 수 있다. 인스턴스 ID는 설명을 위한 예시이며, 실제 필드명과 타입은 아직 확정하지 않았다.

props를 받더라도 그 형태와 동작을 유지하는 내부 업데이트라면 소비자를 수정할 필요가 없다. 문제가 되는 것은 대시보드가 새 위젯마다 업무 전용 입력을 알아야 하거나, 기존 사용법을 깨는 변경이 발생하는 경우다.

신규 위젯을 대시보드 코드 변경 없이 추가하려면 다음 조건도 충족해야 한다.

- 대시보드가 외부 위젯 목록에서 로딩 위치와 지원 계약 정보를 읽는다.
- 위젯 종류별 import나 렌더링 분기를 대시보드 코드에 추가하지 않는다.
- 업무별 설정 화면과 기본값은 위젯이 제공한다. 대시보드에 위젯별 설정 폼을 추가하지 않는다.
- 새 위젯이 기존 공통 실행 계약과 플랫폼이 제공하는 기능 범위를 따른다.

이 조건 안에서의 추가는 다음 흐름으로 처리한다.

    서비스팀이 공통 규격에 맞춰 위젯 개발·배포
      → 외부 위젯 목록에 등록
      → 대시보드가 목록에서 발견
      → 기존 공통 규칙으로 로드·표시

새 위젯이 기존 플랫폼에 없는 기능을 요구하거나 공통 실행 계약 자체를 변경한다면, 플랫폼이나 대시보드의 변경이 필요할 수 있다. 업무별 전용 코드 없이 위젯을 추가한다는 원칙이 모든 미래 변경을 수정 없이 수용한다는 뜻은 아니다.

### 사용자 정보는 공통 SDK를 통해 접근

같은 로그인 세션을 사용한다고 JavaScript의 사용자 정보 객체나 React 상태가 자동으로 공유되는 것은 아니다. 플랫폼 SDK에 사용자·조직 정보를 읽는 공통 접근 기능을 제공하고, 위젯은 그 기능을 사용한다.

단일 Shell에서는 Shell이 설정한 공통 실행 환경을 사용한다. URL별 독립 앱에서는 각 앱이 같은 초기화 규칙과 인증 세션을 바탕으로 공통 실행 환경을 구성한다. Provider와 Hook의 동일 Context 조건은 두 구성 모두 지켜야 한다.

props 대신 Context나 SDK를 통해 값을 읽어도 해당 API와 데이터 의미에 대한 계약은 남는다. [React Context의 데이터 전달 방식](https://react.dev/learn/passing-data-deeply-with-context)

**이 안건은 설계 원칙을 정하는 단계까지 완료했다. 실제 API 이름, 입력 필드, 타입, 오류 처리 명세와 구현은 아직 확정하지 않았다.**

## 7. MF 제공과 버전 반영의 관계

MF로 공통 모듈이나 위젯을 제공하면, 소비자가 재빌드되지 않아도 호환되는 새 코드를 로드하도록 구성할 수 있다. 다만 다음을 구분한다.

- 새 파일을 배포하는 것과 운영에서 그 버전을 사용하도록 선택하는 것은 별개의 작업이다.
- 외부 설정을 통해 사용할 버전을 바꾸도록 구현할 수 있다.
- 계약이나 실행 환경이 호환되지 않는 변경은 MF가 자동으로 해결하지 않는다.
- 이미 실행 중인 모듈이 새 배포만으로 자동 교체되는 것은 아니다.
- 자동 호환성 검사와 운영 버전 갱신은 구현할 배포 정책이며, 구체적인 검사·승격 방식은 아직 결정하지 않았다. 의존성 등록·사용 추적·지원 종료의 원칙은 다음 절에 정리한다.

MF는 런타임 등록·로딩 기능을 제공한다. 소비자별 버전 선택, 운영 승격과 폐기 정책은 그 위에 설계해야 한다. [MF Runtime API](https://module-federation.io/guide/runtime/runtime-api)

## 8. 버전 추적과 지원 종료와 파일 삭제

**위젯은 의존성을 선언하고, 플랫폼은 사용 여부를 확인할 기능과 지원 종료 절차를 제공한다.**

### 배포할 때 의존성을 등록

각 위젯은 자신의 배포 버전, 소유 팀, 사용하는 서비스·SDK와 필요한 버전·계약 정보를 함께 등록한다. 등록된 위젯 버전 중 실제 운영에 연결된 버전도 구분한다.

| 기록 대상 | 의미 |
|---|---|
| 위젯 배포 버전 | 어떤 위젯 산출물을 사용하는가 |
| 의존하는 서비스·SDK와 필요 버전 | 어떤 모듈에 의존하고 어떤 버전을 허용하는가 |
| 요구 계약 버전 | 어떤 공개 API와 동작을 기대하는가 |
| 실제 연결된 버전 | 해당 실행에서 어떤 산출물과 계약을 선택했는가 |
| 소유 팀과 배포 상태 | 누가 이전을 담당하며 어떤 환경에서 사용하는가 |

배포 버전은 실제 산출물의 식별자이고, 계약 버전은 소비자가 따르는 인터페이스의 식별자다. 한 산출물이 여러 계약을 제공할 수도 있으므로 구분하여 기록한다.

### 플랫폼에서 사용 여부를 추적

플랫폼이 제공할 추적 기능은 외부 위젯 등록부, 배포 기록, 공통 로더의 실행 기록을 연결한다. 위젯을 새로 빌드했다는 사실만으로 이전 운영 버전이 교체되었다고 판단하지 않는다.

등록부에는 선언된 의존성과 실제 운영 연결 상태를 기록한다. 공통 로더는 요구 계약과 제공 계약의 호환성을 확인하고, 로딩한 위젯·SDK·계약 버전과 성공·실패를 기록한다. 이러한 관측에 MF 런타임 훅을 활용할 수 있으며, 업무 계약을 해석하고 추적하는 기능은 플랫폼에서 구현한다. [MF 런타임 훅](https://module-federation.io/guide/runtime/runtime-hooks)

최근 실행 기록이 없다는 이유만으로 미사용을 확정하지 않는다. 가끔 실행되는 위젯, 저장된 대시보드에서 다시 열릴 위젯, 허용된 롤백, 단계적으로 배포 중인 버전, 지원 기간 안의 오래 열린 화면도 확인해야 한다.

### 지원 종료와 물리적 파일 삭제를 분리

| 단계 | 원칙 |
|---|---|
| 사용 중 | 지원 대상에서 사용할 수 있는 버전으로 유지한다. |
| 종료 예정 | 종료 예정 사실과 유예 기간을 알리고, 소비자 이전을 진행한다. 종료 예정 버전을 새로 채택하는 것을 제한한다. |
| 지원 종료 | 남아 있는 지원 대상 소비자를 확인하고, 종료 조건을 충족한 뒤 운영 선택·신규 사용을 제한한다. 등록 정보는 종료 상태와 이력을 남긴다. |
| 파일 삭제 | 지원 종료 이후에도 필요한 보존 기간을 거친 뒤, 롤백과 오래 열린 화면 등의 영향을 확인하여 저장소 산출물 삭제를 별도로 판단한다. |

새 버전으로 업그레이드했거나 최근 사용량이 없다는 사실만으로 구버전을 즉시 제거하지 않는다. 공지한 기간이 끝났다는 사실만으로도 제거를 허용하지 않는다. 구버전이 필요한 지원 대상이 남아 있다면 이전하거나 명시적인 지원 종료 처리를 먼저 해야 한다.

새 SDK 코드에서 구계약 구현을 제거하는 변경도, 그 SDK를 사용할 지원 대상 위젯과의 호환성을 확인한 뒤 배포해야 한다. 새 SDK의 코드 변경과 이전 SDK 산출물의 물리적 삭제는 서로 다른 작업이다.

지원 종료 시 등록부의 버전 기록을 통째로 삭제하지 않는다. 종료 상태, 의존 관계, 배포·사용 이력을 보관한다.

S3 파일을 삭제하거나 CDN 캐시를 무효화해도 이미 브라우저에 내려간 코드를 회수할 수는 없다. 구버전의 지연 로딩에 필요한 파일과 롤백 산출물은 정한 지원·보존 정책에 따라 관리한다. [CloudFront 캐시 무효화의 한계](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation.html)

**위 항목은 운영 원칙으로 정리했다. 알림 채널, 담당자 통보·에스컬레이션 방식, 유예 기간, 세션 지원 기간, 파일 보존 기간, 자동 배포 차단의 구현은 아직 정하지 않았다.**

## 9. 다음에 정할 사항

**다음 논의 안건은 A가 B v1을 요구하고 C가 B v2를 요구할 때 버전을 선택하고 공존시키는 방법이다.**

남아 있는 결정 사항은 다음과 같다.

1. A는 B v1, C는 B v2를 요구할 때의 버전 선택과 공존 정책.
2. 구·신 계약을 병행 제공하는 구체적인 구현과 지원 범위.
3. 공통 SDK와 페이지·위젯의 구체적인 API·타입 명세.
4. 호환성 검증과 운영 버전 갱신을 자동화하는 방법.
5. 지원 종료 원칙을 구현할 알림 방식, 기간 값, 배포·로딩 제한 기능.
6. 서비스 간 순환 의존을 검사하고 제한하는 규칙.
7. 단일 Shell을 사용할지, URL별 독립 앱으로 구성할지.

이 항목들은 현재 구성 설명과 구분하여 후속 설계에서 결정한다.
