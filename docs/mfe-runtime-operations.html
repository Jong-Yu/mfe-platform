버전 운영과 오류 복구 참고서

실행 조합 변경, RemoteRegion 복구, 지원 종료와 탭 보호. 구현 방법과 검증 기록을 작업별로 찾습니다.

START

필요한 작업부터 찾아보세요

이 문서는 명령·운영 절차·실패 복구 구현·검증 결과를 찾는 참고서입니다. 처음 읽는다면 입문 설명서에서 Shell·SDK·조합의 뜻을 먼저 확인하세요.

하려는 일읽을 절
SDK/B/D 버전을 바꾸거나 롤백실행 명령 → 기존 탭과 전환 예제
A가 B와 C를 함께 사용하는 경로 이해중첩 경로 → 공통 RemoteRegion
C/B/D 로딩 실패를 격리하고 복구오류 격리 → 재시도 → 하위 D 복구

SDK 1.2.0은 개발 Layout, 1.3.0은 공통 RemoteRegion 도입, 1.3.1은 재시도 정책 개선 사례입니다. 각 검증 당시의 숫자는 기록으로 유지했습니다. 현재 소스 버전·개발 키트·제품/시연 서버의 선택은 별개입니다.

test:nested는 A/C/B 복사본을 빌드합니다. test:region-sdk는 보존된 서비스 파일을 재사용하고 SDK만 빌드합니다. 두 검사의 “재빌드 없음” 범위를 혼용하지 않습니다.

01

필요한 작업만 실행합니다

각 코드 블록은 명시된 위치에서 시작합니다. Node.js 24 환경을 권장합니다. 루트 폴더에는 npm workspace가 없으며, 통합 명령은 로컬 검증을 돕는 편의 기능입니다.

전체 검증 화면 실행

프로젝트를 모아 둔 루트에서 시작
cd integration
npm ci
npm run setup
npm run build
npm start

화면: http://127.0.0.1:4173 · 역순 로딩: /?order=ca · 빈 화면: /?empty=1

서비스 하나만 설치·빌드하기
프로젝트를 모아 둔 루트에서 시작
cd projects/service-a
npm ci
npm run build

B 소스나 B 서버는 빌드에 필요하지 않습니다. dist/release.json에 생성된 배포 ID와 remote 메타데이터가 기록됩니다. 서비스 remote의 npm start는 정적 산출물을 제공하며 별도 업무 개발 화면을 표시하지는 않습니다.

호환 SDK만 업데이트하기

SDK 소스·릴리스 버전과 lockfile을 갱신한 뒤 실행합니다. 아래 SDK_ARTIFACT_ID는 새 SDK의 dist/release.json에 있는 실제 id로 바꿉니다. 활성화 전 기존 소비자 조합 검증을 완료합니다.

프로젝트를 모아 둔 루트에서 시작
cd projects/platform-sdk
npm run build
cd ../../integration
npm run publish -- ../projects/platform-sdk
npm run activate -- --platform 'SDK_ARTIFACT_ID'

publish는 파일 발행, activate는 실행 조합 선택입니다. 새 SDK를 발행한 것만으로 기존 화면이나 현재 선택은 바뀌지 않습니다.

이전 조합으로 롤백하기

integration 디렉터리에서 · 실제 이전 조합 ID로 교체
npm run activate -- --composition 'PREVIOUS_COMPOSITION_ID'

B만 올리고 A·C의 선택 바꾸기

B 소스와 릴리스 버전·lockfile을 갱신한 뒤 B만 빌드·발행합니다. 아래는 B 2.x 예입니다. 1.x도 해당 B 프로젝트에서 같은 절차로 진행합니다.

프로젝트를 모아 둔 루트에서 시작
cd projects/service-b-v2
npm version minor --no-git-tag-version
npm run build
cd ../../integration
npm run publish -- ../projects/service-b-v2

소비자 ID는 현재 /registry.json의 selected.A·selected.C에서, 새 B ID는 발행 결과에서 확인합니다. 새 B에는 사용할 D 배포 ID도 함께 지정합니다. D를 다시 빌드할 필요는 없습니다. 아래 대문자 값은 실제 ID로 교체합니다.

integration에서 · 원하는 소비자만 선택하거나 두 변경을 한 번에 적용
npm run activate -- --bind 'A_ARTIFACT_ID:b=B_1_5_ARTIFACT_ID' --bind 'B_1_5_ARTIFACT_ID:d=D_1_ARTIFACT_ID'
npm run activate -- --bind 'C_ARTIFACT_ID:b=B_2_2_ARTIFACT_ID' --bind 'B_2_2_ARTIFACT_ID:d=D_2_ARTIFACT_ID'

# A와 C를 하나의 조합으로 함께 전환할 때
npm run activate -- --bind 'A_ARTIFACT_ID:b=B_1_5_ARTIFACT_ID' --bind 'B_1_5_ARTIFACT_ID:d=D_1_ARTIFACT_ID' --bind 'C_ARTIFACT_ID:b=B_2_2_ARTIFACT_ID' --bind 'B_2_2_ARTIFACT_ID:d=D_2_ARTIFACT_ID'

이 과정에서 A·C·Shell·SDK를 빌드하지 않습니다. 발행만으로 선택이 바뀌지는 않습니다. 열린 화면은 이전 B를 유지하고 새 화면부터 새 B를 받습니다. 이전 조합으로 롤백하면 SDK와 B·D 바인딩까지 함께 복구됩니다.

A 자체 코드를 바꿔 새 A 배포 ID가 생겼다면 A를 발행한 뒤 --A NEW_A_ID --bind NEW_A_ID:b=B_ID를 함께 지정합니다. 새 소비자 ID에 필요한 바인딩을 생략하면 활성화가 거절됩니다. bootstrap은 최초 구성·의도적인 전체 재설정에만 사용합니다.

B를 그대로 두고 D만 교체하기

처음 D 런타임 연결로 전환한 B부터 사용할 수 있습니다. D 소스·버전·lockfile을 갱신하여 D만 빌드·발행합니다. 아래는 A 경로에서 사용하는 D 1.x 예입니다.

프로젝트 루트에서 시작
cd projects/service-d-v1
npm version minor --no-git-tag-version
npm run build
cd ../../integration
npm run publish -- ../projects/service-d-v1

B 배포 ID는 현재 등록부의 runtimeBindings[selected.A].b 또는 runtimeBindings[selected.C].b에서 확인합니다. 새 D ID는 발행 결과에서 확인합니다.

integration에서 · 실제 배포 ID로 교체
# A가 쓰는 B의 D만 변경
npm run activate -- --bind 'B_1_ARTIFACT_ID:d=NEW_D_1_ARTIFACT_ID'

# C가 쓰는 B의 D도 독립적으로 변경
npm run activate -- --bind 'B_2_ARTIFACT_ID:d=NEW_D_2_ARTIFACT_ID'
경로교체 전교체 후유지하는 파일
A → B 1.xD 1.0D 1.1A·B·Shell·SDK
C → B 2.xD 2.0D 2.1C·B·Shell·SDK

D만 바뀌고 A → B 연결과 B 자체 배포 ID는 유지됩니다. 두 변경을 한 번에 적용하려면 두 --bind를 같은 명령에 전달합니다. 열린 탭은 전체 조합을 유지하므로, 변경 뒤 처음 불러오는 C도 그 탭의 기존 D를 사용합니다.

Shell 자체 서버와 테스트 실행

4173 저장소 서버를 유지하고 별도 터미널의 루트 폴더에서 cd projects/shell, npm start를 실행합니다. Shell 서버는 http://127.0.0.1:4180입니다.

통합 검사는 integration에서 npm test로 실행합니다. 독립 설치 검사는 준비된 npm 캐시를 사용합니다. 새 환경의 캐시·브라우저 준비는 통합 검증 안내를 확인합니다.

02

SDK를 발행한 뒤, 실행 조합을 전환합니다

  1. 새 SDK를 독립적으로 빌드·발행합니다.

    기존 SDK 파일을 덮어쓰지 않고 새 불변 배포 경로에 올립니다. 발행만으로 사용 중인 조합은 바뀌지 않습니다.

  2. 기존 소비자 산출물과의 호환성을 확인합니다.

    서비스들의 지원 SDK 범위와 정확한 React 요구 조건을 검사하고 실제 동작을 검증합니다.

  3. 새 조합을 만들고 현재 포인터를 전환합니다.

    불변 조합 JSON과 HTML이 준비된 뒤 current.json의 선택을 바꿉니다. 기존 소비자 파일은 그대로입니다.

  4. 새 진입에는 새 SDK, 열린 탭에는 기존 SDK를 유지합니다.

    열린 탭에서 나중에 위젯을 추가해도 처음 받은 SDK를 사용합니다. 롤백도 이전 조합을 선택해 이후의 새 진입에 적용합니다.

03

A가 B를 직접 쓰고, C를 통해 다른 B도 쓰는 경우

A → B 1.4, A → C 1.1 → B 2.1을 실제 MF 빌드와 Chrome에서 검증했습니다. Shell에서 A만 마운트해도 두 B 위젯이 나타납니다. C를 Shell의 별도 슬롯에 먼저 띄워야만 동작하는 예제가 아닙니다.

동일한 SDK 1.3.0·React 실행 환경 / A 하나 안의 두 경로

Shell
└─ A 1.1
   ├─ B 1.4 → D 1.0
   └─ C 1.1
      └─ B 2.1 → D 2.0

A의 릴리스도 새 의존성 C와 화면 구성을 추가하면서 1.1.0으로 빌드했습니다. B 1.4·D·Shell은 기존 배포물을 사용하고 SDK는 공통 RemoteRegion을 추가한 1.3.0을 선택했습니다. B 2.1은 D 복구 지원을 넣어 별도 배포 ID로 빌드했습니다.

선택은 호출한 소비자 배포 ID를 기준으로 합니다

소비자별칭실행 대상
A 배포물bB 1.4 배포물
A 배포물cC 1.1 배포물
C 1.1 배포물bB 2.1 배포물

A와 C의 코드에 같은 b/Widget이 있어도 빌드 도구가 넣은 소비자 ID가 다릅니다. getDependencyContainer(소비자ID, 별칭)는 각자의 연결을 조회하므로 A의 B 선택이 C 안으로 상속되지 않습니다. 이 형태는 순환참조가 아닙니다. A는 C의 Consumer이고 C는 A에 대한 Remote이면서 B의 Consumer입니다.

조합의 일부 / ID는 설명용이며 실제 파일에는 정확한 배포 ID 사용
{
  "runtimeBindings": {
    "A_ARTIFACT_ID": {
      "b": "B_1_4_ARTIFACT_ID",
      "c": "C_1_1_ARTIFACT_ID"
    },
    "C_1_1_ARTIFACT_ID": { "b": "B_2_1_ARTIFACT_ID" }
  }
}

버전별 MF container·Webpack 이름·CSS 클래스는 배포 ID로 구분합니다. 화면 인스턴스는 A와 A--c, 복제본은 A-copy와 A-copy--c로 구분해 SDK의 WidgetBoundary를 각각 생성합니다. 배포 ID는 모듈 선택·재사용, 인스턴스 ID는 개별 화면의 상태·팝업 구분에 사용합니다.

실패 캐시 정리 과정에서 이미 준비한 실행 함수는 다시 사용합니다. 같은 루트의 container.get()을 즉시 중복 호출해 대기 정책을 우회하는 현상도 함께 수정했습니다. 이 정책은 로딩 시도 횟수의 상한이며, 의존 그래프 전체의 모든 HTTP 요청을 합쳐 두 개로 제한한다는 뜻은 아닙니다.

제거된 영역은 늦은 결과로 다시 마운트하지 않습니다. 공유 중인 네트워크 요청은 다른 소비자를 위해 끝까지 진행할 수 있습니다. 이미 정상인 A/B 1.4/SDK는 초기화하지 않으며 C의 배포 버전도 바꾸지 않습니다. 기존 v2 복구 지원과 이 의존 경로에서 검증한 결과입니다.

‘파일 삭제 준비’ 후 전체 ID·사유·관측 범위 밖 미사용 확인을 입력하고 실행합니다. 이 화면에서 삭제한 파일을 복원할 수 없습니다.

등록 해제 조건: 지원 종료일과 공지 유예가 지났고 현재 조합에서 사용하지 않아야 합니다. 구버전 탭과 롤백 참조가 남아 있어도 등록 해제는 가능하며 파일은 보관합니다. 등록 해제 후 지원 정책을 수정하거나 같은 배포 ID를 재발행하여 되살리는 것은 금지합니다.

롤백 보관 해제: 상세의 ‘롤백 보관·고정 참조’에서 조합을 선택하고 전체 조합 ID와 사유를 확인합니다. 현재 적용된 조합은 해제할 수 없습니다. 해제는 조합 전체에 적용되며 이후 그 조합으로 돌아갈 수 없습니다. 기록을 지우지 않으므로 이전 탭의 의존 관계는 계속 추적할 수 있습니다.

파일 삭제 조건: 등록 해제 상태, 기간 조건, 현재 사용·탭·롤백·고정 참조 부재를 모두 만족해야 합니다. 준비 화면을 연 뒤 다른 탭의 사용 보고가 들어와도 실행 직전 검사에서 거절합니다. ‘관측 범위 밖 미사용 확인’은 발견된 참조나 보존 기간을 무시하는 옵션이 아닙니다.

지원 종료 차단과 현재 사용 유지는 어떻게 구분하나요?

A → B → D가 그대로 유지되는 동안 D의 지원 종료일이 지나도 현재 조합을 강제로 중단하지 않습니다. 다른 D로 전환한 뒤 종료된 D로 되돌리거나, 새 B를 통해 종료된 D를 새로 사용하는 경로는 거절합니다. SDK와 B에도 같은 규칙을 적용합니다.

UI에서 종료 버전은 선택을 비활성화하고, 등록 해제된 버전은 선택 목록에서 제외합니다. 서버의 preview·apply·명령줄·롤백에서도 전체 경로와 현재 시각을 검사하므로 오래 열린 관리 화면이나 직접 API 요청으로 우회할 수 없습니다. 현재 조합의 신규 방문자를 차단하거나 이미 내려받은 코드를 회수하는 기능은 아닙니다.

삭제 중 오류가 나면 어떻게 하나요?

삭제 의도를 먼저 기록하고 파일을 비공개 작업 디렉터리로 옮긴 뒤 제거합니다. 실제 제거가 끝나야 ‘파일 삭제 완료’가 됩니다. 중간 오류나 프로세스 종료가 있으면 ‘삭제 미완료’로 남으며, ‘남은 파일 삭제 준비’에서 조건을 다시 확인해 재시도합니다.

활성화·발행·정책 변경·관측 보고·제거 작업은 같은 저장소 잠금을 사용합니다. 삭제 직전 조건을 다시 읽고, 대상 ID·수정 번호·현재 조합을 확인합니다. 파일 경로의 심볼릭 링크는 거절합니다. 삭제 기록은 배포 원장에 남기며 운영 사용자 인증·감사 로그는 별도 범위입니다.

응답 없는 탭 때문에 영원히 삭제하지 못한다면?

‘탭이 죽었다’고 추측하지 않고, 구버전을 계속 사용할 수 있는 기한을 관리합니다.

정상 탭은 계속 갱신해 보호합니다. 기한을 넘긴 탭은 구버전 조작과 추가 로딩을 멈추도록 먼저 구현한 뒤, 해당 탭의 보호 참조를 정리합니다. 참조 정리와 파일 삭제는 별도 작업입니다.

  2. 재개 보호 적용 여부, 마지막 응답, 사용 기한, 정리 가능 시각을 확인합니다. 24시간 유예가 끝난 보호 탭만 버튼이 활성화됩니다.
  3. 탭 참조 정리 준비 → 전체 탭 ID와 사유 입력 → 실행합니다. 이 탭이 참조한 전체 조합의 보호 참조를 함께 정리하며 파일은 남깁니다.

정리 요청은 화면에 표시됐던 응답 순서 번호와 기한을 보냅니다. 서버가 실행 직전에 같은 잠금 안에서 다시 읽으므로 새 응답을 무시하고 정리하지 않습니다. 정리된 기록은 삭제하지 않으며 정리 시각·사유·이전 조합을 계속 조회할 수 있습니다. 파일 삭제도 정리 여부와 전체 참조를 다시 검사합니다.

오래된 탭이 돌아오면

브라우저 재개, 뒤로 가기 캐시 복귀, 다시 보이는 화면, 네트워크 복구 시 서버에 사용 기한을 재확인합니다. 만료된 ID는 서버가 거절합니다. 화면에 안내를 띄우고 사용자가 ‘최신 화면 열기’를 누르면 현재 조합으로 새로 시작합니다.

자동 새로고침으로 입력을 버리지 않습니다. 기존 화면은 남겨 두지만 새 화면을 열면 미저장 입력은 사라질 수 있습니다.

이번 도입에 필요한 변경

Shell과 관리 화면을 한 번 수정·빌드했습니다. SDK·A·B·C·D는 다시 빌드하지 않습니다. 이후 탭 갱신·참조 정리·파일 삭제 때 서비스 재빌드는 없습니다.

서버가 추가한 보호 스크립트와 새 Shell 로더가 함께 동작합니다. 이전 Shell 또는 이미 열어 둔 탭을 보호 기능이 있는 탭으로 간주하지 않습니다.

사용 기한이 단순한 타이머와 다른 이유

Shell은 SDK를 불러오기 전에 서버에서 사용 기한을 발급받습니다. 발급에 실패하면 서비스를 시작하지 않습니다. 캐시된 container나 모듈 factory를 사용할 때도 Shell 로더가 기한을 검사하며, 화면 이벤트를 React보다 먼저 차단합니다. 재개 확인 중에도 조작을 막습니다.

서버 시각으로 5분 기한을 정하고 클라이언트는 요청 시작 시각을 기준으로 5초 먼저 잠급니다. 느린 응답이 브라우저 기한을 늘리지 않도록 하며 wall clock과 monotonic clock을 함께 확인합니다. 만료된 기한은 같은 ID로 연장하지 않습니다. 서버 재시작에도 기록이 남습니다.

브라우저는 백그라운드 타이머를 늦추거나 페이지 실행을 동결할 수 있으므로 주기 타이머 외에 재개 이벤트와 실제 로더·조작 시점에도 확인합니다. 근거: Chrome · Page Lifecycle API, MDN · performance.now와 절전 중 시간.

적용 범위: 사용 기한은 이 로컬 호스트와 협력하는 Shell·서비스의 수명 관리 계약입니다. 이미 내려받은 JavaScript 전체를 회수하는 보안 격리가 아닙니다. 임의의 DOM/스크립트 삽입, 별도 Worker·WebSocket, 이미 전송된 업무 요청은 이 보호가 통제하지 않습니다. 실제 업무 API는 별도 인증과 필요 시 서버 측 사용 기한/세대 검사를 적용해야 합니다. 구형 탭에는 다음의 별도 절차를 제공합니다.

보호 기능 도입 전에 열린 구형 탭도 전환·정리하기

응답하는 탭은 문서를 전환하고, 돌아오지 않는 탭은 해당 버전의 제공을 종료한 뒤 참조를 정리합니다. 오래된 추적 코드는 서버의 명령 응답을 읽지 않습니다. 해당 코드를 수정한 것처럼 가정하지 않고 브라우저 중계와 서버의 파일 접근 차단을 추가했습니다.

1. 구형 탭을 최신 화면으로 전환

  1. 관리 화면에서 배포물 → 구형 탭 전환 · 접근 종료를 펼칩니다.
  2. ‘이 브라우저의 전환 중계 연결’을 누릅니다. 같은 브라우저·프로필·출처의 기존 탭에 연결됩니다. 다른 중계가 등록되어 있으면 덮어쓰지 않습니다.
  3. 대상 사용자에게 전환을 안내하고 ‘구형 탭 전환 준비’에서 전체 탭 ID·사유·미저장 입력 손실 확인을 입력합니다.
  4. 구형 탭의 다음 응답을 중계가 받아 별도 전환 문서로 이동시킵니다. 그 문서의 확인 요청이 도착하면 이전 참조를 정리하고 현재 선택된 서비스 화면으로 이동합니다.

2. 돌아오지 않는 탭의 참조 정리

  1. 대상 버전을 현재 조합에서 빼고 지원 종료·공지 유예·등록 해제·롤백 및 고정 참조 정리를 마칩니다.
  2. 보호 탭 참조가 없고 구형 탭 응답도 24시간 이상 없을 때 ‘버전 접근 종료 준비’를 실행할 수 있습니다.
  3. 서버는 해당 배포 ID의 모든 파일 요청을 410으로 거절합니다. 파일 자체는 그대로 보관합니다.
  4. 접근 종료 후 다시 24시간을 기다린 뒤 해당 구형 탭의 이 버전 참조 정리를 실행합니다. 같은 탭이 쓰던 다른 버전은 계속 보호합니다.

요청을 보냈다는 이유만으로 ‘전환 완료’로 표시하지 않습니다.

중계 미설치·오프라인·이동 실패·확인 요청 실패는 완료가 아닙니다. 요청은 24시간 뒤 만료되어 다시 요청할 수 있습니다. 전환 문서의 확인은 이전 JavaScript 문서를 떠났다는 관측이며 새 서비스 전체의 정상 작동을 보증하는 검사는 아닙니다.

정상 사용 보호: 현재 조합·보호 탭·롤백·고정 참조 또는 최근 24시간 이내 구형 탭 응답이 있으면 파일 접근 종료를 거절합니다. 준비 후 새 응답이 도착해도 서버가 실행 직전에 다시 검사합니다. 응답하는 탭은 먼저 전환하거나 정상 종료해야 합니다.

삭제는 마지막 단계입니다. 접근 종료와 버전별 참조 정리 시각도 보존 기준에 포함합니다. 최소 30일 보존과 나머지 사용·참조 조건을 충족해야 실제 파일을 삭제할 수 있습니다. 접근 종료 기록은 파일 삭제 뒤에도 남아 410을 계속 반환합니다. 늦은 구형 탭 응답은 기록하되 이미 정리한 해당 버전의 참조를 부활시키지 않습니다. 다른 버전의 참조와 마지막 응답은 계속 갱신합니다.

원래 코드가 명령을 무시하는데 어떻게 전환하나요?

관리 화면이 같은 출처에 Service Worker를 설치합니다. clients.claim()으로 이미 열린 탭의 이후 요청도 중계하고, 서버가 특정 탭에 발행한 전환 경로를 받으면 그 요청을 보낸 WindowClient.navigate()로 문서를 이동합니다. 임의 URL을 받거나 모든 탭을 일괄 새로고침하는 기능은 없습니다. 캐시는 사용하지 않습니다.

추적 코드가 응답 본문을 무시해도 중계는 별도로 응답을 읽을 수 있습니다. 전환 확인은 기존 문서의 종료 알림과 별개로 새 전환 문서에서 보냅니다. 종료 알림을 의도적으로 유실시킨 검증에서도 이 경로를 확인합니다.

근거: MDN · Clients.claim, MDN · WindowClient.navigate. 등록에는 HTTPS 또는 로컬 개발의 신뢰 가능한 출처가 필요합니다. MDN · ServiceWorkerContainer.register.

범위와 운영상 의미: 관리자의 브라우저에 설치한 중계가 다른 사용자의 브라우저에 원격 설치되지는 않습니다. 그 브라우저·프로필에도 같은 출처의 중계 연결이 필요하며, 그렇지 않으면 사용자가 새로고침해야 합니다. 중계가 연결된 탭은 복귀 후 응답하거나 종료된 파일을 요청할 때 전환 문서로 이동합니다. 중계 없는 탭에도 이 서버의 파일 접근 차단은 적용되지만, 이미 내려받은 코드와 외부 API 실행을 지우지는 못합니다. 따라서 접근 종료는 ‘탭이 죽었다는 증명’이 아니라 해당 버전의 제공을 명시적으로 끝내는 운영 결정입니다. 업무 API·S3/CDN·다른 호스트는 별도의 세션 만료·접근 차단이 필요하며 실행 전 확인란에 이 범위를 표시합니다.

서비스 재빌드 없이 열린 탭을 어떻게 추적하나요?

단순 관측은 로컬 서버가 HTML 응답에 추가하는 /runtime-usage.js로 처리합니다. 재개 보호는 먼저 주입하는 /runtime-lease.js와 이를 호출하는 새 Shell이 함께 처리합니다. 후자는 최초 Shell 도입 빌드가 필요합니다. 두 방식 모두 조합 ID·container 진단을 15초마다 보고하며 같은 탭을 중복 등록하지 않습니다. 사용 현황 화면은 10초마다 갱신합니다.

이 구조는 같은 페이지의 모든 전역 부작용을 차단하는 샌드박스가 아닙니다. 직접 변경한 window·DOM·저장소나 외부 라이브러리의 전역 동작까지 자동 격리하지 않습니다.

구버전 파일은 열린 탭의 지연 로딩과 롤백에 필요할 수 있습니다. 지원 종료와 파일 삭제는 별도 절차로 판단해야 합니다. 이미 브라우저가 받은 코드는 등록부 변경만으로 회수되지 않습니다.
