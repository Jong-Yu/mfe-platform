처음 이해하는 MF 플랫폼

플랫폼과 Shell의 차이부터 독립 개발, 버전 선택까지. 하나의 자동차 서비스 예제로 순서대로 이해합니다.

START

이 순서로 읽으세요

처음에는 이 문서만 위에서 아래로 읽으세요. React로 컴포넌트를 만들고 import해 본 정도면 시작할 수 있습니다. MF 설정과 배포 용어를 미리 알 필요는 없습니다.

순서알게 되는 것언제 읽는가
1. 이 문서플랫폼·Shell·SDK의 역할, 서비스 연결, 버전 선택 원리처음 시작할 때 · 약 15분
2. 개발 안내서자기 서비스 실행, 수정할 파일, SDK 사용, 빌드·발행직접 개발할 때 · 먼저 실행 부분만
3. 운영·검증 참고서SDK/B/D 교체, 오류 복구, 기존 탭, 지원 종료·삭제필요한 작업의 절만 찾아보기
4. DB 확장 설계현재 파일 기반 등록부를 DB로 옮기는 설계운영 저장소를 확장할 때 · 아직 미구현
5분만 있다면

해결하려는 문제 → 담당별 역할 → 버전을 고르는 방법 → 재빌드가 필요한 때만 읽으세요. 모든 프로젝트나 검증 보고서를 처음부터 볼 필요는 없습니다.

01

무엇을 만들었나요

자동차 관리 화면에 공통 헤더와 사이드바가 있고, 그 안에서 OTA 팀과 정비 팀이 각자 만든 화면을 사용한다고 가정합니다. 두 팀 모두 차량 UI가 필요합니다. 차량 UI가 바뀔 때마다 모든 팀이 반드시 다시 빌드해야 한다면 독립 개발의 이점이 줄어듭니다.

이 프로젝트는 각 팀이 따로 만든 실행 파일을 브라우저에서 연결하고, 어떤 파일을 사용할지는 중앙 설정에서 고릅니다. 이 연결에 Module Federation(MF)을 사용합니다. MF는 여러 팀의 화면을 나누어 개발하는 방식인 마이크로 프런트엔드(MFE)를 구현하는 기술 중 하나입니다.

이름예제에서 맡은 역할
AOTA 화면 역할. B의 차량 UI를 사용
B여러 서비스가 재사용하는 차량 UI 역할. 1.4와 2.1을 함께 시험
C정비 화면 역할. 자신의 B 버전을 사용
DB가 사용하는 하위 함수 모듈. 화면에 D 버전과 설명을 제공

실제 예제는 카운터·입력·캐시·팝업으로 버전 공존과 상태 분리를 확인합니다. 실제 차량 목록 API나 OTA 작업 기능을 만든 프로젝트는 아닙니다. A/B/C/D는 설명용 이름이며, 프런트엔드 프로젝트를 백엔드 서비스마다 반드시 하나씩 만들어야 한다는 규칙은 없습니다.

MF의 원리: Webpack 공식 문서는 별도 빌드의 공개 모듈을 실행 시점에 불러오는 구조를 설명합니다.

02

먼저 알아둘 용어

아래 용어는 문서 전체에서 같은 뜻으로 사용합니다. 플랫폼은 제공 범위, Shell은 제품 앱, SDK는 공통 코드입니다.

용어쉬운 뜻이 프로젝트의 예
플랫폼서비스 팀이 함께 쓸 기반과 이를 제공하는 책임 범위SDK·Shell·빌드 도구·버전 운영 기능
Shell제품에 들어왔을 때 시작되고 공통 화면 틀을 만드는 앱헤더·사이드바와 A/C 배치를 담당하는 projects/shell
SDK서비스가 가져다 쓰는 공통 기능 묶음공통 정보, 화면 여백, 상태 경계, RemoteRegion
Host / Consumer다른 모듈을 가져다 사용하는 쪽A가 C를 쓰면 A도 C의 소비자
Remote다른 빌드에서 공개해 가져다 쓸 수 있는 모듈을 제공하는 쪽A에 대해 C는 Remote, C에 대해 B는 Remote
Provider / ContextReact 하위 컴포넌트에 공통 값을 전달하는 수단PlatformProvider가 사용자·테마 등 예제 값을 공급
페이지 / 위젯업무 화면 전체 / 화면에 배치할 수 있는 한 부분MF는 둘 다 공개 가능. 이 예제는 위젯 단위
등록부 / Registry발행된 배포물과 연결 정보를 관리하는 목록현재는 로컬 JSON. DB 문서는 확장 설계
빌드소스를 브라우저가 실행할 파일로 변환각 프로젝트의 npm run build
발행빌드한 파일과 정보를 저장소에 등록publish 후 버전별 파일 보관
선택 / 활성화새로 열리는 화면이 쓸 배포물을 결정SDK는 하나, A.b와 C.b는 각자 지정

다른 서비스를 호출한다고 모두 Shell은 아닙니다. Shell은 앱의 공통 진입·구성 역할을 가리키는 관례적 이름입니다. MF의 제공·소비 역할과는 구분합니다. C는 A에게 모듈을 제공하면서 동시에 B를 소비할 수 있습니다.

같은 단어라 혼동하기 쉬운 container와 manifest

PageContainer는 콘텐츠 제목·여백을 맞추는 SDK 컴포넌트입니다. MF container는 다른 빌드의 공개 모듈에 접근하는 실행 단위입니다. Docker 컨테이너와도 다른 뜻입니다.

매니페스트(manifest)는 파일 위치·버전·의존성 등을 적은 안내 정보라는 일반적인 이름입니다. 이 프로젝트의 release.json, 조합 JSON, 개발용 dev/manifest.json은 서로 목적과 형식이 다릅니다. 동일한 MF 표준 파일 하나를 뜻하지 않습니다.

03

누가 무엇을 만드나요

Shell공통 헤더 · 사이드바 · 서비스 배치
A · OTA 화면
↓ 사용
B 1.4 · 차량 UI
C · 정비 화면
↓ 사용
B 2.1 · 차량 UI
선택된 SDK 하나와 React를 함께 사용PlatformProvider · PageContainer · WidgetBoundary · RemoteRegion
담당만드는 것서비스 팀이 직접 할 일
플랫폼 팀Shell, 공통 SDK, 빌드 규칙, 개발 Host, 버전 등록·선택·사용 추적제공된 규칙을 서비스에 적용하고 호환성을 확인
서비스 팀업무 콘텐츠와 공개할 페이지·위젯, 업무 API 연결공개 모듈과 필요한 의존 범위를 선언
운영 담당어떤 배포 조합을 사용할지와 지원 종료 계획검증된 조합 선택·롤백·정리

운영 화면의 헤더·사이드바는 Shell이 한 번 그립니다. 서비스는 콘텐츠를 만듭니다. 서비스 개발 중에는 개발 Host가 SDK의 DevLayout으로 비슷한 틀을 제공하므로 자기 프로젝트만 실행할 수 있습니다.

PageContainer는 제목·여백 같은 콘텐츠 공통 규칙이 필요할 때 사용합니다. WidgetBoundary는 화면에 띄운 위젯별 상태·캐시·팝업을 구분하고, RemoteRegion은 외부 모듈을 불러오는 영역의 로딩·오류·재시도를 담당합니다. SDK 구현을 서비스에 복사하지 않고 MF로 가져옵니다.

현재 예제의 대시보드 표시 영역은 Shell에 있습니다. 서비스가 공개한 위젯을 관리 화면에서 선택해 순서·너비를 정합니다. 업무 화면은 각 서비스가 만들고, Shell은 공통 SDK 아래에서 선택한 위젯을 조합합니다. 대시보드 기능을 최초 도입한 뒤에는 위젯 추가마다 Shell을 다시 빌드하지 않습니다. 공개 위젯 선언·관리 화면 사용법을 참고하세요.

여기까지 알면 됩니다: 플랫폼 팀은 공통 기반을 제공하고, Shell은 화면 틀을, 서비스는 업무 내용을 만듭니다.
04

따로 만든 서비스는 어떻게 연결되나요

A가 b/Widget을 import한다고 해서 B 소스가 A 프로젝트에 복사되는 것은 아닙니다. 이 프로젝트의 빌드 도구는 해당 import를 실행 시 선택된 B의 공개 모듈을 요청하도록 연결합니다.

1. 선언A가 “b라는 이름으로 B가 필요하다”고 기록
2. 독립 빌드A 팀은 A 소스만 실행 파일로 만듦
3. 버전 선택플랫폼 조합에서 A.b가 사용할 B 배포물 지정
4. 브라우저 실행Shell이 조합을 읽고 A와 필요한 B 파일을 로드

b는 A가 쓰는 별칭이고 Widget은 B가 공개한 이름입니다. 실제 URL과 정확한 배포 ID는 플랫폼의 연결 설정에 있습니다. B의 내부 파일명을 바꿔도 공개 이름과 동작을 유지하면 A의 import를 유지할 수 있습니다.

npm과 MF의 차이는 무엇을 언제 가져오느냐입니다. 이 프로젝트에서 npm은 React·빌드 도구를 설치하는 데 사용합니다. 공통 SDK와 업무 Remote는 브라우저 실행 시 MF로 가져옵니다. SDK나 B를 npm 의존성으로 A 번들에 넣는 방식과 구분합니다.

공통 사용자·테마는 같은 SDK의 Provider로 명시적으로 전달합니다. 같은 로그인 세션이라는 이유만으로 React 데이터가 자동 공유되지는 않습니다. 위젯은 자신의 업무 데이터를 API로 조회하고, 화면 간 협업이 필요하면 선택 값·콜백 등 공개 입력과 출력을 정합니다.

React 근거: Provider와 소비자는 같은 Context 객체를 사용해야 합니다. useContext 공식 주의 사항.

05

버전과 연결은 어떻게 정하나요

이 문서에서 “B 1.4”는 읽기 쉬운 릴리스 이름입니다. 실제 선택에는 배포 ID를 사용하고, 화면 전체의 선택을 묶어서 조합으로 저장합니다.

구분무엇을 식별하나예시
릴리스 버전팀이 배포한 코드의 버전B 1.4.0
배포 ID정확히 어떤 빌드 파일인가b_1_4_0_…처럼 버전과 빌드 입력 해시로 구분
지원 범위소비자가 사용할 수 있다고 선언한 버전 범위A는 B 1.4 이상, 2.0 미만
조합 IDSDK·A/C·각 B/D의 선택을 묶은 스냅샷composition_…
인스턴스 ID같은 화면에 띄운 개별 위젯A와 A-copy는 같은 코드지만 다른 화면 상태

“계약”은 공개 모듈 이름, 입력·출력, 기대 동작을 합친 약속입니다. 현재 코드는 지원 버전 범위로 연결 가능 여부를 검사합니다. 별도의 계약 버전 체계나 API 의미를 자동 증명하는 기능은 없습니다.

중첩 예제 · 화살표는 “이 모듈을 사용한다”는 뜻

한 탭의 Shell + 공통 SDK 하나
└─ A 1.1
   ├─ B 1.4 → D 1.0
   └─ C 1.1
      └─ B 2.1 → D 2.0

A가 직접 고른 B와 C가 고른 B는 별개입니다. C 안에서 A의 B 선택을 물려받지 않습니다.

누가 요청했나별칭선택 결과
A 배포물bB 1.4
A 배포물cC 1.1
C 1.1 배포물bB 2.1

중앙 조합은 요청한 소비자 배포 ID + 별칭으로 버전을 찾습니다. 같은 C 배포물을 두 곳에 띄우면 두 곳 모두 같은 B 선택을 쓰되, 인스턴스별 상태는 나눕니다.

두 B 버전이 충돌하지 않게 하는 규칙

플랫폼 빌드 도구가 배포물마다 MF 이름·Webpack 실행 이름·CSS 클래스를 구분하고, SDK가 위젯마다 상태·캐시·팝업을 분리합니다. React와 SDK는 한 탭에서 하나를 공유합니다. 직접 바꾼 전역 변수나 브라우저 저장소까지 자동 격리되는 것은 아니므로 서비스도 공통 규칙 안에서 개발해야 합니다.

이 “SDK 하나, 소비자별 B/D 선택”은 이 플랫폼의 정책입니다. MF를 쓰는 모든 시스템의 필수 규칙은 아닙니다. 순환 의존성은 이 프로젝트의 조합 검사에서 거절합니다.

06

어떤 때 다시 빌드하나요

소스가 바뀌는 프로젝트는 다시 빌드합니다. 이미 발행한 파일의 선택만 바꾸면 소비자를 다시 빌드하지 않습니다. 공개 계약과 지원 범위가 맞는 것이 전제입니다.

변경다시 빌드할 곳선택·확인할 것
A의 화면 코드 수정A새 A와 A의 의존 연결
호환되는 B 개선BA 또는 C가 사용할 새 B. 해당 소비자 빌드는 불필요
호환되는 D 개선DB가 사용할 새 D. B/A/C 빌드는 불필요
SDK 내부 호환 개선SDK공통 SDK 선택. 기존 A/C/B 빌드는 불필요
서비스가 새 SDK API를 처음 사용그 서비스, 필요하면 새 SDK새 API가 있는 SDK 지원 범위와 실제 선택
B의 입력·출력 계약 변경B와 새 계약을 채택하는 소비자기존 소비자는 이전 B 유지 가능. 새 연결은 별도 검증
빌드 도구 규칙 변경새 규칙을 적용할 프로젝트이미 발행한 실행 파일에는 소급 적용되지 않음

실제로 SDK 1.3.1에서는 RemoteRegion의 수동 재시도가 일시적 파일 로딩 오류로 실패하면 500ms 뒤 한 번 더 시도하도록 바꿨습니다. A·C·B의 이전 파일을 그대로 사용해 18개 검사를 통과했습니다. 교체 전후 동작과 검증 근거는 필요할 때 확인하세요.

서비스 버전은 각 팀이 올립니다. SDK가 호환 개선됐다고 모든 서비스의 버전 번호를 함께 올리는 구조는 아닙니다.
07

배포하면 기존 탭도 바뀌나요

발행만으로는 화면이 바뀌지 않습니다. 새 SDK를 발행한 뒤 새 조합에서 선택해야 합니다. 그 이후 새로 들어온 탭이 새 조합을 사용합니다.

시점먼저 열린 탭나중에 열린 탭
SDK 1.3.0 사용 중1.3.01.3.0
SDK 1.3.1 발행만 함1.3.01.3.0
새 조합에서 1.3.1 선택1.3.0 유지1.3.1
이전 조합으로 롤백각 탭이 시작한 SDK 유지1.3.0

탭은 시작할 때의 조합을 고정합니다. 이미 열린 탭에서 나중에 C를 추가해도 그 탭의 SDK와 연결을 사용합니다. 공통 Provider를 실행 도중 바꾸지 않으므로 화면 상태를 안정적으로 유지할 수 있습니다.

따라서 새 버전이 나왔다고 구버전 파일을 바로 지우면 안 됩니다. 기존 탭의 뒤늦은 로딩과 롤백에 필요할 수 있습니다. 사용 추적 → 지원 종료 공지 → 신규 선택 차단 → 등록 해제 → 참조·보존 조건 확인 → 파일 삭제의 순서로 관리합니다. 상세 운영 절차는 운영할 때 읽으세요.

MENU

새 서비스는 어떻게 메뉴에 추가하나요

서비스만 빌드·발행 → 관리 화면에서 서비스와 메뉴 등록 → 검사·적용 → 새 탭에서 사용 순서입니다. 이 기능을 지원하는 Shell로 최초 한 번 전환한 뒤에는 새 서비스마다 Shell을 수정·재빌드하지 않습니다.

공통 헤더·사이드바는 Shell에 있고, 서비스는 콘텐츠만 공개합니다. 메뉴 이름·주소·사용할 정확한 배포 버전은 조합에 저장합니다. 기존 탭은 이전 메뉴와 버전을 유지하며 롤백하면 메뉴도 함께 돌아갑니다. 관리 화면 입력 방법과 실행 검증에서 이어서 보세요.

보존된 예제 실행 · 새 빌드 없음
cd integration

4175 예제 열기 → A 불러오기 → 파란 B 1.4와 C 안의 초록 B 2.1을 확인합니다. 각각 카운터와 입력을 바꿔 보세요. A 안의 C 제거를 눌러도 직접 B 1.4는 남습니다. 정상 시연에서는 실패를 주입하지 않습니다.

보존본을 포함하지 않은 새 환경이라면 이 명령만으로 준비되지 않습니다. SDK 교체 시연의 준비 조건을 확인하거나 기본 환경 설치부터 시작합니다. 보존본을 복원해야 하는 검사와 새로 빌드하는 검사를 구분합니다.

FAQ

자주 헷갈리는 질문

헤더·사이드바를 각 서비스가 import하고 nginx로 주소만 나누면 MF인가요?

그 사실만으로 MF는 아닙니다. 각 주소가 별도 앱을 열고 공통 라이브러리를 재사용하는 형태일 수 있습니다. 팀별 독립 앱으로 MFE를 구성할 수도 있지만, 이 프로젝트는 한 Shell 안에서 MF 모듈을 조합하는 방식을 택했습니다. URL 분리와 실행 중 모듈 조합을 구분하세요.

대시보드 위젯은 props를 전혀 받으면 안 되나요?

이 프로젝트의 원칙은 대시보드가 위젯마다 업무 데이터를 준비하지 않도록 하는 것입니다. instanceId 같은 공통 실행 값은 전달합니다. 특정 업무 흐름에서 선택 값이나 콜백이 필요하면 해당 모듈의 공개 계약에 포함할 수 있습니다. “모든 props 금지” 규칙은 아닙니다.

다른 서비스의 UI가 필요하면 API만 써야 하나요?

공통 차량 UI 자체가 필요하면 B가 공개한 모듈을 MF로 재사용할 수 있습니다. 데이터만 필요하면 담당 백엔드 API를 사용합니다. 이 예제에서 B는 프런트엔드 UI이고 D도 백엔드가 아닌 MF 함수 모듈입니다.

호환 버전이라고 적으면 오류를 완전히 막을 수 있나요?

아닙니다. 버전 범위와 연결 검사는 잘못된 선택을 줄이지만 입력·출력의 의미나 모든 부작용까지 검사하지는 않습니다. 공급자는 기존 계약을 유지하고 소비자는 실제 사용 경로를 검증해야 합니다. 계약을 바꾸면 이전 버전을 보관하며 필요한 소비자부터 전환합니다.

SDK 버전 선택과 S3 배포, DB 관리도 모두 구현됐나요?

SDK/B/D의 실행 시 선택, 관리 화면, 사용 추적과 삭제 절차는 로컬 저장소로 구현·검증했습니다. S3/CDN 업로드와 운영 인증·권한은 별도 구현이 필요합니다. DB 문서는 이 구조를 옮기는 설계안입니다.

MFE와 특정 로딩 기술을 구분하는 참고: Micro Frontends 개념 소개. 이 문서의 SDK 공유·버전 선택·순환 차단은 프로젝트에서 정한 정책입니다.
